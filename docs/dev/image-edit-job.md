# Upscale and LUT job loop: output modes, the PNG fallback and the run's outcome

This file covers `backend/services/image_edit_job.py`, the one job loop that `POST /upscaling/run`
(`backend/routers/upscaling.py`) and `POST /lut/run` (`backend/routers/lut.py`) both enqueue:
`run_image_edit_job` and its `EditSpec`, the new-file and replace output modes, the PNG fallback
and the `info["out_path"]` it forces every caller to follow, the per-directory occupied-stem
sets, the stored-path gate, chunked lookups and stats refresh, the counts the job writes to
`result_data`, and how `ImageDetailPage` reads that outcome. The models themselves, the
`spandrel` scan, the `.cube`/`.3dl` parsers and LaMa are `docs/dev/image-processing-models.md`;
the shared helpers it calls are indexed in `docs/dev/shared-utilities.md`; what a finished job
invalidates on the frontend is `docs/dev/job-invalidation.md`.

## The loop

**Upscale and LUT share one job loop.** Since M8 stage 3 the two routers keep only the request half (the scope, the `BackgroundJob` row and the enqueue) and hand `services/image_edit_job.run_image_edit_job` an `EditSpec` holding what differs: the job type, the words in its messages, the copy's suffix, the pixel function and the `record_in_place` entry. Everything below is that loop. The spec's callables are built in the router and look up the router's names when called, so a test that patches `upscale_image_sync` or `apply_lut_sync` on the router module still reaches the job; `generate_thumbnail` and `chunked` are patched on `image_edit_job`. A LUT replace writes `width`/`height` from the result as an upscale does, which rewrites the same values, since a grade keeps the size. Inpaint and detection crop stay out: their count keys, commit order and model lease would each need a flag. `test_labels_survive_rebuild_paths.py` reads the loop's one `copy_labels` and checks both routes still enqueue it.

## Output modes

**Upscale output modes**: *New file* — filename `{stem}_up{N}x{ext}` (`{stem}_1x{ext}` when the detected scale is 1, `{stem}_upscale{ext}` when `_detect_scale` returned `None`), where `{ext}` is the extension that will actually be **written** (the PNG fallback below, not necessarily the source's), collision-handled via `unique_filename_with_thumb`; new `Image` record created, thumbnail generated. *Replace* — updates `width`/`height`/`file_size_bytes`/`updated_at`/`processing_history` on the existing record, plus `filename`/`file_path`/`format` when the fallback moved the path; thumbnail regenerated from the written file. Replace mode calls `protect_file_before_overwrite` before overwriting the file — see `docs/dev/versioning/hooks.md` for the copy-on-write mechanism.

**LUT output modes**: *New file* — filename `{stem}_lut{ext}`, `{ext}` being the extension that will actually be written (collision-handled via `unique_filename_with_thumb`), new `Image` record created, thumbnail generated. *Replace* — updates `file_size_bytes`/`updated_at`/`processing_history` on existing record, thumbnail regenerated. Replace mode calls `protect_file_before_overwrite` before overwriting the file — see `docs/dev/versioning/hooks.md` for the copy-on-write mechanism.

## Replace mode follows the PNG fallback

**Replace mode follows the PNG fallback — at all three call sites.** Its twin is the LUT paragraph below (the LUT call site is the same loop), and the reason PM-009 recurred: `upscale_image_sync` ran the identical correction but did not return `out_path`, so its callers were structurally unable to follow it. All three now read `info.get("out_path", …)` — the upscale job in `services/image_edit_job.py` (both modes), and `routers/images.py`'s two crop+upscale workers, whose `_croptmp` source carries the original suffix and hits the same fallback. Replace-shaped paths update `filename`/`file_path`/`format`, commit, and only then unlink the original and regenerate the thumbnail — both best-effort, neither allowed to fail the image (`docs/dev/postmortems/PM-013-fs-mutation-before-the-commit.md`). New-file paths take the row's name *and* its thumbnail from the written path. The pre-write collision guard differs by shape: the batch jobs log, emit progress and skip the image, while `POST /images/{id}/crop` handles one image and answers **409** before touching anything (see `docs/dev/image-detail.md`). Copy mode reserves its name under the written extension, so `unique_filename_with_thumb`'s on-disk check applies to the path that will exist. Tests: `backend/tests/test_upscale_png_fallback_http.py`.

**LUT replace mode follows the PNG fallback too.** `normalize_image_format` falls back to PNG for `.gif`/`.bmp`/`.tiff`/`.avif`, all of which `media_types.IMAGE_EXTENSIONS` accepts, so a replace-mode grade of one of those writes a *different file* from the one it read. The shared loop (`services/image_edit_job.py`) updates `filename`/`file_path`/`format` to match `info["out_path"]` and commits before unlinking the original or regenerating the thumbnail (PM-013 — both are fallible, and a raise between the write and the commit rolled the row back onto a file that no longer existed); without the reassignment the row kept pointing at the stale source, which was also left on disk. A pure extension change moves nothing derived — the stem is unchanged, so the thumbnail and the `.txt` sidecar stay put — but the collision guard runs **before** the save, not after: an unregistered file at the fallback path has no DB row guarding it and is already gone by the time `apply_lut_sync` returns, so such an image is skipped with a message instead. Copy mode reserves its name under the written extension for the same reason — `unique_filename` only stats the suffix it is handed, so reserving `{stem}_lut.bmp` would leave an existing `{stem}_lut.png` to be overwritten. Upscaling is the same story at three more call sites (the paragraph above), and pass-2 video re-extraction does the swap deliberately; see `docs/dev/video/reextract.md` § The extension change.

## Copy mode's occupied-stem sets

**Copy mode's occupied-stem sets are keyed by thumbnail directory.** The upscale and LUT loop (`services/image_edit_job.py`) carries the `occupied_by_dir` / `planned_by_dir` dicts that `routers/detection.py` already had, built lazily per dir *inside* the loop. Neither job constrains its selection by dataset — `Image.id.in_(...)` with a bare id list — while `dest_images` is chosen per image, so the single flat set each of them built from `images[0]`'s `thumbnails/` dir false-shared stems across datasets and let a derived `.webp` overwrite a live sibling's in whichever dataset did not seed the set (PM-007's recorded recurrence, fixed 2026-07-31). `db_names` was already per image in both, which is why only the *thumbnail* was clobbered while the filename looked correct. The general rule: when a guard is built once before a loop but the thing it guards is chosen inside it, something has to make them agree. Tests: the two `..._copy_across_two_datasets_does_not_share_one_thumbnail_stem_set` cases in `test_upscale_png_fallback_http.py` and `test_lut_replace_extension_http.py`.

## The run's outcome

**The run reports what it did.** `batch_upscale` writes `result_data = {processed, skipped, missing, failed, thumbnails_stale, failed_count, failure_summary}` — `skipped` seeded with the rows that vanished between enqueue and run, which `missing` also holds on its own so `ImageDetailPage` can tell a deleted image from the replace-mode name collision when a one-image run did nothing, and committed above `raise_if_cancelled` so a cancelled run keeps its counts. Without it both `continue` branches were invisible and a run that failed on 40 of 50 images still toasted a flat "Upscaling complete". `failed_count` mirrors `failed` and `failure_summary` names up to three files and the first error, built by `backend/job_outcome.py`: the job still ends `completed`, so these two are the only record of *why* once the live `Failed:` message is gone (`docs/dev/frontend-jobs.md` § The partial-failure line on the Logs page). `thumbnails_stale` is the epilogue's own failure: the image is committed and serves, but the gallery tile is the old one. `TopBar` owns the warning and the repair pointer for all four such jobs — see `docs/dev/frontend-jobs.md` § The stale-thumbnail warning.

`batch_lut` carries the same `result_data` as its upscale twin, `failed_count` and `failure_summary` included, with the same seeding and the same placement above `raise_if_cancelled`, and the same path gate, chunked lookups and stats refresh (§ The stored path is a gate, below).

## The stored path is a gate

**The stored path is a gate, the id lookups are chunked, and the run refreshes stats** — all three shared with `batch_lut`.

- **The gate.** Each iteration runs `utils.contained_path` on `img.file_path` before `protect_file_before_overwrite` and before any path is derived: a link in `images/` would otherwise have a replace-mode write go through it to a file outside the datasets folder, while the versioning backup refuses the same path and lets the write go ahead. A refusal counts as `failed`, with `utils.OUT_OF_TREE_MSG` as its `Failed:` message and its `failure_summary` entry. It is only a gate — everything after it keeps the row's own spelling (the Stored-path containment entry in `docs/dev/shared-utilities.md`).
- **Chunked lookups.** Both the request-time lookup of a client's `image_ids` and the job's image load go through `utils.chunked`, since a whole-dataset run can pass SQLite's bind limit. The request-time lookup is `services/image_scope.resolve_scope_ids`, shared with LUT, inpaint and detection crop.
- **The stats refresh.** After the final commit and before `raise_if_cancelled`, the job runs `dataset_service.refresh_stats` for every dataset it touched: a replace changes `total_size_bytes`, a copy adds to `image_count`, and both are stored columns. That is detection crop's epilogue, best-effort and per dataset (PM-013, PM-029).
- **The refresh on a raise.** A raise outside the per-image `try`, or a hard cancel, skips that tail with earlier images already committed, so `run_image_edit_job` wraps the loop and calls `dataset_service.refresh_stats_after_abort` on the same `touched` set before re-raising — `videos._run_with_stats`' shape, and that of inpaint, detection crop and batch resize and crop too. Every one of them adds a dataset to `touched` **before** the commit that changes it, so a hard cancel landing in that commit (or in detection crop's thumbnail epilogue) still refreshes it; adding early is harmless, since an unchanged dataset refreshes to the same numbers.

Tests: `backend/tests/test_edit_jobs_scope_and_stats_http.py`, `test_edit_job_failure_summary_http.py` and `test_out_of_tree_edits_http.py`.

## The detail page's outcome read

The Upscale tool's button and controls are listed with the other surfaces in
`docs/dev/image-processing-models.md` § Upscaling.

`ImageDetailPage` — "Upscale" toolbar button toggles inline controls (model select, Replace checkbox, optional W×H). Uses `upscalingApi.run()` with `image_ids: [imageId]`. On completion it reads the job's counts through the page's `fetchEditOutcome`, never the status alone: a one-image run that failed still ends `completed`, and its last progress event can carry a stale `image_id`. `processed: 0` shows `failure_summary` (or a skip warning naming the deleted image, the name collision, or nothing changed, from `missing` and `skipped`), leaves the tool open to try again, and navigates nowhere. Run is held from the POST's success to a terminal status, `pending` included, so a job queued behind another cannot be started twice; a `cancelled` status clears the id like the other two. The id is cleared before that GET returns, though, so Run is live meanwhile: a per-tool generation ref, bumped at each run's `onMutate` and on every `imageId` change and bound to the job in `onSuccess` with the image the run was for, lets a stale outcome toast but never close the tool or navigate. The generation alone is not enough: a navigation renders as a React transition, so the outcome can land after the click and before the render that would bump it. The page therefore also compares the run's image with `intendedImageId`, which reads the URL, or the pane store through `paneStore.currentPaneView`, both of which move at the click. `frontend/e2e/detail-edit-outcome.spec.ts` pins all of it with stubbed jobs. The LUT tool does the same.
