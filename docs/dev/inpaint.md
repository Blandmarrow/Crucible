# Painting detections out (watermark removal)

This file covers the watermark-removal job: how it consumes detections, the paint mask,
path gating, replace mode and the `has_watermark` rule, copy mode, and its counts and frontend.

`POST /inpaint/run` (`backend/routers/inpaint.py::run_inpaint`, schema `InpaintRunRequest`) enqueues a `batch_inpaint` job that rasterizes an image's existing `Detection` rows into a mask and paints that region out with LaMa. It shares the loop shape of the bulk jobs in `docs/dev/bulk-image-jobs.md` and is structurally the closest to `crop_to_detection` (`docs/dev/detection-crop.md`): the same scope triple, the same replace/copy branches, the same per-thumbnail-directory collision dicts, the same PM-013 loop ordering, the same `result_data` placement above `raise_if_cancelled`. The model half is `docs/dev/image-processing-models.md` § LaMa inpainting, and the user-facing side is `docs/editing.md` § Watermark removal.

## Consuming detections

**It consumes detections; it never produces them.** The flow is two steps and the first is a grounding detection pass (`docs/dev/detection.md`). Nothing in this router runs a detector, so an image with no matching detection is `skipped_no_detection` — pre-filtered in the *handler*, before the job row is created, so `total_items` is honest and the response carries `{job_id, total, skipped}` like `POST /detection/crop`. `_fetch_masks_by_image` is `detection.py::_fetch_bboxes_by_image` widened to `(id, mask_json, bbox)` triples, keeping the `chunked()` wrapper for SQLite's bind ceiling.

## The paint mask

**`rasterize_detections`, never `compose_loss_mask`.** The latter's empty-`include` case deliberately returns full white, which trains an image unmasked — and here would repaint the *entire* image. `rasterize_detections` fails safe in the other direction: empty geometry rasterizes to all black and nothing is painted. The mask is then grown by `dilate_px` (a `MaxFilter` over an odd window, exact for a binary mask; default 6) because a segmentation boundary sits tight against a semi-transparent watermark and leaves a halo of its edge pixels behind. Measured against a synthetic watermark, 6 costs nothing and 12 starts eating neighbouring detail.

**The whole mask build runs in an executor, and `_dilate` is bbox-limited.** Rasterize → dilate → PNG-encode is `_build_mask_png`, a module-level sync helper called through `run_in_executor` — full-resolution Pillow work with no `await` in it, which on the event loop freezes every other request (the SSE progress stream included) for its duration. `export_service._write_mask` is the precedent. The dilation is the expensive half: `MaxFilter` is a `RankFilter` selecting over all *k*² window pixels per output pixel, so the cost scales with `canvas_area × (2·px+1)²` — 2.0 s at the default `px=6` on a 4000×3000 mask and 168 s at the schema's max of 64. `_dilate` therefore filters only `mask.getbbox()` grown by `px` and pastes the result back, which is **exactly** equivalent (dilation cannot reach further than `px` from a white pixel; outside the crop every window sees black either way, and at the image border both runs face the same padding). `backend/tests/test_inpaint_dilate.py` pins that equivalence against a naive full-canvas filter, empty and border-touching masks included.

## Path gating

**Every stored path goes through `utils.contained_path` first, which makes this router stricter than its `lut.py`/`upscaling.py` siblings — deliberately.** `img.file_path` is gated at the top of each iteration, above `protect_file_before_overwrite`: that helper copies the bytes into `{ds}/.versions/objects/`, so an out-of-tree value is an arbitrary-file *read* primitive even before the overwrite, and the copy branch derives its destination from the path's parent. `img.thumbnail_path` is gated in the replace epilogue, because `generate_thumbnail` mkdirs its parent and an out-of-tree value is an arbitrary-file *write* primitive — the reasoning CLAUDE.md gives for `images.bulk_thumbnails`. `contained_path`, not `safe_dataset_path`: a 403 is wrong inside a job loop, so a refusal logs, counts (`failed` for the source, `thumbnails_stale` for the thumbnail) and `continue`s, and everything downstream uses the **resolved** path the helper hands back. Read the difference from the siblings as intent, not as a sweep that stopped early.

## Replace mode and the watermark flag

**Replace mode writes four things above the commit** and nothing fallible sits between the overwrite and it: `file_size_bytes`, `phash` (returned by `inpaint_image_sync` precisely because nothing else would refresh it), the filename/path/format trio when the PNG fallback moved the file, and the `record_in_place(img, "inpaint", …)` that stamps `processing_history` and `scores_stale`. Geometry is unchanged, so — unlike `crop_to_detection` — there is **no** `remap_detections_for_crop` and no `width`/`height` write. Two more DB-only writes share that transaction: the consumed `Detection` rows are deleted by id, and `has_watermark` is cleared under the rule below. The post-commit epilogue is the usual pair: unlink a superseded original, re-cut the thumbnail, `thumbnails_stale += 1` on failure.

**`has_watermark` is cleared iff the image has no detection left at all**, and the `iff` is the whole rule. Crucible has **no vocabulary of "watermark labels"** — `detection._apply_watermark_flag` sets the flag from `bool(detections)` on a watermark-sync grounding run, whatever the phrase was — so a run scoped to some other label cannot tell whether what survived is a watermark; clearing anyway would let the image escape both the *Flagged: watermark* filter and export's `exclude_flags` and ship with the watermark visible. Deciding it costs one extra batched `select(Detection.id, Detection.image_id)` over `matched_ids` (`_fetch_detection_ids_by_image`, unfiltered by label — the companion to `_fetch_masks_by_image`), never a per-image query. The write is copy-then-reassign (`flags = dict(img.quality_flags or {})`), because SQLAlchemy compares JSON columns by equality and an in-place mutation is silently skipped; when nothing is cleared the column is not written at all rather than reassigned to an equal dict. The common workflow — detect `watermark`, then paint that label — still clears.

**`watermark_score` is left standing, stale.** `record_in_place` sets `scores_stale`, so the number is visibly flagged rather than silently trusted, and clearing the *flag* while leaving the *score* is the honest pair — nothing here measures anything. The Quality page therefore shows a stale score beside a cleared flag until the user re-scores. See `docs/dev/quality/scores-stale.md`.

## Copy mode

Copy mode writes a `{stem}_nowm` derivative through `unique_filename_with_thumb` with `**copy_provenance(img)`, records `derivative_ids` and calls `copy_labels` after the loop so a cancelled run still labels what it copied — the fifth same-dataset derivative site, pinned by `backend/tests/test_labels_survive_rebuild_paths.py`. It touches the parent not at all: the parent still has the watermark, so its detections and its flag stay. Only the copy branch `undefer`s `Image.source_meta`; undeferring in replace mode would load a scraper's full raw payload for the whole batch and discard it. **Its ordering is PM-013 Tier 1, not the Tier 3 the four sibling routers still carry**: `new_img` is built with its `thumbnail_path` set, `session.add` → `commit()` (the id read back afterwards, `expire_on_commit=False`), and only then is the thumbnail cut, inside a `try/except` that counts `thumbnails_stale` and cannot change the item's outcome. Cutting first lets an `OSError` on image 300 of 500 propagate out of `_run`, where `job_queue` marks the job failed from a separate session and this one rolls back **every** uncommitted derivative row while their `_nowm` files stay on disk.

## Counts and frontend

Counts are `{inpainted, skipped_no_detection, skipped_name_taken, failed, thumbnails_stale}`. `skipped_name_taken` is the PNG-fallback squatter branch — an unregistered file already sitting at the `.png` the write would take — and is a separate key precisely so `skipped_no_detection` keeps only its two real causes (a row that vanished between enqueue and run, and one whose label filter matched nothing); blaming the detection pass for a stray file on disk sends the user looking in the wrong place. `InpaintForm.resultToast` surfaces it as `N skipped (name already taken)`. **Frontend**: `InpaintForm` (`frontend/src/components/inpaint/InpaintForm.tsx`) — the `CropToDetectionForm` props contract (`docs/dev/detection-crop.md` § Frontend) and single-job pattern, plus `apiErrorDetail` in `onError` so a missing-weights `FileNotFoundError` or a 507 reaches the toast. Mounted twice: a **Remove Watermark** button in the `ImageDetailPage` toolbar (gated on the image having detections, scoped to `imageIds=[imageId]`, `onSuccess` also invalidating `["image", imageId]`) and a **Remove WM** modal in `SelectionToolbar`. `batch_inpaint` is registered in all three `TopBar` sets it belongs to — `IMAGE_MODIFYING_JOB_TYPES`, `THUMBNAIL_EPILOGUE_JOB_TYPES`, and the detection branch, since it deletes `Detection` rows — and deliberately **not** in `LIVE_IMAGE_JOB_TYPES`. `backend/tests/test_inpaint_http.py` covers the whole loop torch-free.
