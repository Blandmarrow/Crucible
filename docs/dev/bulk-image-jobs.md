# Bulk image jobs (resize, crop, thumbnails)

This file covers the bulk operations that rewrite pixels or files as a `BackgroundJob` —
batch resize and aspect crop, and the thumbnail rebuild — plus the detection remap that
every replace-mode crop runs. These jobs and detection-driven cropping
(`docs/dev/detection-crop.md`) share one loop shape — per-item failure counting that never aborts the run, `job_queue`
cancellation checks, and a `result_data` counters dict — so a reader debugging one of them is
usually reading the right file for the others. Three things they do **not** share, each worth
knowing before assuming: only `bulk_thumbnails` calls `contained_path`, the others passing
`img.file_path` raw; `regenerate_thumbnails` writes no `thumbnails_stale` counter, being
itself the repair; and the PM-013 per-item commit ordering, though now universal here, was
reached at three different times by three different fixes. The watermark-removal job,
`batch_inpaint` (`docs/dev/inpaint.md`), shares the shape too, and gates every stored path
through `contained_path` on purpose.

The metadata side of "bulk" lives in `docs/dev/bulk-ops.md`: `_apply_bulk_filters`, the
endpoint table, caption find/replace, `BulkEditPage`'s tabs and Renumber's two-phase rename.
The detector whose geometry the remap rewrites is `docs/dev/detection.md`; the job-completion
toasts and invalidations are `docs/dev/frontend-jobs.md`; the commit-ordering invariant is
CLAUDE.md § Key invariants and `docs/dev/postmortems/PM-013-fs-mutation-before-the-commit.md`.

## Batch resize and aspect crop

`POST /images/batch/resize` (`{image_ids, width?, height?, scale?, maintain_ar, label?}`) and `POST /images/batch/crop` (`{image_ids, target_ar, strategy, label?}`) enqueue `batch_resize` / `batch_crop` jobs that rewrite each image **in place**: `image_service.resize_image`, or `aspect_crop_rect` (the rect, computed without writing) then `crop_image_to_dest`, into a `{stem}_resizetmp_{token}`/`_croptmp_{token}` temp file (`image_service.temp_sibling`) that is swapped over the original last. The random token is load-bearing: the images folder is the user's, and a fixed temp name can be another registered image's — a stray a rescan adopted — which the write would overwrite and then swap away. Both take a bare id list with no dataset constraint, so `_guard_batch_datasets` resolves every dataset the selection touches and `ensure_not_busy`-guards each one before the job row is created; it also sets `BackgroundJob.dataset_id` when the selection resolves to exactly one dataset. `result_data` carries the same four counters as the LUT and upscale runs (`processed`, `skipped`, `failed`, `thumbnails_stale`), and both loops honour `job_queue.cancel_requested`.

The loop shape is **stage, flush, swap, commit** (GPT-010), the order every replace-mode crop and resize shares: `protect_file_before_overwrite` + commit; then, inside one `try`, write the output to the temp file, assign every row field (geometry, `file_size_bytes`, `phash` — measured from the output by `image_service._save_measured`, GPT-016), `record_in_place`, (crop only) `remap_detections_for_crop`, `session.flush()`, and finally `replace_retrying(tmp, original)`; then the per-image `commit()`, then a post-commit epilogue for the thumbnail and the SSE emit. A raise anywhere in the `try` rolls back, discards the temp file and counts `failed` with the original's pixels, row and detections untouched.

**Why the remap moved above the swap.** It used to run *after* the overwrite, as "DB-only work, so it stays above the commit" — reasoning that treats a raise as a clean rollback. It is not: a remap is a SELECT plus ORM writes that can fail (a locked database, a malformed stored mask), and a raise there rolled the row back onto pixels that no longer matched it — the disk held the crop, the row the old geometry, and the `processing_history` entry pass 2 reads was gone (PM-010's consequence). Flushing first surfaces any DB error while the original is intact, so only the commit itself follows the irreversible step. Because a failed item **rolls the session back**, which expires every instance in it, the loops load each row per item (`session.get`) instead of iterating a list loaded up front — touching an expired instance lazy-loads on an async session and raises `MissingGreenlet`. Each job then calls `refresh_stats` once per touched dataset, since `total_size_bytes` moved.

Both record the rewrite through `backend/utils.py::record_in_place(img, op, **params)`, and so does every other in-place path in the repo — the `crop_to_detection` job (`docs/dev/detection-crop.md`), `batch_inpaint` (`docs/dev/inpaint.md`), `batch_lut`, `batch_upscale`, `crop_upscale`, the two single-image twins, and `video_reextract`. It was `images.py`'s private `_record_in_place` until 2026-07-31; the four routers that could not import it had each hand-rolled a copy. Promoting it to `utils.py` made it the single writer of `processing_history` **and** `Image.scores_stale` (set only when the row already carries a score), which is the point: a site that appends the history entry by hand records the edit and leaves the scores looking trustworthy. A structural AST guard in `backend/tests/test_scores_stale.py` fails CI for the eleventh site that tries. It is staged with the other row fields ahead of the swap and the per-image `commit()`, never in the epilogue — it is pure attribute access and cannot raise. See `docs/dev/quality/scores-stale.md`.

**Both endpoints were unreachable until 2026-07-31**, declared below `POST /images/{image_id}/resize` and `/{image_id}/crop`, which match first because `image_id: str` accepts the literal `"batch"`. They now sit above those routes, and any future `/batch/*` route on this router belongs in the same block — declaration order *is* the routing table (`docs/dev/postmortems/PM-018-batch-routes-shadowed-by-a-path-parameter.md`). Two consequences of that history remain open on purpose: neither job type is in `TopBar.tsx`'s `IMAGE_MODIFYING_JOB_TYPES`, and neither is in its `THUMBNAIL_EPILOGUE_JOB_TYPES` either, so a run whose previews all failed to rebuild writes `thumbnails_stale` and tells the user nothing. Both are open because no UI can start them — `frontend/src/api/images.ts` defines `batchResize`/`batchCrop` and nothing calls either. Wiring a UI means touching both `TopBar` sets, not one. `backend/tests/test_batch_resize_crop_http.py` covers the route order, the per-image commit, the epilogue and the 409.

## Rebuilding thumbnails

`POST /images/bulk-thumbnails` is the **repair** for every job that re-cuts an image thumbnail as a best-effort post-commit epilogue. When that epilogue raises, the image is correct and committed but the gallery keeps drawing the old tile, and nothing self-heals it: `GET /images/{image_id}/thumbnail` only regenerates when the file is *missing*, and the stale file exists.

**Eight jobs write `result_data["thumbnails_stale"]`; six surface it.** The writers are `batch_lut`, `batch_upscale`, `crop_upscale`, `crop_to_detection`, `batch_inpaint`, `video_reextract`, `batch_resize` and `batch_crop`. `TopBar`'s `THUMBNAIL_EPILOGUE_JOB_TYPES` holds the first six, so those turn the count into the one warning toast (`docs/dev/frontend-jobs.md`); the two batch jobs record it and nothing reads it, because no UI can start them yet — see § Batch resize and aspect crop.

The request body carries a **scope, never the affected id list**. The realistic trigger — a full volume, a read-only `thumbnails/` — is deterministic, so "the affected images" is "everything the run touched"; an id list would be thousands of uuids serialized into every `GET /jobs/` row, and it is least available exactly when it matters (`job_queue` fails a raising job from a separate session and never persists the worker's dict). Over-scoping is safe here in a way it never is for delete or rename: regenerating a correct thumbnail costs one re-encode.

- **Scope**: the shared `_apply_bulk_filters` triple, plus `Image.dataset_id == body.dataset_id` **only** when `image_ids` is empty — a `SelectionToolbar` selection can span datasets, exactly as in `bulk_provenance`. `ensure_not_busy` runs for every dataset the rows actually touch.
- **Preflight**: `require_free_space` → **507**, on the request path so no job row is created. This is the repair you run *because* the volume filled up, so a 507 is the right answer rather than 400 more log lines.
- **Job body** (`regenerate_thumbnails`): rows are loaded through `utils.chunked` — `_apply_bulk_filters` builds one query and does not chunk, but it never binds the ids; this loader does. Per row: cancel check, progress emit, then `contained_path` on **both** `file_path` and `thumbnail_path` — `generate_thumbnail` `mkdir(parents=True)`s its destination's parent, so an ungated stored path is an arbitrary-file-*write* primitive, not merely a stale tile. A `None` gate or an absent source counts `skipped`; a row with no `thumbnail_path` falls back to `thumbnail_path_for`. The re-encode runs in an executor under a per-row `try/except → failed += 1; continue`, so the repair does not inherit the failure mode it exists to fix.
- **`updated_at` is bumped on every repaired row, and that is load-bearing**: `imagesApi.thumbnailUrlVersioned` builds `?v=${Date.parse(updatedAt)}`, so a repair that rewrites the `.webp` without moving the row leaves the `<img src>` byte-identical and the browser serves the stale tile from cache — the repair would visibly do nothing. The column value written to `thumbnail_path` is the *stored* form (derived from `img.file_path`), never the `.resolve()`d path the write uses, so the stored-path form does not drift mid-table.
- Commits every 50 rows; `result_data = {regenerated, failed, skipped}` is written above `raise_if_cancelled`, so a cancelled run keeps what it repaired. **No `refresh_stats`** — a thumbnail is not counted in `total_size_bytes`, and nothing else this job writes appears in a dataset rollup.
- Tests: `backend/tests/test_regenerate_thumbnails_http.py` (the `updated_at` bump, the out-of-tree refusal, subfolder scoping, an unreadable source, the 507, a cross-dataset selection) and `frontend/e2e/thumbnails.spec.ts`.

`RegenerateThumbnailsForm` (`frontend/src/components/image/RegenerateThumbnailsForm.tsx`) — the `UpscaleForm` props contract, the single-job `jobId` + `useJobStore` pattern, and a `resultToast` in the `CropToDetectionForm` shape (`docs/dev/detection-crop.md`). Two surfaces: the **Thumbnails** tab on `BulkEditPage` and a **Thumbnails** button + modal in `SelectionToolbar`. The tab is the one that matters — a deterministic failure means "the whole dataset", and `SelectionToolbar` only exists when there is a selection. `targetsFlaggedImages` stays `tab === "delete"`, so the shared scope panel and its cache key are unchanged.

## Remapping detections through replace-mode crops

Any crop that *replaces* the image changes its geometry, so its normalized detection coordinates must be re-expressed relative to the crop.

- **The pure remap** is `backend/ml/mask_utils.py::remap_detection_geometry(mask_json, bbox, rect, old_size)`. `rect` is `(x, y, w, h)` **in pixels of the OLD image's EXIF-transposed frame** (the frame detection coords live in — captured *before* `Image.width/height` are overwritten), `old_size` is `(old_w, old_h)` of that frame. Each coordinate maps `new = (n*old_dim − offset)/extent`, so the crop becomes the unit square.
- **Malformed stored masks** are dropped, not raised on: every reader of `Detection.mask` parses through `mask_utils.stored_polygons`, which keeps only lists of at least three two-number points. A `{"polygons": 5}` written by raw SQL used to `TypeError` out of the remap and fail every crop of that image.
- **Dropping rows.** The bbox is the primary (non-nullable) geometry: if its remapped extent < 0.002 on either axis the detection is outside the crop and the fn returns `None` (delete the row). The bbox is clamped to [0, 1], which for an axis-aligned box is clipping. Polygons are **clipped**, not clamped: the remapped ring goes through `_clip_polygon_unit`, a pure-Python Sutherland–Hodgman clip against the unit square (no cv2 or shapely, so it runs in CI). Clamping each vertex used to invent geometry — a triangle wholly outside the crop, whose vertices clamped onto two different borders, came back as a mask inside it (GPT-017). A concave ring that leaves and re-enters stays one ring joined by zero-width runs along the border; those enclose no area. A clipped polygon with fewer than three distinct vertices or shoelace area < 1e-4 is dropped, and a masked detection that loses every polygon keeps its bbox with `mask=None`.
- **The async orchestrator** `backend/services/detection_service.py::remap_detections_for_crop(session, image_id, rect, old_size) -> (remapped, dropped)` selects all of an image's detections, deletes the `None` results and writes `det.mask` **then** `det.bbox` via ORM assignment (bbox last so the final `mask_area` listener recompute sees both — see `docs/dev/detection.md`). It does **not** commit; the caller owns the transaction.
- **Call sites** (each captures `old_size` before mutating dimensions): the `crop_to_detection` worker replace branch (`docs/dev/detection-crop.md`), `routers/images.py::crop` sync-replace path, `_run_crop_upscale_replace` (remapped only after a successful upscale — a failed upscale must not remap), and `routers/images.py::batch_crop` (`aspect_crop_rect` returns its rect + orig dims without writing). Every one of them remaps **before** the swap and flushes it, so a failed remap leaves the original untouched (§ Batch resize and aspect crop).
- **Exempt** (normalized coords are invariant under pure scaling): resize/`batch_resize` and all upscaling; new-file crop paths (the new row has no detections to remap). Coordinates are invariant under scale because they are already fractions of the image.
- **Version restore needs no remap:** a snapshot records each image's detections alongside its pixels, and a restore writes the snapshot's set back (GPT-026), so the geometry returns in the frame of the restored file rather than being remapped through the crop in reverse. See `docs/dev/versioning-service.md`.
