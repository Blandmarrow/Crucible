# Duplicate detection — the pHash grouping and the flag it writes

This file covers how Crucible finds duplicates and keeps the duplicate flag true: `find_duplicates_sync`'s two exact implementations, and `backend/services/duplicate_service.py`, which owns the `is_duplicate`/`duplicate_of` pair across re-scans, deletes and cross-dataset copies. What the user sees and does with the groups — the `GET /quality/duplicates/{dataset_id}` read path, the panel, *Keep best* and the bulk resolve — is `docs/dev/quality/duplicate-resolution.md`. The `phash` it groups on and the `duplicate_threshold` setting are `docs/dev/quality/scoring.md`. Part of the Quality family; the hub, `docs/dev/quality.md`, routes from a code path to the file that owns it.

## Duplicate detection

**Duplicate detection** (`technical_scorer.find_duplicates_sync`) runs after technical scoring: it greedily groups images whose phash Hamming distance is `< duplicate_threshold` (first unassigned image is the group root and claims every *later* unassigned image within the threshold, members in input order; each image is claimed once). `find_duplicates_sync` is a **dispatcher over two exact, output-identical implementations** — only speed differs, never results:

- `_find_duplicates_indexed` (the path at scale): a pigeonhole multi-index chunk search, ~linear in N. Each hash is split into 4 chunks; any pair within distance d must agree on ≥1 chunk up to ⌊d/4⌋ bit flips, so probing 4 chunk tables with the chunk value XOR every ≤⌊d/4⌋-bit mask is guaranteed to surface every true neighbor as a candidate, which is then verified with the exact `dist < duplicate_threshold` popcount comparison. **Do not "simplify" the chunk count or radius derivation** — an undershoot silently drops duplicate pairs.
- `_find_duplicates_bruteforce`: the O(N²) vectorized all-pairs scan (numpy + module-level 256-entry `POPCNT` table). Semantically frozen — it is the reference implementation the golden tests compare against, and the fallback when `n < MIN_INDEX_N` (2048), the hash is shorter than 4 bytes, the threshold is so large the index would probe more than `CANDIDATE_FRACTION_CUTOFF` (0.25) of all rows per query (≥ ~21 for 64-bit hashes; practical thresholds are 4–12), or the total probe volume exceeds `n // PROBE_COST_DIVISOR` (8) — probes are pure-Python dict lookups, far costlier each than a vectorized scan row, so the index must be clearly cheaper before it engages (at 64-bit hashes, thresholds 13–20 need n ≳ 22k–80k).

Both paths are length-generic (no 64-bit assumption; the chunk-key fold must stay **unsigned** — a signed int64 fold wraps 8-byte-chunk keys negative and silently drops pairs whose probe crosses bit 63). The dispatcher and the golden tests both derive the chunk split and probe radius from the shared `_chunk_plan()` helper, so the tested plan cannot drift from the production one. `backend/tests/test_find_duplicates.py` pins the byte-identical-output property (groups, roots, member order) across sizes, thresholds (incl. floats — `threshold_settings.duplicate_threshold` is a Float column, though the quality router currently truncates it to `int` before calling, so algorithm-level float support is future-proofing), and hash lengths up to 256-bit; it runs in CI via `.github/workflows/backend-tests.yml` (cv2 is imported lazily inside `score_technical_sync`, so *these* tests need no cv2 and no stub — the workflow installs it anyway, for the video suite: see `docs/dev/video-tests.md` § cv2 in CI, and the skip convention). The O(N²) path was the critical scaling wall found in `backend/scripts/scaling_bottlenecks_report.md` (~3.4 h projected at 1M images); re-verify with `python -m backend.scripts.bench_scaling --only dedup` after touching this code. The consumer `_flag_duplicates` (`routers/quality.py`) then loads the flagged images with a single chunked `select(...).where(Image.id.in_(...))` (≤10k ids per chunk) rather than per-row `session.get`, and follows the copy-then-reassign `quality_flags` invariant. `backend/tests/test_quality_flags_persistence_http.py` pins that invariant at request level: duplicate-resolve keep and empty-caption artifact clearing must persist their flag changes to a fresh session.

### The flag is a relationship, and both directions are maintained

`is_duplicate` is never a property of one image: it is meaningful only alongside `duplicate_of`, which names *another row*, so the flag can be falsified by a delete that never touches the flagged row — and derived relational state maintained additively drifts silently in both directions at once. `backend/services/duplicate_service.py` owns that invariant, and there are exactly two ways to maintain it — recomputation and pruning. Both live there; nothing else writes the pair except `resolve_duplicates`' keep-side clear. See `docs/dev/postmortems/PM-022-orphaned-duplicate-flags.md` for the incident that produced this section.

**The scan is authoritative, so a re-scan is the repair.** `_flag_duplicates` hands the whole grouping to `apply_duplicate_groups(db, dataset_id, dup_of)`, which flags every row in `dup_of` **and clears every other currently-flagged row in the dataset** in one pass. There is deliberately no `if not dup_of: return` — zero groups found is precisely the case that must clear the dataset, and reinstating that early return is what would break the recovery path a user is told to run. The clear side is keyed on the stored flag rather than on the scan's input, so a row that has since lost its `phash`, or one flagged by an earlier run at a looser `duplicate_threshold` that a stricter one no longer groups, is repaired too. Scoped to the scanned dataset, and only ever the two duplicate keys — an unrelated flag on the same row is not this function's business.

**Every path that deletes `Image` rows prunes, between its row DELETEs and the commit** — one commit, atomic with the delete. The image deletes unlink *before* that transaction's DELETE (files first, PM-021, GPT-008), so a row whose file is locked is never deleted and never counted gone. Six sites call `prune_orphaned_duplicate_flags`: `images.delete_image`, `images.batch_delete`, `images.bulk_delete_filtered`, `filesystem.delete_path`, `videos._delete_previous_frames`, and `quality.resolve_duplicates` (a backstop, after the `keep_ids` loop, for a resolve that deletes a root without naming every survivor). **Five of them are atomic with their delete; `resolve_duplicates` is not, and cannot be.** Its prune has to run after the `keep_ids` clears so it counts survivors against them, and those clears come after the delete's own commit — so there it is a **second** transaction. The cost is stated rather than fixed: a failed second commit leaves drift, and a Technical re-scan repairs it. A keep-only call (no `delete_ids`) has an empty `dataset_ids` and so skips the prune entirely — an API caller that clears a flag and thereby strands the last survivor of an already-dead root leaves it flagged until the next delete in that dataset. `QualityPage`'s only call site always pairs a group's keep with its own deletes, so the UI cannot reach it.

Three sites are deliberately exempt from the prune and say so in a comment, so the next sweep does not "finish the conversion": `comfy.py`'s failure-path cleanup (rows generated seconds earlier, never scanned), `version_service.restore_snapshot`'s extras removal (a restore rewrites `quality_flags` wholesale from `VersionImageState`, so its output is snapshot-defined — a re-scan is the repair), and `datasets.delete_dataset` (the whole dataset goes, so there are no survivors).

**The rule is narrow: a flagged survivor is orphaned iff its root row is gone *and* it is the only surviving flagged member of its group.** Two survivors of a dead root are still duplicates of each other and keep their flags — the group `get_duplicates` renders with no `kept` row, deliberately.

**The prune takes the datasets touched, not the ids deleted.** Deriving the affected group keys from the deleted ids is the obvious implementation and it is wrong: it only works when the root goes in the same request. Prune a group one image at a time from the lightbox — the likeliest way a user does it — and the delete that strands the last survivor names a *member*, whose own `duplicate_of` is unreadable by then because its row is already gone. Re-checking the invariant across the dataset instead is idempotent, placement-insensitive, and repairs orphans an older build left behind on the first delete that touches that dataset. It costs one scan over an unindexed JSON extract, alongside the `refresh_stats` aggregation all six endpoints already run. A flagged row with no `duplicate_of` at all is left alone — it names no root, so no delete orphaned it, and `apply_duplicate_groups` is what clears that shape.

**Crossing a dataset boundary: remap or strip, never copy.** A group only ever exists inside one dataset, so `duplicate_of` is a derived-from-elsewhere value in exactly the sense `Image.source_video_id` is, and CLAUDE.md's rule for that column applies unchanged. Carried verbatim it is worse than the orphan PM-022 was about: the destination holds a flagged image naming a row it does not contain, its duplicates panel cannot resolve the group, and **no prune can ever reach it** — the root is alive, just somewhere else. `duplicate_service.carry_duplicate_flags(flags, id_map)` is the one rule, and the four boundary sites import it rather than re-inlining it: `images.batch_copy_dataset`, `images.batch_move_dataset`, and `dataset_service.duplicate_dataset`'s two branches (the on-disk one keyed on the source row id, the snapshot one on `VersionImageState.image_id`, which is nullable and carries no FK — a state whose image is gone contributes no entry, so any mark naming it is stripped). `_clear_duplicate_flags` is expressed as `carry_duplicate_flags(flags, {})`, because "no root came with it" and "the root is gone" are the same answer.

Two details of the carry are load-bearing. **The remap is a second pass, not part of the row constructor**: in both copy paths the id map is filled inside the loop that builds the rows, so at row *i* it holds only rows `0..i-1` and an in-constructor remap would miss every forward reference. Each path keeps a `new_by_source` beside its id map and applies the carry after the loop, while the rows are still pending in the session — preserving its stage-DB → copy-files → commit ordering. **A move maps the ids to themselves**: a move is an UPDATE in place, so a whole group travelling together resolves and keeps its marks, while a member leaving its root behind arrives unflagged. `batch_move_dataset` therefore selects `Image.quality_flags` into `_move_cols` (small, unlike the `source_meta` that column list deliberately excludes) and carries it inline in the per-row UPDATE.

**Two readers agree that a root is a row in the same dataset.** The prune's aliveness query is scoped to the dataset it is pruning, so a root that *moved away* counts as gone exactly like a deleted one — which makes the first delete in a dataset a repair for any cross-dataset drift an older build left there. `get_duplicates`' root lookup is scoped the same way: an out-of-dataset root then renders the group with no `kept` row (the case the endpoint already handles for a root deleted since the scan) instead of pulling a foreign image into the payload, where *Keep best* could reach it and delete an image from a dataset the user was not looking at. Neither change disturbs the two-survivors rule, which counts flagged **members**, not roots. `backend/tests/test_duplicate_flags_cross_dataset.py` pins all of it — the four writers and both readers.

`backend/tests/test_duplicate_flags_authoritative.py` covers the reconciliation and the prune at service level (no cv2, no torch, no job queue); the delete paths are pinned request-level in `test_duplicate_groups_http.py`, including the case the prune must *not* touch.
