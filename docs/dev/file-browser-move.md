# File browser: `POST /move`

The `POST /move` endpoint of the `/filesystem` router: its file and directory branches, the 409s that refuse re-homing a registered file or moving a folder that holds rows or derived artifacts, why the directory branch rewrites nothing since V-21, and `_find_dataset_for_path`, which only this endpoint calls. The endpoint table, § Name collisions, § Path safety and § Still open are in `docs/dev/file-browser.md`; `POST /rename`, which reuses this file's derived-artifact guard and escaped prefix tests, and `POST /delete` are in `docs/dev/file-browser-rename-delete.md`.

## `POST /move`

**`POST /move` has two branches, chosen from `src` *before* `shutil.move` runs** — `src` no longer exists afterwards, so a late `is_file()`/`is_dir()` answers False for both and the whole sync becomes dead code (PM-011).

- **File branch.** Looks up the `Image` or `Video` row whose `file_path` is the source — also before the move, so the 409 below lands with the filesystem untouched, matching the collision guards' convention. If a row exists and the destination is not inside that row's own dataset, the move is **refused with a 409**: re-homing is `batch_move_dataset`'s job (provenance materialization, stats refresh, NULLing `Image.source_video_id`, moving the poster/thumbnail), and none of it happens here. The condition is `new_ds is None or new_ds.id != row.dataset_id` — deliberately broader than "another dataset", because a registered file moved out of the datasets tree entirely is equally broken: `utils.safe_dataset_path` then 403s every request for its bytes. Files with no DB row still move anywhere. Otherwise only `file_path`/`filename` are rewritten.

  Same dataset is not sufficient either: the destination must be *directly* the dataset's canonical media folder (`images/` for an image, `videos/` for a video), else 409. Two silent failure modes otherwise. `_rescan_videos` globs `videos_dir.glob("*")` non-recursively, so a video parked in `{ds}/images/` or `{ds}/videos/sub/` is reported under `videos_missing` forever while the file is perfectly fine. And images are stored **flat** — `Image.subfolder` is a purely logical column — so `images/sub/a.jpg` makes `thumbnail_path_for`'s `parent.parent` resolve to `images/thumbnails/`, at every site that re-derives a thumbnail path from a filename. The check is nested under "a row exists" on purpose: unregistered files still move anywhere, which is the file browser's actual job.
- **Directory branch.** Checks for rows under the moved folder before `shutil.move`, for the same reason the file branch does, and **refuses with a 409 if it finds one** — a single `Image`/`Video` whose `file_path` is under the old prefix is the whole predicate. The destination is not consulted at all. Unregistered folders still move anywhere, which is the file browser's actual job.

  The 409 is unconditional because the app supports exactly one layout for registered media — the one the file branch enforces per row, directly in the dataset's `images/` or `videos/`. A folder move can only land its contents one level *deeper* than that (`new_path.exists()` refuses the move back onto the original), so there is no destination this branch could permit that the file branch would not refuse file by file.

  **Same-dataset was permitted until V-21**, together with a prefix rewrite that kept `file_path` — and a `poster_path`/`thumbnail_path` that travelled with the tree — consistent with the new location. The rows were correct and the app was still wrong: `rescan_dataset` and `_rescan_videos` glob the canonical folders non-recursively, so every moved row is reported missing forever while its file is fine, and `thumbnail_path_for`'s `parent.parent` then resolves into a `thumbnails/` beside the *new* parent, orphaning the real thumbnail at the next rename. Supporting the layout instead would mean a recursive rescan plus stored-rather-than-derived thumbnail paths at eleven sites, against CLAUDE.md's flat-storage invariant — so the endpoint refuses to create a layout the rest of the app cannot read, and the rewrite went with the permission it existed to serve.

  The two destinations that were *always* refused motivate the guard and are still tested: `POST /move {src: "{ds}/images", dst_dir: "/outside"}` returned 200 and left every row's `file_path` outside `settings.datasets_dir`, where `utils.safe_dataset_path` 403s each one's bytes — a blank gallery with nothing in the DB saying why — and a move into *another* dataset's folder left `dataset_id` stale. A tree spanning two datasets needed a set-equality check when the destination still mattered; it no longer does.

  A user who rearranges a dataset folder in their own file manager, or a database written before V-21, still arrives in the out-of-layout state — unsupported rather than blocked, and `/rename`'s guard A (`docs/dev/file-browser-rename-delete.md` § Directory branch) is tested against it via `_relocate_out_of_layout` in `backend/tests/test_filesystem_rename_http.py`.

  A second directory guard covers the folders that hold **only derived artifacts**. `{ds}/thumbnails` and `{ds}/videos/thumbnails` contain no `file_path` at all, so the guard above matches nothing, the rewrite below has nothing to rewrite, and every stored `thumbnail_path`/`poster_path` in them is stranded by a 200. The predicate is "a derived path under the old prefix while that row's `file_path` is **not**", which is exactly what separates it from an ordinary media folder: for `{ds}/videos` the poster is under the prefix but so is `file_path` (second conjunct False — this guard passes it; the row guard above has already refused it); for `{ds}/images` the thumbnails are in the sibling `{ds}/thumbnails/` (first conjunct False); for `{ds}/thumbnails` both hold, so 409; and `{ds}` itself has both under the prefix and falls through to the row guard above, which already refuses it. The damage it prevents is a silent full-dataset cache regeneration plus a folder of orphaned `.webp`, not permanently broken tiles — `serve_thumbnail` regenerates a missing thumbnail and `get_video_poster` backfills a missing poster, both mkdir'ing their parent — but a move that silently invalidates a whole derived cache should not answer 200.

  Both prefix tests are escaped LIKEs (`startswith(..., autoescape=True)`). `ColumnOperators.startswith` defaults to `autoescape=False`, and `_` is a single-character LIKE wildcard *and* the character `_name_to_slug` puts in every multi-word dataset folder (plus the `_{ds_id[:8]}` collision fallback), so unescaped, `{ds}/my_dataset/…` matched `{ds}/myxdataset/…`. Here an over-matched row is an over-**refusal** rather than a wrong rewrite: it can only widen what the guards above match, so the request 409s on a folder that should have been permitted. Annoying, and nothing moves. (Before V-21 the same over-match reached a prefix rewrite after `shutil.move`, which was the PM-013 shape; there is no rewrite left to reach.)

  **A permitted move rewrites nothing on the directory branch.** V-21 deleted the prefix rewrite that used to live here: by construction any folder holding a registered `file_path` was already refused above, so there is nothing left to rewrite — the rewrite went with the permission it existed to serve. The *file* branch rewrites `file_path` and `filename` and never touches a derived column. No `refresh_stats` on either branch: it recomputes counts and sizes only — never a path, never `dataset_id` — and the guard makes every permitted move a same-dataset one, so none of those numbers can change.

**No UI caller.** `filesystemApi.move` exists in `frontend/src/api/filesystem.ts` and nothing calls it — there is no move menu item, drag/drop or destination picker. The endpoint is API-only; the wrapper is scaffolding for a move UI that has not been built.

## DB sync

`_find_dataset_for_path(db, file_path)` checks if `file_path` is inside any dataset's `folder_path` and returns the dataset — a `LIKE` pre-filter over `Dataset.folder_path` (longest first) with `relative_to` as the authoritative check. Only `/move`'s **file** branch calls it — one call site in the whole router. The directory branch's two guards are pure escaped-prefix tests over `file_path`/`thumbnail_path`/`poster_path` and resolve no dataset at all. Delete still matches on the exact path and needs no dataset lookup; rename's **file** arms do too (both in `docs/dev/file-browser-rename-delete.md`), but its directory guard runs two `Dataset.folder_path` queries of its own (an exact-or-prefix match, then a parent match for the layout names) rather than going through `_find_dataset_for_path`, because it needs to tell "is this folder a dataset's" from "is this folder inside one".
