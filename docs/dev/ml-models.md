# ML model lifecycle

This file covers what every model shares on its way in: the `model_manager` singleton and how it loads, the ambient `HF_TOKEN` every hub loader relies on, the EXIF-consistent `open_rgb` rule for inference, caption target-resolution preprocessing, startup config validation, TorchDynamo, and the `backend/ml/device.py` abstraction.

Its siblings: `docs/dev/model-residency.md` covers what keeps a model resident and how its weights leave — eviction, the unload paths, leases and `_release_to_cpu` — and `docs/dev/model-registry.md` covers the model IDs themselves and each model's loader quirks. The subsystems that consume these models have their own files: `docs/dev/detection.md` (object detection), the Quality family that `docs/dev/quality.md` routes to (quality scorers and flags, duplicate detection, style similarity), and `docs/dev/image-processing-models.md` for the pipelines that rewrite pixels — upscaling, LUT grading and LaMa inpainting.

### ML model management

`ml/model_manager.py` is a singleton that tracks loaded models and their VRAM usage. Before loading a model it calls `_evict_lru(needed_mb)` to free space. Each model_id gets its own `asyncio.Lock`, which serializes **loading and unloading** of that id — not inference; what keeps a model resident while something is using it is a lease (`docs/dev/model-residency.md` § Leases). All inference runs in `loop.run_in_executor(None, _sync_fn)` to avoid blocking the event loop. Ollama models are not tracked — Ollama manages its own VRAM.

After a successful load, `_registry[model_id]["vram_mb"]` is updated with the measured GPU delta so eviction decisions reflect reality.

`HF_TOKEN` is written into `os.environ` by `backend/services/secrets_service.py::sync_env`, its only writer, so every loader that passes no `token=` picks it up: early in `main.py` from the `.env`/OS-env chain, again in the lifespan from the DB, and on every `PATCH /settings/secrets`. A token saved in Settings → API Keys therefore applies to the next download with no restart — `huggingface_hub` re-reads the variable on every call. See `docs/dev/settings.md` § API Keys tab for the precedence rules.

**EXIF-consistent opening (mandatory for inference)**: every ML inference path must open images through `ml/image_utils.py::open_rgb(path)` — `Image.open().convert("RGB")` + `ImageOps.exif_transpose`. This guarantees all predictors (captioners, quality scorers, SAM2/SAM3, NudeNet) see pixels in the same EXIF-transposed frame, so normalized point/box coordinates denormalize consistently and detection overlays align with the subject on rotated images. Never open with a bare `Image.open(...)` in an inference path; `preprocess_for_caption` itself calls `open_rgb`. Close the returned image right after handing pixels to the model (per the "Close PIL Images after preprocessing" invariant).

The rule is now **enforced**, not just stated: `backend/tests/test_ml_image_opens.py` walks the AST of every module in its `INFERENCE_MODULES` list and fails on an `Image.open`/`PILImage.open` call. That list covered four scorer files while eight more inference paths shipped, and now names all twelve — the four scorers, `nudenet_scorer`, both SAM predictors and all five captioners; a companion test fails when a new `*_scorer`/`*_captioner`/`*_predictor` module is in neither it nor the annotated `NOT_INFERENCE` set, so the next one cannot ship unenforced. It exists because the rule was silently false for seven sites until 2026-07-30 — all four in `aesthetic_scorer.py`, both in `dino_scorer.py`, and `nsfw_scorer.py` — while this paragraph asserted it held everywhere. Nothing had broken, and the reason is worth knowing before trusting a green quality run: this app's images are overwhelmingly generated (PNG/WebP from ComfyUI), which carry no orientation tag, so the bug needs a folder import of phone photos to surface. What it produced there was an *inconsistency*, not a uniform error — `technical_scorer.py` reads through `cv2.imread`, which applies EXIF orientation itself, so on a rotated image the technical scores and the aesthetic/NSFW/DINO scores described pixels in two different orientations within one quality run.

`open_rgb_bytes(image_bytes)` is the in-memory twin, for callers that never touch disk. The pair exists so `extract_clip_embedding_sync` (path) and `extract_clip_embedding_from_bytes_sync` (bytes) cannot drift: both feed the same style-similarity comparison, so transposing in only one makes a reference image uploaded as bytes compare against stored embeddings in a different orientation — a subtler failure than the original, since both sides still return a well-formed normalized vector. Fix or add to one form, do the same to the other.

Two inference-adjacent sites deliberately stay outside `open_rgb`: `ml/lut_processor.py` and `ml/upscaler.py` transpose inline because they are image-*processing* paths that write their result to disk, governed by the `image_service._open_safe` half of the invariant rather than this one.

**Target resolution preprocessing**: `CaptionJobRequest` accepts optional `target_width` / `target_height`. When set, `ml/image_utils.py::preprocess_for_caption()` center-crops each image to the target aspect ratio and resizes it to the exact target resolution before inference. This ensures captions describe the composition the model will actually see at training time. All captioners (Florence-2, PaliGemma-2, JoyCaption, Ollama) call this utility; Ollama's existing `max_px` scale-down runs afterward on the already-cropped image. Omitting both fields leaves behavior unchanged.

**Config validation** (`backend/config.py`): `@model_validator(mode="after")` enforces at startup: (1) `max_vram_mb < 1000` → `ValueError` (fail fast); (2) an `hf_token` absent from the `.env`/OS-env chain → debug-level warning, worded to note it may still be set in Settings → API Keys, since the validator runs before any DB read and cannot see one saved there; (3) unrecognised `.env` keys → WARNING log; `extra="ignore"` retained so OS env vars are never flagged. `config.py` still declares `watermark_threshold` for legacy `.env` compatibility but the quality router reads all six flag thresholds (blur, noise, uniformity, watermark, duplicate, NSFW) from the `threshold_settings` DB table instead.

**TorchDynamo is disabled** (`TORCHDYNAMO_DISABLE=1` set in `main.py`). Triton is unavailable on Windows and single-image inference gains nothing from `torch.compile`, so it is disabled for the entire process. Do not remove this without re-testing all ML inference paths on Windows.

### ML device abstraction

**ML device abstraction** (`backend/ml/device.py`): centralises all device-detection and device-aware utilities. Every module under `backend/ml/` that touches the GPU imports from here — ten of them, plus `routers/captioning.py` and `routers/detection.py`. Five direct `torch.cuda.*` calls survive on purpose and are the exceptions to look for: `torch.cuda.OutOfMemoryError` in an `except` clause in `florence_captioner.py` (twice), `paligemma_captioner.py` and `joycaption_captioner.py`, and `torch.cuda.is_available()` behind sam3's pin-memory probe. Routing those through `is_oom_error()` / a device-level availability check is the tidy-up; until then, "nothing else calls `torch.cuda.*`" is an aspiration rather than a fact. Detection priority: `cuda` (NVIDIA or ROCm, identical API) → `mps` (Apple Silicon) → `cpu`. Key helpers: `get_device()`, `empty_cache()`, `memory_allocated_bytes()`, `memory_reserved_mb()`, `autocast_ctx()`, `safe_dtype_for_device()`, `is_oom_error()`. **`torch` is imported inside each function, never at module scope** — this is the one module the router import chain reaches (`routers/captioning.py` → `model_manager.py` → here), so a module-level import makes `from backend.main import app` require torch, which took down collection of the entire backend suite in CI. Don't "tidy" the per-function imports back to the top; the docstring explains it.

**A lazy import moves the failure from import time to call time, and the callers' guards did not follow.** `memory_allocated_bytes()` and `memory_reserved_mb()` document `cpu → 0`, and every caller wraps the *import* — `try: from backend.ml.device import memory_reserved_mb as _vram_mb / except Exception: _vram_mb = lambda: 0` (both captioning loops, three sites in `routers/detection.py`) — but that guard catches nothing on a torch-free install, because importing the *function* succeeds and only the call raises `ModuleNotFoundError`. Both reporters therefore keep `import torch` **and** the `get_device()` call inside their own `try`, so the documented 0 covers "no accelerator" and "no torch" alike. It stayed invisible until `test_caption_empty_guard.py` became the first CI-runnable test to drive a caption job through its VRAM sampling; the repo venv has torch, so only a torch-free venv reproduces it (`docs/dev/video/tests.md` § cv2 in CI describes the same class for cv2). `get_device()` itself still raises on purpose — a caller that genuinely needs a device cannot be handed a fallback.
