# Captioning post-processing & LLM providers

This file covers the captioning model picker, caption job post-processing (merging, refusal stripping, rename-on-caption), job queuing/execution, and OpenAI-compatible provider configuration.

### The captioning model picker

**The registry owns what a model is.** Each entry of `model_manager.list_models()` carries a `kind` (`"caption"` / `"score"` / `"detect"` / `"embed"`) and a `description` that the pickers render verbatim. Both live beside the loader that knows the repo id and the VRAM figure, because the alternative — model copy authored in the frontend — is what drifted: a two-way ternary in `CaptioningPage` gave Florence-2 one blurb and *everything else* PaliGemma-2's `"Google · requires HF token"`, so JoyCaption (`fancyfeast/llama-joycaption-*-hf-llava`, ungated) claimed to be Google's and to need a token. Only PaliGemma-2's description mentions gating, deliberately: every other loader merely passes the ambient `HF_TOKEN` along (`docs/dev/ml-models.md`) and needs no token, so "ungated" on the rest would be noise. `wd14_tagger.py::_VARIANTS` carries a `description` too, but no `kind` — those arrive in their own `wd14_models` array, every one is a captioner by construction, and the field would have no reader.

`kind` is singular, the model's *primary* role: `florence2_large` is `"caption"` even though detection also drives it, because detection's model list is frontend constants (`constants/detectionModels.ts`) that read nothing from here. A multi-valued capability set would be a field with no second reader.

**Two mechanisms, both required.** `GET /captioning/models` filters `local_models` to `kind == "caption"`, on the registry's own field rather than an id allowlist in the router — an allowlist would be a second list of model ids to drift from the registry, which is the failure this exists to kill. The filter alone is not the fix, though. Selecting a non-captioner was a **silent no-op**: both per-image loops are `if/elif` chains on id prefixes over a `caption = ""` starting value, so an id matching no branch fell through, failed the `if caption:` save, and finished the job green claiming every image processed and zero failures. A stale `CAPTION_DEFAULT_MODEL_KEY`, a saved workflow blob or a direct API call all still reach the endpoint, so `_caption_backend(model) -> str | None` is now the dispatch chains' single source of truth, enforced by a `@field_validator("model")` on `CaptionJobRequest` **and** on `PipelineStep` (on the step, not the request, so every step is covered for free). An unrecognised id is a 422 with no `BackgroundJob` row. The `else: raise RuntimeError` in each loop is unreachable behind that validator; it is there so a *future* prefix mistake becomes a per-image failure with a traceback instead of a green empty job. `backend/tests/test_captioning_model_registry.py` partitions the registry into `CAPTIONERS`/`NOT_CAPTIONERS` and checks both directions, so a thirteenth model fails CI rather than appearing in the picker.

**Four surfaces read the one query.** `CaptioningPage` and `SelectionToolbar`'s Caption modal render the description as a line under the name; `ImageDetailPage` takes it as `title=` instead — that sidebar is already `text-xs` and scrolls, so a second line per model is a regression for one-off recaptioning. `SettingsPage`'s Default-model `<select>` shows names only, and *blanks* on a saved default the endpoint no longer offers — derived during render, so no `setState` in an effect, and deliberately with no `localStorage.removeItem` behind it. The offered list is empty for a whole group whenever that service is merely unavailable (the backend swallows a dead Ollama daemon and returns `[]`) or its query has yet to resolve (`providers` is a separate query defaulting to `[]`), so a delete would destroy a good `ollama:llava` or `openai_compat:{id}` preference, permanently and with no toast, on a transient outage. A blank `<select>` recovers on the next render; the delete does not.

**Two predicates over a model id, deliberately not the same one.** `captionBackend` in `frontend/src/constants/captionModels.ts` hand-mirrors `_caption_backend` — the same six prefixes in the same order — and answers *will the validator 422 this*. The Run / Start Captioning / Generate Caption buttons on `CaptioningPage`, `SelectionToolbar` and `ImageDetailPage` are disabled on it, naming the offending step: a pipeline is one request, so a stale step 3 stops step 1 from running and the error names no step. Membership in the offered list (`captionModelOptions`, lifted into that same file from `SettingsPage`) is the *other* predicate and never blocks — it produces an informational note only, for the reason above. Reusing `modelType` (`constants/captionStyles.ts`) for either is the trap: it returns null for the perfectly runnable `wd14:` and `openai_compat:`, which have no `STYLE_LABELS` vocabulary, so gating on it disables the two most-used backends. `test_captioning_model_registry.py` parses `captionBackend` out of the TypeScript and evaluates it against the real function over every registry id, every wd14 id and the runtime-constructed forms; `frontend/e2e/captioning-run-gate.spec.ts` covers the gate itself, its wd14 negative control being the regression test for that trap.

The three pickers are deliberately **not** one component. They share *shape*, not markup: `.mr-desc` exists only in `CaptioningPage` and `QualityPage`, while the other two are hand-rolled Tailwind at different densities (`p-2.5 text-sm` vs `p-2 text-xs`). A shared component would need ~8 props plus two style variants and would drag two surfaces onto a third's visual language. The drift being fixed was in the data, and the data is now shared — one query key feeds all four.

### Captioning post-processing

`CaptionJobRequest` (in `backend/routers/captioning.py`) accepts the following fields for post-processing, merging, and job display:

| Field | Default | Effect |
|---|---|---|
| `label` | `null` | Optional display name shown in the job queue. When omitted, the router auto-generates `"{model_short} — N images"`. |
| `delimiter_mode` | `"overwrite"` | How to merge new caption with existing: `"overwrite"` replaces, `"append"` adds new text after (`existing + delimiter + new`), `"prepend"` adds new text before (`new + delimiter + existing`). Merge only runs when an existing caption is non-empty; images with no prior caption always receive just the new caption regardless of mode. |
| `delimiter` | `", "` | Text inserted between the two strings when `delimiter_mode` is `"append"` or `"prepend"`. |
| `strip_refusals` | `true` | Remove common AI refusal phrases from generated captions via `_REFUSAL_RE` compiled regex. The regex is narrowly scoped: `"This image appears to be X"` (Florence-2 PromptGen v2 standard output) is NOT stripped; only actual refusal phrasing like `"be depicting"` is matched. |
| `strip_thinking` | `false` | Strips `<think>…</think>` / `<thinking>…</thinking>` blocks and a first-line thinking preamble ("Let me think/analyze…", "I'll describe…", "Alright, let's…"). Thinking is **detected regardless** of this flag — a match always writes `has_ai_artifacts` to `quality_flags`. |
| `strip_underscores` | `false` | `word_word` → `word word` (`(?<=\w)_(?=\w)`). Prose styles: applied to the whole text. Tag styles (`_TAG_STYLES`): applied per-tag before rejoining with `, `. |
| `strip_hedges` | `false` | Strips sentence-level hedging prefixes ("It appears that…", "Possibly,…", "Looking at this image,…"), re-capitalising the remainder. Hedges are **detected regardless** — a match always sets `has_ai_artifacts`. |
| `dedupe_tags` | `false` | Tag styles only. Drops any freshly generated tag that is a whole-word subsequence of a longer tag in the same list (`tail` when `long tail` present; `shirt` when `white shirt` present) and collapses case-insensitive exact duplicates, via `subsume_tags()` in `backend/utils.py`. Applied to `new_tags` **before** the append-merge, so existing/prev tags merged in afterwards are untouched (mirrors `strip_underscores`). No-op for prose styles. (`PipelineStep.dedupe_tags` defaults `false`.) |
| `min_aesthetic_score` | `null` | Pre-filter applied in the initial DB query: only caption images with `aesthetic_score ≥` this value. `null` = no filter. |
| `exclude_flags` | `null` | Pre-filter: skip images with any of the listed quality flags set truthy; validated against `ALLOWED_FLAG_KEYS` via a `field_validator`. |
| `append_tags` | `true` | Tag styles only. When `delimiter_mode != "overwrite"`, new tags are deduplicated against the existing comma-separated `caption_text` (new tags win; remaining existing tags are appended). `false` = no merge. (`PipelineStep.append_tags` defaults `false` and merges against `prev_captions`.) |
| `save_backup` | `false` | Before calling `set_caption`, write the existing `.txt` sidecar to `.txt.bak`. |
| `rename_on_caption` | `false` | After saving each caption, rename the image file to `{subfolder_slug}_{NNN}.ext` (or `image_{NNN}.ext` for root). Sets `is_auto_named=True`. Subfolder and original filename are fetched from the initial bulk query — no per-image DB round-trip. |
| `wd14_threshold` | `0.35` | Minimum confidence (0–1) for a WD14 tag to be included in output. Only used when `model` starts with `wd14:`. |

`PipelineStep` has its own `delimiter_mode`, `delimiter`, `strip_refusals`, `strip_thinking`, `strip_underscores`, `strip_hedges`, `target_width`, `target_height`, and `wd14_threshold` fields — all configurable per step in the UI. `save_backup` and `rename_on_caption` live on `CaptionPipelineRequest` (pipeline-wide, not per-step). `prev_captions` is fetched from the DB at the start of each pipeline step when `delimiter_mode != "overwrite"` so the merge has the current caption text. When `delimiter_mode == "overwrite"` and `body.overwrite` is `False`, only images with empty captions are queued; append/prepend modes always process all images (the merge requires the existing caption).

**Captioning job execution**: `_run` in `routers/captioning.py` processes images one at a time (generate → save → emit SSE).

- **Progress and failures**: each event carries `image_id`, `throughput_ips`, and `vram_used_mb` (sampled every 10 images; Ollama always 0; WD14 and OpenAI-compat always 0). Failed images accumulate in `failed_image_ids`; a `caption_summary` SSE event is emitted after the loop if any failed. Both loops catch `openai.APITimeoutError` in a branch **ahead** of the broad `except Exception`, logging the provider's name and its configured `timeout_s` instead of a bare traceback — the image still fails, only the diagnosis changes, and a provider that hung up mid-generation is what a bare traceback made read as "nothing happened". The import is guarded with a no-op subclass fallback, since `openai` ships in `requirements.txt` but not in `requirements-ci.txt`. The client is built with an explicit `max_retries=0` — the SDK's default is 2 and it retries timeouts, which made one image cost up to 3 × `timeout_s` and the configured number a lie. Cancellation is checked at each image boundary via `job_queue.raise_if_cancelled(job_id)` (an in-memory set check, used in both `_run` and `_run_pipeline_job`); see `docs/dev/backend-infrastructure.md` § Job cancellation. Because that poll is the only one, **Stop waits out the request in flight** — bounded by one `timeout_s` now that retries are off.
- **A partial failure is durable, not just an SSE event.** A run that loses images still *returns*, so `job_queue.py` marks the row `completed` with `error_msg` unset and the Logs page would show it green — `logger.error` reaches uvicorn's stdout and nothing else. Both tails therefore write `BackgroundJob.result_data` (only when something failed; a clean job's row stays `{}`) in the same `AsyncSessionLocal()` block that calls `refresh_stats`, **before** that call and with its own explicit `commit()` — `refresh_stats` committing internally is an implementation detail of `dataset_service`. The shape follows the import-summary convention: `{failed_count, timed_out, failure_summary, failed: [{file, error}]}`, capped at `_MAX_FAILED_DETAILS = 50` entries (a restated twin of the constant in `dataset_service.py`, not an import of a private name). `failure_summary` comes from `_failure_headline(timed_out, provider)` and is `None` unless something timed out — a timeout is the only failure with a diagnosis specific enough to beat the badge's generic wording. The same string rides the `caption_summary` SSE event as a new `failure_summary` field. **Known gap**: a *cancelled* run reaches neither tail (`raise_if_cancelled` propagates out), so it writes no `result_data` and emits no summary — already true of the SSE event before this. Surviving cancellation needs a `try/finally` around each loop.
- **`has_ai_artifacts` is written** to `quality_flags` whenever `_has_thinking()` or `_has_hedges()` matches the generated caption, **regardless** of whether `strip_thinking` / `strip_hedges` are enabled (stripping is independent of detection); `strip_refusals` does **not** set this flag. The flag flows through `set_caption(..., has_ai_artifacts=)`.
- **Flag lifecycle**: because `has_ai_artifacts` describes cruft *in the caption text*, emptying the caption must clear it — an empty caption can't contain artifacts. This is enforced by `_maybe_clear_ai_artifact(img, caption_text)` in `caption_service.py`, which sets the flag to `False` (matching the quality-router convention of setting flags false rather than deleting the key) only when it is currently set and the new caption is empty/whitespace, copying the JSON dict before mutating (per the never-mutate-in-place invariant). **Call it in every caption-write path that can produce an empty caption** — it already runs in `set_caption` (manual editor + captioning save) and in the bulk paths (`bulk_edit_captions`, `find_replace_captions`); see `docs/dev/bulk-ops.md` § Bulk caption editing.
- **Tag-producing styles** (WD14, booru-style outputs, and the four JoyCaption tag styles) produce comma-separated text stored directly in `caption_text` — there is no longer a separate tags table. The `_TAG_STYLES` frozenset in `routers/captioning.py` identifies them; see `docs/dev/ml-models.md` § ML model management for the definition and JoyCaption tag-style details.

**Job queuing**: The backend `asyncio.Queue` in `workers/job_queue.py` runs caption and pipeline jobs serially — any number of jobs may be submitted while one is running. `enqueue()` emits a `"pending"` SSE event immediately after putting the job on the queue (before the worker picks it up), so the frontend knows the job exists right away. The worker checks the DB status after dequeuing; if a job was cancelled while pending it emits a `"cancelled"` SSE event and skips without running. The cancel endpoint (`DELETE /jobs/{id}`) accepts both `"running"` and `"pending"` status, and also calls `job_queue.request_cancel(job_id)` so a *running* caption/pipeline job stops cooperatively at the next image boundary (see `docs/dev/backend-infrastructure.md` § Job cancellation).

**Which job the CaptioningPage panel shows**: the frontend tracks all submitted job IDs in `submittedJobIds: string[]`; `submittedActiveJobId` is the oldest non-terminal entry (gated only by `seenTerminalJobIds` ref, not live store status, to avoid the effectiveJobId race where the gallery invalidation never fires) — and **falls back to the most recently submitted id when every entry is terminal**, which is what keeps the panel bound long enough to render its own Done state. Without that fallback `effectiveJobId` went null on the first re-render after completion (the terminal effect mutates a ref, so the drop landed on whatever render its `invalidateQueries` triggered), the panel unmounted back to "Run captioning to see progress here", and both the "✓ Captioning complete" line and the amber failed-images badge were unreachable — confirmed with a `MutationObserver` over the whole run, not just by polling. Starting another job puts a non-terminal id back at the front of the `find`, and `submittedJobIds` resets on remount, so nothing stale is resurrected. `otherPendingJobs` (the queue list displayed in the CaptioningPage live-progress panel) is derived from `allActiveJobs` (the persistent Zustand store), not from `submittedJobIds`, so the list survives navigation/remount. `globalCaptionJob` (the fallback when `submittedActiveJobId` is null) also includes `"pending"` status for the same reason. Cancelling a pending job in either `CaptioningPage` or `TopBar` calls `useJobStore.getState().updateJob(id, { status: "cancelled" })` optimistically before the API call so the job disappears from the queue list immediately without waiting for an SSE event.

**Ollama timeout**: `httpx.AsyncClient` in `ollama_captioner.py` uses a 300-second timeout per image to accommodate slow hardware and cold model loads.

**Sidecar writes never run on the event loop.** `_write_txt_sidecar` (`caption_service.py`) is blocking file I/O, and a bulk edit or import calls it once per image — inline, that stalls the whole server for the length of the batch. Two shapes, picked by how tight the surrounding loop is:

- **Tight loops batch.** `bulk_edit_captions` and `find_replace_captions` accumulate `(file_path, text)` pairs while assigning captions, then make **one** `run_in_executor` call to `_write_sidecars_async(pairs)` **before** `db.commit()` — one hop per batch, since a hop per tiny file costs more than the write. Keeping it before the commit preserves the fail-before-commit ordering the inline writes had. Use this helper for any new batch caption path.
- **Already-slow loops hop per file.** The captioning loop (`routers/captioning.py::_backup_sidecar`, for `save_backup`) and the standalone caption import (`dataset_service.py::_copy_caption_file_sync`) are GPU- or disk-dominated per item, so a per-image executor hop is free. Folder import writes the sidecar *inside* `_ingest_file_sync`, which already runs in an executor — zero extra hops. Export's `_write_sidecar` is wrapped to match its `_write_image`/`_write_mask` siblings.

The ORM caption assignment always stays on the event loop: `Image.caption_text` must be set by attribute assignment or `caption_token_count` goes stale (`docs/dev/shared-utilities.md`). Sync helpers therefore return the text rather than touching the session.

### OpenAI-compatible providers

**Router**: `backend/routers/providers.py`, prefix `/providers`. Registered in `main.py`. No service layer — CRUD is thin enough to live in the router.

| Endpoint | Behaviour |
|---|---|
| `GET /` | List all providers ordered by `created_at` |
| `POST /` | Create provider; 409 on duplicate name. Builds the row as `OpenAIProvider(**body.model_dump())` — the old explicit field list silently dropped `max_tokens`, and would have dropped `timeout_s` too |
| `PATCH /{id}` | Update any fields; `exclude_none=True` so omitted fields are not cleared |
| `DELETE /{id}` | Hard delete |
| `GET /{id}/models` | Calls provider's `/v1/models` endpoint via `openai.OpenAI` with a 5-second timeout and `max_retries=0` (without it the never-raises probe spends 15 s); returns `{"models": []}` on any error (provider offline, auth failure) — never raises |

**Model**: `backend/models/openai_provider.py` — `OpenAIProvider` table. Fields: `id` (UUID), `name` (unique), `base_url`, `api_key` (stored plaintext), `default_model`, `max_image_px` (`ge=128`, `le=2**31 - 1` — default 1024; image is JPEG-encoded at this resolution before sending, and the ceiling is the SQLite integer bind's rather than a resolution limit, since `_encode_image` only downscales), `max_tokens` (`ge=1`, `le=2**31 - 1` — default 2048; the ceiling is the SQLite integer bind's, not a model limit, and exists so an absurd value is a 422 rather than an `OverflowError` out of the commit), `timeout_s` (10–3600 s, default 300), `created_at`.

**Schema**: `OpenAIProviderOut.from_orm_row` is the remaining hand-maintained field list (the create path was fixed by the `**model_dump()` splat above) — a column added to the model and the schema but forgotten there fails *silently*, leaving the field at its default. `OpenAIProviderOut` masks the API key (last 4 chars visible) and adds a computed `is_remote: bool` — true when the base URL hostname is not `localhost`/`127.0.0.1`/`::1`. Remote providers show a warning banner in the CaptioningPage and Settings form.

**Captioner**: `ml/openai_compat_captioner.py` — `caption_image(image_path, base_url, api_key, model_name, style, custom_prompt, max_px, max_tokens, target_w, target_h, timeout_s)`. Encodes the image as JPEG base64 (after `preprocess_for_caption` and optional `max_px` downscale), sends via the v1 SDK (`OpenAI(base_url=…).chat.completions.create`) with an `image_url` content block. The per-image timeout is the provider's `timeout_s`; `_caption_sync` takes it as its **last** positional parameter, and the `run_in_executor` call is positional, so both signatures append new parameters at the end. Not tracked by `model_manager`.

**Model ID format** in captioning: `openai_compat:{provider_id}:{model_name}`. The router splits on `:` with `maxsplit=2` to recover `provider_id` and `model_name`. If `model_name` is empty, `openai_provider.default_model` is used.

**Settings UI**: Settings page → "LLM Providers" tab. Add/edit/delete providers. `Max tokens` and `Timeout` are `NumberField`s, not sliders: a `type="range"` cannot express "no upper bound", and its `max={16384}` *was* the ceiling users hit. Each field's bounds live in the `clamp` callback it passes — including `max_tokens`' `2 ** 31 - 1`, which mirrors the schema's `le` rather than adding a `max` attribute. The "Default model" field uses `ModelPicker` (preset dropdown for well-known cloud APIs; fetch button for local servers). Provider mutations also invalidate `["captioning-models"]` so CaptioningPage model list updates immediately.

**`ModelPicker` component** (`frontend/src/components/providers/ModelPicker.tsx`): Props `{ value, onChange, providerId?, baseUrl?, placeholder? }`. On mount with `providerId`, auto-fetches models via `providersApi.fetchModels(providerId)`. Computes `presets = getPresetsForUrl(baseUrl)` from `providerPresets.ts`. When both are empty: plain text input. When either has entries: `<select>` with a "Custom…" sentinel + optional text input below for custom entry. When `value` is not in the list, the select shows "Custom…" and the text input is pre-filled. Explicitly selecting "Custom…" sets local `showCustom: bool` state so the text input appears even when the current value is a known model; selecting any list item resets it. A `useEffect` on `[value, allModels]` also resets `showCustom` whenever `value` becomes a known model (e.g. parent switches providers and passes a new default), preventing the select from staying stuck on "Custom…" after an external value change. A refresh button (↻) allows manual re-fetch. `fetchError` shows a muted "Could not reach provider" message on empty result.
