# Dataset operations

This file covers the actions on a dataset as a whole, as `DatasetsPage` and the gallery toolbar expose them: importing a folder into a dataset (`ImportFolderModal`, the shared `DirPickerModal`), rescan and caption import, how job outcomes are surfaced, dataset folder naming, edit, rename and duplicate (including carrying the videos). The page those buttons sit on, its layout, categories and persisted UI are in `docs/dev/datasets-page.md`; the backend import and rescan passes are in `docs/dev/image-import.md`, and the video half of ingest is in `docs/dev/video/storage.md` and the video routes in `docs/dev/video.md`. The user doc is `docs/datasets.md`.

## Import and rescan

**Import job tracking is not this page's** (GPT-030). `ImportFolderModal` adopts the job it submits (`utils/jobReconcile.ts::adoptJob`) and closes. `TopBar`'s import branch then refreshes the dataset's caches, `["licenses-in-use", id]` included, and toasts the outcome, success, failure or cancel, wherever the user has gone by then. `DatasetsPage` used to keep its own `importJobId` watcher, which handled only `completed` and dropped a failure silently. It was deleted with GalleryPage's, so nothing toasts twice. See `docs/dev/frontend-jobs.md` § Job completion → cache invalidation.

**Import modal** is the shared `ImportFolderModal` component (`frontend/src/components/common/ImportFolderModal.tsx`), used by both `DatasetsPage` (card + header "Import folder" buttons) and the `GalleryPage` toolbar ("Import folder" button). It takes `datasets: Dataset[]` (candidate targets), an optional `initialDatasetId`, and `onClose`; the `onStarted(jobId)` callback is gone, since no page tracks the job any more. On success it adopts the job, toasts "Import submitted" and closes, and a rejected submit shows the server's `detail` through `apiErrorDetail`. When more than one dataset is passed it renders a **target-dataset selector** (dropdown); with a single candidate it shows the fixed target name. The `DatasetsPage` header button passes the full list with no preselection (previously it hardcoded `datasets[0]`, giving no way to choose the target — fixed); card buttons and the gallery preselect via `initialDatasetId`. The folder path has a **"Browse…"** button that opens the shared in-app `DirPickerModal` (see below) instead of a native OS dialog; the manual path text input always remains available as an alternative.

The form's options — `subfolder` (target logical subfolder, empty = root), `preserve_structure: bool` (recursively walk the source and map each subdirectory to a logical subfolder; when false everything lands in `subfolder`), `import_captions: bool` (default true — read `.txt` sidecars next to source images), `include_videos: bool` (default **false**; when ticked the modal surfaces the consequence inline — videos are imported as sources rather than gallery images and always land flat, so `subfolder` and `preserve_structure` apply to images only — see `docs/dev/video/storage.md` § Ingest), and the four source/license fields from the shared `ProvenanceFields` component (`source_name`, `source_url`, `license`, `attribution`) — are passed in the `POST /datasets/{id}/import` body as `DatasetImportWithOptions`. The **Target subfolder** field has its own *Browse…* popover — a second, different Browse from the `DirPickerModal` one below — listing the target dataset's existing logical subfolders from `GET /datasets/{id}/subfolders` (keyed on the target id) plus a `(root)` entry. It is disabled while `preserve_structure` is on, since that mode derives every subfolder from the source tree. Folder import is the **only** ingest path with a request-supplied provenance layer; it takes precedence over the scraper sidecar and EXIF (see `docs/dev/provenance.md`). The page that owns the modal tracks nothing: the job's outcome is `TopBar`'s, as above.

**`DirPickerModal`** (`frontend/src/components/common/DirPickerModal.tsx`) is the shared in-app folder browser behind every "Browse…" button (import modal, caption import, and the Export page output folder). It browses the **server's** filesystem via `GET /filesystem/roots` (drive roots / `datasets_dir`) and `GET /filesystem/list` (subdirectories only) — the same endpoints as `FileBrowserPage` (`docs/dev/file-browser.md`) — so it works identically on every OS with no native-dialog / window-focus issues. Props: `initialPath`, optional `title` and `confirmLabel` (default `"Select output folder"` / `"Select folder"`), `onConfirm(path)`, `onCancel`. It offers breadcrumb navigation, a drive-root switcher, "New folder" (`POST /filesystem/mkdir`), and a free-text path field, and returns an absolute path. **Nesting caveat:** it renders its own full-screen fixed overlay, so when it is opened from inside another modal, render it as a **sibling of** (not a child of) any backdrop that has an `onClick`-to-close handler — otherwise clicks inside the picker bubble up and close the parent. `ImportFolderModal` does this by wrapping its return in a fragment and placing `DirPickerModal` outside the `onClose` backdrop.

**Rescan & caption import**: each dataset card also has a "Rescan folder from disk" button (`POST /datasets/{id}/rescan`) and an "Import captions" button → modal with a folder-path input (with a "Browse…" button using the same `DirPickerModal`) (`POST /datasets/{id}/import-captions`). The gallery toolbar carries its own "Import folder" + "Rescan" buttons so both are reachable while viewing a dataset's images (see `docs/dev/gallery.md`). Both run as background jobs tracked in `jobStore`; on completion `DatasetsPage` invalidates the dataset caches (via a shared `invalidateDatasetCaches` helper, whose keys include `["videos", datasetId]` — both callers can add `Video` rows, and the card's counts come off `["dataset", id]`) and fetches the job's `result_data` through `jobsApi.get(jobId)` to show a summary toast (rescan: `added` / `captions_updated` / `renamed` / `videos_added`, plus a `missing` count that sums `missing` and `videos_missing` because one number is what the user acts on; caption import: `matched` / `unmatched`). The `renamed` clause is not cosmetic — rescan otherwise never touches a file, so a collision rename has to be *reported* rather than inferred, and `GalleryPage`'s rescan toast is kept in step with this one for the same reason. See `docs/dev/image-import.md` § Folder rescan / sync for the backend services and § Dropping a caption file onto an image for the drag-`.txt`-onto-image feature.

**Every terminal status clears the job.** The rescan, caption-import and duplicate effects each have a `cancelled` arm as well as `failed`, skipped on a cancel button's optimistic write. A cancelled rescan or caption import refreshes the dataset, since both keep the work done before the stop, and all three toast the cancel and clear their job id. Before, a cancelled job was never cleared at all.
(`DatasetsPage` hosts these effects; the page itself is `docs/dev/datasets-page.md`.)

## Dataset operations

**Dataset folder naming**: `create_dataset()` in `dataset_service.py` derives the folder name from the dataset name via `_name_to_slug()` (lowercase, spaces → underscores, special chars stripped, max 80 chars) rather than using the UUID. The UUID is still the DB primary key. If the slug folder already exists (name collision edge case), a `{slug}_{uuid8}` suffix is appended. Example: dataset named `"My Portraits"` creates `data/datasets/my_portraits/`.

**Dataset edit**: the pencil (Edit) button on each dataset card opens a modal for editing the name, description, category, and the dataset's four source/license defaults (rendered by the shared `ProvenanceFields` component — see `docs/dev/provenance-api.md`). `PATCH /datasets/{id}` accepts `{ name?, description?, category?, source_name?, source_url?, license?, attribution? }`; on the provenance fields `None` (omitted) leaves the value alone and `""` clears it — there is no inherit sentinel at the dataset level, because those columns are NOT NULL and `""` already means "unset". Returns 400 on name conflict. The Save button is enabled when any field differs from the current values. The **create** modal carries the same four fields (seeded from `EMPTY_PROVENANCE`) minus `customLicenses`, there being no dataset yet whose in-use licenses could be offered; `DatasetCreate` extends `ProvenanceDefaults`, so `POST /datasets/` accepts all four.

**Dataset rename**: when the name changes, `rename_dataset()` renames the folder on disk and rebases every stored path that pointed into it — `Image.file_path`/`thumbnail_path` **and** `Video.file_path`/`poster_path`, all four through one `_rebase` closure — then updates `Dataset.folder_path`/`name`, all in one transaction. `.versions` needs nothing: `version_service._object_store_path` derives the object store from `folder_path` at read time, so the store travels with the column. Both row sets are loaded **before** the `old_folder.rename(...)` (PM-013) — the `SELECT` is the fallible half and the rename is irreversible, so querying afterwards meant a failed query left the folder moved with nothing committed to describe it. The video half was missing until B5, and it failed **silently**: `_rescan_videos` keys `by_filename` on the row's `filename` and the files in the new folder carry those same names, so every row hit `continue`, `videos_missing` came back empty, and `GET /videos/{id}/file` 404'd on a row no report ever named. `backend/tests/test_dataset_rename_folder_http.py` pins all of it. Renaming the folder from the **File Browser** instead is refused outright — see `docs/dev/file-browser-rename-delete.md` § `POST /rename` (its Directory branch), whose guard C points users back at this endpoint.

**Dataset duplicate**: the copy icon button on each card opens a Duplicate modal. `POST /datasets/{id}/duplicate` is a background job that returns `{job_id}` immediately; `DatasetsPage` watches the job in `jobStore` and invalidates `["datasets"]` on completion. The new dataset inherits the source's description, category, declared subfolders, and the four provenance defaults (`dataset_service.py::duplicate_dataset` — copying them is what lets the copied images keep raw `copy_provenance` values and still resolve to the same license); blob columns (`clip_embedding`, `dino_embedding`, `dino_layer_embeddings`) are not copied. When versioning is enabled and the source dataset has branches, the modal shows a branch + version dropdown; choosing a specific snapshot copies from the object store (using the snapshot's `file_hash` if present, otherwise the current file path). `datasetsApi.duplicate(id, newName, sourceVersionId?, includeVideos?)` in `frontend/src/api/datasets.ts`. Backend: `duplicate_dataset()` in `dataset_service.py`; `DatasetDuplicateRequest` schema (`new_name`, `source_version_id?`, `include_videos`) in `backend/schemas/dataset.py`.

### Duplicate: carrying the videos

`include_videos` defaults to **false**, matching `DatasetImportWithOptions.include_videos` — the footage dwarfs the images beside it, so doubling it is a visible, costed choice rather than something a duplicate does quietly. The modal renders the checkbox only when `duplicateTarget.video_count > 0` and labels it with the real cost read off the columns the card already shows (`Copy 3 videos (1.4 GB)`, via the page's local `formatSize`). With a snapshot selected the box is **disabled with the inline reason "Snapshots don't capture videos"**, and the mutation sends `false` regardless of the state behind it, so the UI can never provoke the router's 400 — that 400 is the backstop for a direct API call, and it exists because a version snapshots images only, so live videos would pair a historical image set with present-day sources.

The endpoint also carries duplicate's **first disk preflight**: `require_free_space(settings.datasets_dir, needed)` → **507** in the request path, before a dataset row or a job id exists. `needed` is `Dataset.total_size_bytes` (+ `video_size_bytes` when the toggle is on) for a current-state duplicate, or one `SUM(VersionImageState.file_size_bytes)` over the present rows for a snapshot — both cheap, since `refresh_stats` already maintains the dataset columns.

Copying is skip-and-report per video, like the image loop: a failure logs and continues, and the job's `result_data` (`{dataset_id, images_added, videos_added, videos_failed}`) drives the completion toast, whose video clauses drop out at zero so an image-only duplicate reads exactly as it did before the toggle existed. Videos land flat in the clone's `videos/` with their posters in `videos/thumbnails/`, both created lazily so an image-only clone never grows an empty `videos/`; names are copied verbatim with **no uniquifier**, because the destination folders are fresh and the source's names are already mutually unique. A copied frame's `Image.source_video_id` is **remapped** through an old→new id map onto the clone's own video — never copied raw — and falls back to NULL on a map miss. See `docs/dev/video.md` and the frame-lineage rule in `CLAUDE.md`.

That remap makes the video loop's closing `await db.flush()` load-bearing, and it is the one thing here the ordinary test suite cannot see. `Image.source_video_id` is a real FK to `videos.id`, so the copied `Video` rows must be **in the database** — not merely in the session — before the first copied `Image` naming one is inserted; without the flush the job dies whole with `IntegrityError: FOREIGN KEY constraint failed`. The suite runs with SQLite's `foreign_keys` pragma OFF (it builds its schema with `create_all` on its own engine and so never gets the `PRAGMA foreign_keys=ON` that `backend/database.py` installs on the app engine — the same blind spot as the delete cascade), so this passed every test and only surfaced on a real run. `backend/tests/test_duplicate_video_fk_enforced.py` pins it, via a `foreign_keys=True` opt-in on `conftest.api_env` that turns the pragma back on for that module alone.
