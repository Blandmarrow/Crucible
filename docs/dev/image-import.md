# Image import: folder import, rescan & caption import

This file covers the three paths that bring images and captions in from a folder on disk — folder import, rescan/sync and standalone caption import — how import and rescan work on several files at once and decode each one once, plus dropping a `.txt` onto an image to set its caption, and the rule the rescans share with every creation path: a stem-keyed derived artifact needs a collision guard at every writer. How a new file's name is picked (`unique_filename_with_thumb`), the `rename_with_sidecar` contract and cross-dataset moves are in `docs/dev/image-files.md`; `ImportFolderModal` and the `DirPickerModal` Browse button are in `docs/dev/dataset-operations.md`; the video half of import and rescan is `docs/dev/video/storage.md` § Ingest.

## Caption sidecars

Captions are persisted *out* to `{stem}.txt` sidecars (`caption_service._write_txt_sidecar`) and read *in* via `utils.read_caption_sidecar(image_path) -> str | None`. **An empty caption has no sidecar**: given blank text the writer deletes the `.txt` instead of writing an empty file, so every caller — a single-image blank, a bulk `clear`, a `remove` or `find_replace` that empties a caption, tag consolidation, caption import — follows one rule, the one restore's `version_service._sync_caption_sidecar` already kept. The reader returns `None` for a missing file and an empty one alike, so a rescan cannot tell them apart and never brings a cleared caption back. Three import paths feed captions/images in from disk; all overwrite existing captions and stamp `captioned_by="import"` — folder import, rescan/sync and standalone caption import, each below.

## Folder import

`import_images_from_folder(..., import_captions=True)` reads a `{src_stem}.txt` next to each source image and applies it after the copy. Toggled by `DatasetImportWithOptions.import_captions` (default `True`); the Import modal in `DatasetsPage` exposes an "Import captions (.txt sidecars)" checkbox. Returns a summary dict `{added, videos_added, failed_count, failed}` (was a bare `int`) stored in `BackgroundJob.result_data`; the shared `utils/importToast.ts::showImportSummaryToast(jobId)`, called by the import-job completion handlers in both `DatasetsPage` and `GalleryPage`, reads it via `jobsApi.get` and shows `Imported N images and M videos` (the video clause is dropped at zero, so an image-only import reads as before) or, when `failed_count > 0`, a warning `Imported N images · M failed (see server log)`. `videos_added` is only ever non-zero when the import was started with `include_videos` (see `docs/dev/video/storage.md` § Ingest). Per-file failures are logged with `logger.warning(..., exc_info=True)` (no longer silently swallowed); `failed` retains at most the first 50 `{file, error}` details while `failed_count` is the full tally.

**Per-file I/O** (copy + PIL decode/phash + generation-metadata parse + thumbnail) runs off the event loop via a single `run_in_executor(_ingest_file_sync, ...)` hop so a large import doesn't stall other requests/SSE. Several of those hops run at once, and each decodes its file once: § Several files at once, one decode each. The directory walk and the source-size sum share **one** `run_in_executor(_scan_source_files, …)` hop before the loop: `is_file()` already stats every entry, so summing in the same pass is free, and neither an `rglob` over a deep tree nor N `stat()` calls belongs on the event loop. The total then goes through `utils.require_free_space(dataset.folder_path, …)` (the local `_file_size` treats a vanished file as 0) so a too-small disk fails the job with a readable `error_msg` instead of leaving a half-imported folder — the same helper the export loop uses, see `docs/dev/export.md` § The shared export loop (the **Disk-space preflight** note).

## Folder rescan / sync

`rescan_dataset(db, dataset, job_id, import_captions=True)` walks `{folder_path}/images` and reconciles **by `filename` alone** (unique per dataset via `uq_dataset_filename`), then runs a second pass, `_rescan_videos`, over `{folder_path}/videos` — a flat glob, skipping the `videos/thumbnails/` child (`docs/dev/video/storage.md` § Ingest). A dataset with no `images/` at all is handled. The image pass is **committed before** the video pass runs, so a failure in the second cannot roll back renames and thumbnails the first has already made permanent on disk. Endpoint `POST /datasets/{id}/rescan`; `job_type="rescan"`.

- **Never derive subfolder from the on-disk path.** Image files are always stored flat in `images/` — `subfolder` is a purely logical DB column, never reflected on disk — so deriving it would mis-key every subfoldered image, hit the unique constraint on commit, and fail the whole job.
- **Reconciliation**: files on disk absent from the DB are registered at root (`subfolder=""`, thumbnail via `thumbnail_path_for`, sidecar caption; the decode/metadata/thumbnail work runs in a `run_in_executor(_rescan_file_sync, ...)` hop, several at once, see § Several files at once, one decode each); existing rows pick up changed/added sidecars (compared against the stripped stored caption to avoid re-stamping provenance on whitespace-only diffs); DB rows whose file is gone are **reported (never removed)**.
- **Rescan is the one path that renames a file it did not create.** Thumbnails are `.webp` keyed by stem, so `a.png` and `a.jpg` hand-dropped into `images/` both resolve to `{dataset}/thumbnails/a.webp` and the second written clobbers the first, leaving two rows sharing one picture. Every other creation path avoids this by picking a free name through `unique_filename_with_thumb`; rescan adopts the name off disk, so it runs the adopted name through the same helper and renames the loser to `a_001.jpg` before registering it. **`disk_exclude={f.name}` is mandatory** — the file is already sitting in `images/`, so without it the uniquifier sees every file's own name occupied and steps all of them to `_001`. The `.txt` sidecar deliberately does **not** move with it (the sanctioned exception to the `rename_with_sidecar` rule): the two files share a stem, so one `a.txt` belongs to both equally, and the caption is read before the rename either way. Only flat `images/` files are disambiguated — a nested file is already mis-keyed by the filename-only reconcile above and `thumbnail_path_for` resolves it to the wrong directory, so guarding on `f.parent == images_dir` leaves that untouched rather than half-fixing it.
- **It renames the file, where video rescan renames the poster** (`docs/dev/video/storage.md` § Poster stems and collisions). The asymmetry is load-bearing: eleven sites re-derive an image's thumbnail path from its filename (they are enumerated in the code comment at `backend/services/dataset_service.py`'s rescan rename branch — rename, move, copy, crop, the extension change, rename-on-caption, `duplicate_dataset` and four versioning paths), so an image whose thumbnail stem drifted from its own would have that thumbnail orphaned by the next rename, move, copy, crop or restore. Nothing re-derives a poster path — every consumer reads `Video.poster_path`.
- **`occupied_thumb_stems` has two terms**, mirroring `claimed_poster_stems`' three (`docs/dev/video/storage.md` § Poster stems and collisions — read its reasoning; this is the same argument one term shorter). The `*.webp` in `{dataset}/thumbnails/` are what is actually on disk; the **registered rows' own `filename` stems** are the conservative reservation for a thumbnail that is not there yet. Without the second term, deleting `{dataset}/thumbnails/` from the File Browser — which leaves the `Image` rows alone, since their `file_path` is not under that prefix — lets a hand-dropped `a.jpg` take the exact path registered `a.png` regenerates into, and PM-007 recurs silently. A file's own stem is by construction absent from both: the uniquifier is only reached when the file has no row, and nothing has cut its thumbnail.
- **The collision rename must not overwrite `original_filename`.** `f = f.rename(...)` rebinds the loop variable, so the `Image(...)` below has to record a `original_name` captured *before* it. That column is the name the user gave the file, and `import_captions_from_folder` matches a later sidecar against its stem first — record `a_001.jpg` there and an `a.txt` arriving afterwards can never pair with the file that arrived as `a.jpg`.
- **Result**: nine keys — `{added, renamed, captions_updated, missing, total_on_disk, failed_count, failed}` plus `videos_added` and `videos_missing`. Only the two *failure* fields are folded (the video pass reports `videos_failed`/`videos_failed_count`, which `_fold_video_failures` merges into `failed`/`failed_count` rather than adding keys); the two count fields are genuinely its own, and both rescan toasts read them. Stored in `BackgroundJob.result_data` and surfaced as a toast. `renamed` is reported rather than silent because rescan otherwise never touches a file — both the `DatasetsPage` and `GalleryPage` toasts name it.
- **The endpoint dedupes**: if a pending/running rescan job for the same dataset already exists it returns that job's id instead of creating another — auto-rescan-on-open fires on every gallery mount (the "already rescanned" guard is a per-mount ref), so without this, duplicate rescans pile up behind any long-running job in the serial queue (two *simultaneous* requests can still race past the check; sequential ones cannot).
- **UI**: a per-card "Rescan folder from disk" button in `DatasetsPage`, a **"Rescan" button in the `GalleryPage` toolbar** (next to Upload), and an auto-rescan-on-open in `GalleryPage` gated by the `auto_rescan_on_open` setting (off by default — see `docs/dev/settings.md`). In `GalleryPage` the manual button and the auto-on-open path share one `runRescan(manual)` helper and one `rescan: {jobId, datasetId, manual} | null` state, and the job is adopted (`utils/jobReconcile.ts::adoptJob`) the moment it is submitted. The completion effect fires on **any** non-optimistic terminal status and always refreshes the *job's* dataset, not whichever one the pane shows by then. For a manual run it toasts through the id `gallery-rescan`: the `jobsApi.get`-fetched summary, "Rescan failed: `<message>`", or "Rescan cancelled". Auto rescans refresh silently. It always clears the state, which is what re-enables the button: only `completed` used to clear it, so a failed or cancelled rescan left the button disabled until a reload (GPT-030). The loading toast is dismissed if the page unmounts mid-run.

## Several files at once, one decode each

Folder import and rescan work on up to `_import_workers()` image files at once: half the cores, capped at `IMPORT_MAX_WORKERS = 8` (M10 T3). Both loops share `InOrderWindow` from `backend/utils.py`, the pattern T1 uses inline for the technical scorer (`docs/dev/quality/scoring-job.md`). It awaits the oldest file first, so the rows, the `failed` list and the progress `done` all come out in input order, as the one-at-a-time loops gave them. The window only holds futures. Each loop creates its own with `run_in_executor` in its own body, so the GPU thread guard's Rule B (`backend/tests/test_gpu_executor_guard.py`) still resolves every callable.

- **What stays serial.** Everything stateful runs on the event loop, in input order, before a file is handed to the pool. For import that is the name pick: `unique_filename_with_thumb` reserves each name in `db_filenames` and `planned_thumb_stems` before any copy starts, so picking ahead of copies still in flight gives the same names. For rescan it is `seen_filenames`, the name pick and the collision rename. A failure in that step is queued behind the files in flight (`push_done`), so `failed` keeps its order.
- **Rescan's caption read moved into the pool.** It used to be its own awaited hop per file, registered or not. `_rescan_file_sync` reads it from the file's path *before* any collision rename, because the `.txt` stays at the original stem.
- **Rescan holds back a thumbnail path already in flight.** Two nested files with one stem share a `thumbnail_path_for` path (the nested-file defect at the rename branch). The serial loop wrote them one after the other, so the second waits for the first rather than writing the same file at the same time.
- **A cancel stops new files at once.** The files in flight finish and get their rows, since their bytes are already in `images/`, so a cancel can let at most `bound − 1` more files finish than the serial loop did. A hard cancel cannot stop a pool thread that has started, and a file such a thread copies has no row until the next rescan adopts it.
- **Videos stay one at a time.** They are rare, and their probe and poster cost is ffmpeg's or cv2's, not this path's.

**One decode per file.** `image_service.decode_for_ingest(path, thumb_path)` returns what four separate calls used to: `get_image_info`, `generate_thumbnail`, `extract_generation_metadata` and `extract_embedded_provenance`. Each of those opened the file. On a PNG every one of them also decoded all its pixels: `exif_transpose` (inside `_open_safe`) and both metadata readers call `getexif()`, and Pillow loads a PNG to look for an eXIf chunk after the pixel data. A 4096px PNG was decoded four times; now it is decoded once and every reader shares the loaded image. A JPEG keeps its EXIF in the header, so it goes from two decodes to one. The results are the same as the four calls'. The metadata reader gets a copy of the text chunks taken *before* the load, which is all it ever saw, while the attribution reader reads them after `getexif()`, as it always did. `backend/tests/test_import_parallel.py` checks this against PNGs with chunks after the pixel data, among others, and counts the decodes. Import, rescan (and so ComfyUI's per-row import, through `_register_file_sync`), upload and the snapshot copy use it. A caller that wants only one of the four still calls that one.

**Timing.** Measured 2026-11-12 on 32 logical cores and SATA SSDs, 600 1024px JPEGs and 100 4096px PNGs of about 29 MB each:

| Run | JPEGs | PNGs | PNG peak memory |
|---|---|---|---|
| Before T3 (serial, four decodes) | 14.4 s | 63.3 s | |
| One decode, one file at a time | 12.5 s | 19.5 s | +133 MB |
| One decode, 8 at a time | 1.9 s (7.6×) | 3.5 s (18×) | +873 MB |
| One decode, 16 at a time | 1.3 s | 2.9 s | +1.7 GB |

The cap is 8 because the big files flatten past it (6.6× against 5.6× for twice the memory), and each file in flight holds about 110 MB at 4096px. Unlike T1, whose OpenCV calls are already threaded inside, the curve is close to linear up to 8. The source drive was an SSD. A spinning disk or a network share was not measured.

## Standalone caption import

`import_captions_from_folder(db, dataset, folder_path, job_id)` matches each `*.txt` in a folder to an image by stem (`original_filename` stem first, then `filename` stem) and overwrites. Returns `{matched, unmatched}`. When several images share an `original_filename`/`filename` stem only the first (`setdefault`) is matched. Endpoint `POST /datasets/{id}/import-captions`; `job_type="import_captions"`. UI: per-card "Import captions" button → modal with a folder-path input.

## Gallery entry points and import toasts

The `GalleryPage` toolbar also carries an **"Import folder" button** (next to Rescan/Upload) that opens the shared `ImportFolderModal` for the current dataset, so folder import is reachable without returning to `DatasetsPage`. See `docs/dev/dataset-operations.md` for `ImportFolderModal` and the in-app `DirPickerModal` Browse button.

**An import's outcome toasts come from `TopBar`, for every entry point** (GPT-030): the summary on completion (`utils/importToast.ts`), "Import failed: `<server error>`" on failure, and a cancel notice. The modal only says "Import submitted", because a folder that turns out not to exist, or a drive without room, fails in the worker after the modal has closed. Before, that failure showed nothing but the old "Import started". See `docs/dev/job-invalidation.md` § Job completion → cache invalidation.

## Dropping a caption file onto an image

**Drag a `.txt` onto an image** sets that image's caption (issue #47 approach 2). In `ImageCard` (gallery grid) the card's `onDragOver/onDrop` only intervene when the drag carries a `text/plain` (or empty-type — Windows/some browsers report `.txt` with no MIME type) file and `stopPropagation()` so a `.txt` is consumed as a caption while image-file drops still bubble up to the gallery grid's upload drop zone; in `ImageDetailPage` the caption `<textarea>` accepts a `.txt` drop. Both read the file client-side and call `captionsApi.update(imageId, { caption_text })` (the `PUT /captions/image/{id}` endpoint), then invalidate `["images", datasetId]` (and `["caption", imageId]` in the detail view).

## A stem-keyed derived artifact needs a collision guard at every writer

**A stem-keyed derived artifact needs a collision guard at every site that *writes* it — including the ones that adopt a filename rather than pick one.** Thumbnails and posters are `.webp` keyed by stem, so two files differing only in extension share one derived path and the second write clobbers the first, leaving two rows pointing at one picture. Creation paths pick a free name via `unique_filename_with_thumb`; the two rescan paths instead register files found on disk under the names the user gave them, and resolve collisions in **opposite** directions on purpose — `rescan_dataset` renames the *image file* (`a.jpg` → `a_001.jpg`) because eleven sites re-derive an image's thumbnail path from its filename (enumerated in the code comment at that rename branch), so a drifted thumbnail stem would be orphaned by the next rename/move/crop/restore; `_rescan_videos` renames the *poster* (`clip_001.webp`) and leaves the video file alone, because nothing re-derives a poster path — every consumer reads `Video.poster_path`. When reviewing any new path that writes a derived file, ask which of the two it is. A path registering a file already in place must also pass `disk_exclude={f.name}`, or the uniquifier sees each file's own name occupied and renames everything.
- An **unregistered** file sitting at a rename's target path has no row to guard it and must be refused, not clobbered. (A *pure extension change* — `a.jpg` → `a.png`, from a re-extraction or a PNG format fallback — is otherwise the one rename that disturbs nothing derived: the stem is unchanged, so the thumbnail and the `.txt` sidecar stay put, and no uniquifier call is needed.) See `docs/dev/video/reextract.md` § The extension change.
