# The aesthetic model picker

This file covers the choice between `aesthetic_score`'s two producers and the bookkeeping that keeps a column holding both honest: the `aesthetic_model` marker and its invariant, the two destructive consumers and how each guards against mixed scales, per-model coverage and the re-score offer. The scorers themselves, the columns they write and the scoring job's model lifecycle are `docs/dev/quality/scoring.md`; why V2.5 has its own registry entry is `docs/dev/ml-models.md`. Part of the Quality family; the hub, `docs/dev/quality.md`, routes from a code path to the file that owns it.

## Two producers, one per-run choice

`aesthetic_score` has two producers: LAION's `sac+logos+ava1-l14-linearMSE` MLP over CLIP ViT-L/14 (marker `laion`) and Aesthetic Predictor V2.5 over SigLIP-so400m (marker `v2_5`). Which one runs is a **per-run choice with a sticky default**, not a setting: `aestheticModel` rides in the already-global `QUALITY_WORKFLOW_KEY` blob beside `embeddingType` and `dinoLayer`, and arrives as `ScoreRequest.aesthetic_model`. There is no DB setting and no per-dataset override — the control sits in the same panel as the button that runs it, which makes a cross-dataset carry-over *more* visible than a stored setting would. It is a `Literal["laion", "v2_5"]`, so an unknown value is a 422 rather than an unknown marker in the column, and `body.model_dump()` carries it onto `BackgroundJob.config` and into the job's auto-label (`"Quality: technical, aesthetic (V2.5) — 100 images"`) for free.

**The loop is shared, the per-image callable is not.** `score_images_batch(paths, handle, job_id=…, model=…)` picks between `score_image_sync` and `score_image_v2_5_sync` *above* its loop, importing the V2.5 module inside the branch so a LAION run never imports the package. Duplicating the loop would duplicate the SSE cadence, the `job_queue.cancel_requested` check and the None-on-failure contract (`docs/dev/quality/scoring.md` § The failure contract) — three things this repo has already had to fix once each. `handle` is per-model on purpose: `aesthetic`'s `ModelEntry.model` is a three-tenant `{"clip", "mlp", "preprocess"}` dict, while `aesthetic_v2_5` returns the plain entry and the V2.5 scorer reads `.model` + `.processor`. See `docs/dev/ml-models.md` for why V2.5 gets its own registry entry rather than replacing the existing one.

## The marker is a safety device, not bookkeeping

`Image.aesthetic_model` records which model produced each stored score, because both scales land in 1–10 and that is **all** they share. Two consumers act destructively on the number: `aesthetic_min` in `export_service.py` omits images invisibly, and `rankForKeepBest` in duplicate resolution *deletes* them. So the guards ship with the capability that creates the hazard, not later — the moment a second model is selectable a dataset can hold two scales in one column.

The invariant every consumer leans on is

> `aesthetic_score IS NOT NULL` ⟺ `aesthetic_model IS NOT NULL`

established by migration `a5e1b7c3d9f0`, which backfills `'laion'` onto every existing scored row. The backfill is legitimate here and was not for `scores_stale` for one reason: the historical value is *knowable* — LAION was the only producer that had ever written the column. Without it, five consumers would each re-derive a three-way rule (scored-and-marked / scored-but-unknown / unscored). `routers/quality.py` maintains it at the single write site: the marker is assigned inside the same `i < len(aesthetic_scores)` guard as the score, and set back to NULL when the score is. A marker beside a NULL score would claim a model looked and produced nothing; a stale marker on an overwritten NULL would put a phantom row in the per-model breakdown.

`aesthetic_model` is deliberately **outside** `_JOB_SCORE_COLUMNS` and never enters the router's `refreshed` set — see `docs/dev/quality/scores-stale.md`. It *is* mirrored on `VersionImageState` and diffed; see `docs/dev/versioning-service.md`. It is carried by all five field-by-field rebuild paths, enrolled in their structural guard by its own `info={"qualifies": "aesthetic_score"}` rather than by the `*_score` suffix those guards otherwise derive from (`backend/tests/test_video_lineage_mirrors.py`).

No Enum and no CHECK constraint: a future learned head writes `head:{uuid}` into this column, so the value set is open. Every frontend consumer therefore renders an unrecognised marker verbatim rather than swallowing it — `frontend/src/constants/aestheticModels.ts` is the one place the two known markers are named, shared by the picker, the duplicates refusal, the export advisory and the Stats breakdown.

## The two destructive consumers differ, on purpose

- **Duplicate resolution refuses.** `DupGroupMeta.mixedModels` is true when a group's scored members carry more than one marker; per-group *Keep best* is then disabled with a title naming the models found, and a small producer label renders under each thumbnail's score chip so the refusal explains itself outside a tooltip. `rankForKeepBest` itself stays untouched — it is a pure, null-safe sort and is correct *within* one scale; the refusal belongs at the caller, where the unscored refusal already lives. **The bulk bar skips mixed groups rather than disabling itself**, counted separately as `skippedMixed` beside `skipped` and stated in the confirm dialog: killing the whole bar because 1 of 300 groups is mixed pushes users to resolve by hand in the gallery. *Keep first* reads no score and is untouched.
- **Export warns.** `get_export_preview` emits `aesthetic_models` and `aesthetic_models_will_export`, both `{marker: count}` — the same whole-scope / will-export pair the stale-scores and unlicensed advisories use. Dicts rather than a bool, because the useful sentence is *"1,204 by LAION, 766 by V2.5"*: the skew is what says whether one `aesthetic_min` threshold is over- or under-including. Advisory only — it never blocks, never changes `will_export`, and adds no exclusion row. It renders whenever more than one marker is present rather than only when filtering, because the gallery's aesthetic sort reads the same column.

## Per-model coverage and the re-score offer

Two surfaces, two mechanisms, deliberately not shared:

- **Stats** gets a `GROUP BY Image.aesthetic_model` beside the existing three-count coverage query, emitted as flat `aesthetic_{marker}` keys in `score_coverage`. **`aesthetic_*` is a reserved prefix** in that dict. No schema change (it is `dict[str, int]`) and the CSV export picks them up for free. They are *not* added to `StatsPage`'s `coverageDefs`, which stays at four entries: that list is a fixed four-column grid and the producer set is open-ended. The page renders a breakdown line under the Aesthetic tile instead, and only when more than one producer is present.
- **The Score images page** gets its own endpoint, `GET /quality/aesthetic-coverage/{dataset_id}?subfolder=` → `{"scored", "unscored", "by_model"}`. It needs the page's subfolder scope and a refetch on job completion, and dragging `get_dataset_stats` onto a page that otherwise makes three light queries would be the expensive way round. `by_model` sums to `scored` — that is the arithmetic the backfill buys.

**The re-score offer takes a scoping flag, not an id round-trip.** `ScoreRequest.only_mismatched` adds `Image.aesthetic_score.isnot(None), Image.aesthetic_model.isnot(body.aesthetic_model)` to the selection query, so it composes with `subfolder` like every other scope and the selection stays atomic with the run. It deliberately excludes never-scored rows: plain *Run scoring* already covers those, and two buttons with two literal meanings beat one with a mode.
