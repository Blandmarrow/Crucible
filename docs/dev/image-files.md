# Image files: naming, moves & deletes

This file covers how image files are named and renamed on disk, upload reporting, cross-dataset moves and copies, and deleting images. The gallery UI that triggers them is in `docs/dev/gallery.md` and `docs/dev/datasets-page.md`. The paths that bring images and captions in from a folder (import, rescan/sync, standalone caption import), and the stem-keyed collision rule the rescans share with every creation path, are in `docs/dev/image-import.md`.

## Image file naming

Images receive human-readable names derived from their original filename via `slugify_filename`. Collision handling is done by `unique_filename_with_thumb` (counter suffix `_001`, `_002`, …) in every path that creates or renames an image file with an associated thumbnail — upload, bulk-rename, rename-image, crop new-file, batch-move-subfolder, batch-move-dataset, batch-copy-dataset, rename-on-caption, upscale non-replace, LUT non-replace, detection crop new-file, video frame extraction, folder import (images *and* videos), ComfyUI generate-import, versioning restore, and folder rescan (which adopts a name off disk rather than picking one — see `docs/dev/image-import.md` § Folder rescan / sync). Treat that list as illustrative and grep as authoritative — it has been out of date twice. Use `unique_filename_with_thumb` for any new image-creation path: the bare `unique_filename` has no caller anywhere outside `utils.py`, where `unique_filename_with_thumb` is its one consumer.

**The occupied-stem set is per thumbnail directory, never one flat set.** Build it from the `thumbnails/` dir of the image being written, inside the loop, keyed in a dict — `routers/detection.py`'s `occupied_by_dir` / `planned_by_dir` pair is the shape to copy. A job selecting on `Image.id.in_(...)` has no dataset constraint, so its selection can span datasets with distinct `thumbnails/` dirs; `routers/lut.py` and `routers/upscaling.py` each built one flat set from `images[0]`'s dir and false-shared stems across them until 2026-07-31 (PM-007's § Fix records the recurrence). `db_names` was already per image in both, which is why the derived *filename* looked right while the `.webp` landed on a live sibling's.

**`bulk_rename` is the one sanctioned exception** to the rule that a batch must not exclude its own members' stems from that set — it excludes them so a second Renumber restarts its counter, and pays for it with a two-phase rename whose collision test covers all three artifacts a rename moves. See `docs/dev/bulk-ops.md` § Renumber's two-phase rename and `docs/dev/postmortems/PM-017-bulk-rename-clobbered-a-sibling-stem.md`.

`Image.is_auto_named: bool` (default `False`) — set to `True` when a file is renamed by the captioning job or by a subfolder move. Used to distinguish auto-named files from manually named ones. `PATCH /images/{image_id}/rename` sets it back to `False`.

**Single rename** (`PATCH /images/{image_id}/rename`) is the twin of `PATCH /videos/{id}/rename` (`docs/dev/video/endpoints.md`) and carries the same two guards. A row whose file was deleted underneath it **404s** rather than surfacing `FileNotFoundError` as a 500 with the row already renamed. The thumbnail move is a **post-commit epilogue**: ORM fields → `rename_with_sidecar` → `commit()` → the `old_thumb.replace(new_thumb)` in a logged `try/except`, per CLAUDE.md § Key invariants (the **Nothing fallible between an irreversible filesystem mutation and the `commit()`** entry). Sitting between the rename and the commit, an `OSError` there discarded a rename that had already happened on disk. `img.thumbnail_path` names the new thumbnail either way — the row states intent, and `serve_thumbnail` regenerates a missing one on the next view.

**Subfolder-based naming**: when `rename_on_caption=True` or when images are moved between subfolders (`POST /images/batch/move-subfolder`) or between datasets (`POST /images/batch/move-dataset` / `POST /images/batch/copy-dataset`), filenames are derived from the target subfolder slug (e.g. images in `"animals"` become `animals.jpg`, `animals_001.jpg`, …; images in root become `image.jpg`, `image_001.jpg`, …). Cross-dataset moves and copies always rename. For same-dataset subfolder moves, renaming is conditional: `BatchMoveSubfolderRequest.rename_on_move: bool = True` — when `False`, only the `subfolder` metadata column is updated and filenames are preserved (the user's preference is stored in `localStorage` under `SUBFOLDER_RENAME_KEY` and read by `SelectionToolbar` at mutation time).

**`batch/move-subfolder` takes one dataset's ids per request** and answers 400 to a mixed list, before touching anything. Everything it does is keyed on one dataset — the images folder it renames into, the filename set it uniquifies against, the busy guard — and it used to take that dataset from `rows[0]` for every row, so a gallery selection spanning split-view panes renamed the second dataset's files into the first one's folder while their rows kept their own `dataset_id`. A subfolder is a per-dataset label, so a mixed request has no single meaning to repair it to. `SelectionToolbar` sends one request per dataset (see `docs/dev/frontend-core.md`); the gallery's drag path only ever sends its own pane's ids. `backend/tests/test_move_subfolder_mixed_datasets_http.py` covers both `rename_on_move` values.

**A subfolder move with renaming commits per image**, unlike the two DB-first batch paths below: UPDATE the row → `rename_with_sidecar` → `commit()` → the thumbnail move in a logged epilogue. A failed rename rolls back that one row with its file still at the old name, is counted in the response's `failed`, and the loop carries on. The old shape — every row staged, every file renamed, one `commit()` after the loop — rolled back the rows of every file it had already moved (PM-013's "is the commit per item?" question, GPT-009).

**A caption sidecar never fails a rename.** `rename_with_sidecar`'s contract is *a raise means nothing moved*: only the image rename can raise, and a `.txt` that will not move is logged and reported by a `False` return, with the image already at its new name. The two renames cannot be atomic, and the image is the half a row names — a raise after it moved stranded a rename-first caller's row on a vanished path (`GET /file` 404), and sent a commit-first caller's compensation back onto the old one. A stranded `.txt` loses nothing durable: `Image.caption_text` is the authority.

## Upload reporting

**Upload reporting goes through `frontend/src/utils/uploadToast.ts`** — `tallyUpload(results, errors)` folds one or more responses into a tally, `showUploadSummaryToast(tally)` reports it. Both `GalleryPage.handleUpload` and `DatasetsPage.handleCardDrop` (the dataset-card file drop) use it. It exists to enforce one contract: `POST /images/upload` answers `{added, files, videos_added, videos, skipped}` and returns **201 even when it declined a file** — an unsupported or unreadable file comes back as a `skipped: [{file, reason}]` entry, never as an HTTP error, because one bad file must not fail the rest of a multi-file upload. Counting thrown requests therefore reports a rejected upload as a successful one, which is how the two call sites had already drifted: the card reported every dropped file as an uploaded image. The tally keeps `errors` (thrown requests) and `skipped` (server-declined) apart — a network failure and an unsupported type need different wording — and the toast names the reason for the first three skips. `videos_added` counts files routed to the `videos` table instead of `images` (`docs/dev/video.md`); the client-side pre-filter that decides what is worth POSTing is `constants/mediaTypes.ts` (`docs/dev/frontend-core.md` § Frontend constants).

## Cross-dataset moves and copies

**Cross-dataset moves** (`POST /images/batch/move-dataset`): accepts either `image_ids` (explicit list) or `source_dataset_id + source_subfolder` (moves the whole subfolder). Files are renamed to the target subfolder slug, moved to `{target_dataset.folder_path}/images/`, thumbnails are copied then the originals removed. Calls `refresh_stats` on **every source dataset in the selection** and on the target after the filesystem operations — a selection can span datasets, so the router derives `source_dataset_ids` from the rows and drives the busy guard and provenance materialization off the same set (CLAUDE.md § Key invariants). The UPDATE also NULLs `Image.source_video_id`, since the destination holds no such video; `source_timestamp_ms` and `source_shot_index` travel. **DB is committed before the filesystem operations** so the DB is always the authoritative record of where files should live; if a rename fails mid-batch, already-moved files remain accessible via their new DB paths while not-yet-moved files are temporarily unreachable.

**Cross-dataset copies** (`POST /images/batch/copy-dataset`): same request schema as move. Source images and files remain untouched; new `Image` records are inserted in the target dataset with all metadata copied (scores, captions, flags, generation metadata, processing history — deferred blob embeddings are not copied). Frame lineage splits: `source_video_id` is deliberately omitted from the column tuple and written as `None`, because it would point at a video the destination does not contain, while `source_timestamp_ms` and `source_shot_index` travel. Same rule as move; see CLAUDE.md § Key invariants. Uses `copy_with_sidecar` for the image file and `shutil.copy2` for the thumbnail. Calls `refresh_stats` on the target only. **DB inserts are staged before file copies** so that a filesystem failure prevents commit and leaves no orphaned DB records (opposite ordering to move — here an incomplete copy should leave nothing rather than partial records).

**Regression tests**: `backend/tests/test_rename_collisions_http.py` pins rename/bulk-rename placement over HTTP (thumbnail-stem uniquify, sidecar-follows-rename, mixed-suffix distinct stems, the two-phase swap-permutation rename — PM-001 class, plus the cross-extension stem clobber and the counter restart — PM-017); `backend/tests/test_move_copy_placement_http.py` pins move/copy file + thumbnail + sidecar placement and both DB-vs-filesystem ordering invariants above under mid-batch fault injection. The two placement tests that matter most **assert bytes, not names** — a clobber leaves every filename correct and is invisible to a set-of-stems assertion.

Frontend entry points for both: `SelectionToolbar` ("Move to Dataset" / "Copy to Dataset" buttons) and `GalleryPage` subfolder sidebar (arrow icon for move, copy icon for copy). Shared modal: `MoveToDatasetModal` (`frontend/src/components/common/MoveToDatasetModal.tsx`) — accepts an optional `mode?: "move" | "copy"` prop (default `"move"`) which changes the icon, title, and confirm button label. Callback prop is `onConfirm(targetDatasetId, subfolder)`.

## Deleting images

**Files first, row second** — the order `videos.delete_video` set (PM-021), shared by all four image deletes through `backend/services/image_delete.py` (GPT-008). `unlink_image_files` gates each path through `contained_path`, backs the file up with `mark_image_deleted_in_versions` (it copies the bytes, so it must precede the unlink) and **commits that backup before any unlink** — left pending in the delete's transaction, a failure past the unlink rolled back the snapshot's record of a file already gone, and no retry could re-record it — then unlinks the image through `unlink_retrying`, then the `.txt` and thumbnail best-effort. It raises **only while the image file is still on disk**, so the caller keeps the row. `delete_image` lets that raise — a lock is the `main.py` 409, with row and file intact. `batch_delete`, `bulk_delete_filtered` and `quality.resolve_duplicates` use `unlink_files_for_rows`, which keeps the row of any file that would not go and answers `{deleted, in_use, failed}`; refusing the whole batch would be wrong, since the files before the lock are already gone. Then the DELETE, `prune_orphaned_duplicate_flags`, `commit()`, and `refresh_stats` — which used to run after the unlink and so never ran when one raised. The old order (commit, then unlink) answered 500 with the row gone and the file stranded, and a retry 404'd.
