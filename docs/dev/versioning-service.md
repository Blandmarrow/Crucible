# Version service internals

This file covers `backend/services/version_service.py` — the copy-on-write and deletion
hooks, `create_snapshot`, `restore_snapshot`'s four passes, `diff_versions` — and the table
of call sites in other routers where the two hooks fire. It is the half of versioning that
is read line by line when something has gone wrong.

The model, the object store, the busy guard, the `/datasets/{id}/versions` routes and the
frontend are in `docs/dev/versioning.md`. Two CLAUDE.md invariants point at restore's Pass 2
and Pass 3 — DB-before-filesystem, and "nothing fallible between an irreversible filesystem
mutation and the `commit()`" — and the Path traversal guard names both hooks by symbol.

## Service

**Backend service** (`backend/services/version_service.py`):

Key functions:
- `protect_file_before_overwrite(image_id, file_path, db)` — COW hook; fires in **every** versioning mode, gated only on `_has_lazy_rows` — the image has a snapshot row with `file_hash IS NULL` — and never on the mode (GPT-022, PM-026). It only *flushes* the hash backfill — every caller that overwrites the file before its own final commit must `commit()` right after the hook (all current call sites do), otherwise a crash during the overwrite rolls the backfill back and the snapshot rows silently claim "content unchanged"
- `mark_image_deleted_in_versions(image_id, file_path, db)` — deletion hook; the same `_has_lazy_rows` gate, Off mode included (a fully hashed snapshot already holds the bytes, so it is a no-op there)
- **Containment is enforced inside `_store_row_bytes`**, the single place a row's bytes enter `{ds}/.versions/objects/`: `_backup_and_record_hash` (and so both hooks) and Manual `create_snapshot`'s eager copy both route through it, so one guard covers every call site. The eager copy was the second entry and went ungated until PM-026 — an escaping symlink was copied in on every Manual snapshot; such a row is now skipped with its own `[warning]` line, which is a refusal and never counts as a backup failure. It is not just bookkeeping — an out-of-tree `file_path` is an arbitrary-file read primitive retrievable through a snapshot restore, even if the caller skipped the unlink. The base is the row's own `dataset.folder_path` rather than `settings.datasets_dir`, which is stricter and also catches a row pointing into another dataset; a refusal is a skip-and-log, so an out-of-tree row still completes its overwrite or deletion instead of failing the job. Because `within_datasets_dir` resolves, it catches the one live vector: a symlink placed in `{ds}/images/` that rescan registers under its in-tree path while `open()` follows it out of tree. `backend/tests/test_versioning_maintenance.py` pins the hook and the eager copy, the symlink case built rather than reasoned about.

  The **call-site** gates (`utils.contained_path`, per the CLAUDE.md Path traversal guard) are still the right shape and are defence in depth rather than redundancy: they also gate the `unlink`, and they let a destructive route drop the row for a path it refuses to touch. A destructive route that refuses a path must therefore skip the hook too, not only the `unlink`; and a site that fires *both* hooks must gate the whole loop, not the deletion branch alone. Two sites gated only their unlinks until 2026-07-31: `routers/filesystem.py::delete_path`'s row loop (reachable because the endpoint validates with `sanitize_abs_path`, which proves a path absolute, not contained) and `restore_snapshot`'s extras loop, whose `else` branch reaches the same primitive through `protect_file_before_overwrite`. Both are now gated per row and the row deletes stay unconditional. Tests: `backend/tests/test_path_containment_http.py` and `test_versioning_restore.py` — both need a lazy (NULL-hash) snapshot row, or the hook no-ops and the test proves nothing; the restore one needs **two** snapshots, since an extra added after the only snapshot has no `VersionImageState` row and the hook returns on its first query.
- `_backup_and_record_hash(image_id, file_path, dataset_folder, db, precomputed_sha256=None)` — shared helper: store via `_store_row_bytes` → backfill all NULL `file_hash` rows for the image in one `UPDATE` with the hash of the bytes *actually stored*. `precomputed_sha256` is only a fast path: when its object already exists, all I/O is skipped (the content is safely stored — correct even if the file changed since the caller hashed it); otherwise the file is re-streamed through `_store_object`, so a stale caller hash can never poison the store or the state rows.
- `create_snapshot(db, dataset_id, name, description, branch_id, parent_id, job_id, source)` — creates snapshot; an explicit `branch_id` must belong to the dataset (`ValueError` → 404 otherwise, GPT-024), and `create_branch`/`restore_snapshot`/`diff_versions`/`checkout_branch` check their version ids the same way. `parent_id` is not vestigial: `create_branch` passes `parent_id=from_version_id` so a branch-init snapshot's parent is the source branch's head. `source` is `"manual"` (user-triggered), `"pre_restore"` (auto before restore), or `"branch_init"` (new branch). When `branch_id` is omitted it resolves to the dataset's **current branch** (`dataset.current_branch_id`), falling back to `main` only for never-branched datasets — so pre-restore/checkout auto-snapshots land on the branch the user is actually on and never move `main`'s head. `"manual"` mode also copies every file eagerly; per-file backup failures are counted, appended as a `[warning]` line to the version description, and emitted in the job progress (a NULL hash would otherwise restore as "content unchanged" with no trace). `create_branch` resolves its `from_version_id` default from the current branch's head the same way.
- `restore_snapshot(db, dataset_id, version_id, handle_extra_images, pre_restore_snapshot, job_id)` — refuses a version of another dataset (GPT-024); optionally auto-snapshots current state before it mutates anything — after planning and the Pass 0c gate, before Pass 1 (**a failed safety snapshot aborts the restore** with a `RuntimeError` — proceeding would silently make it non-undoable; the UI checkbox is the explicit opt-out); after all files are restored, sets `branch.head_version_id = version_id` so the UI "Current" badge moves to the restored snapshot. Runs as **four passes** (plan → protect → DB-commit → execute), each with an invariant:
  - **Pass 0/0b — plan, and resolve foreign IDs**: builds a per-image `_RestorePlan`. Pass 0b handles snapshot images whose `image_id` now lives in *another* dataset (moved out via batch move — the ID cannot be re-inserted here): a same-name current image whose content hash matches the snapshot is **adopted** (keeps repeat restores from duplicating), otherwise the row is **forked** under a fresh UUID and its content restored from the object store; with no recorded hash there is nothing to materialize (counted in `files_unavailable`).
  - **Pass 0c — path gate, before the pre-restore snapshot**: `_refuse_unsafe_restore_paths` proves every path the restore will write or move is safe, collects every violation, and raises `RestoreRefused` (a `RuntimeError`, so the job ends `failed` with the count and one example in `error_msg`, ending "Nothing was changed."). Three rules: every **target** of a plan that yields a row — and its derived thumbnail, which `generate_thumbnail` would mkdir — resolves strictly inside the dataset folder and not under `.versions`; every **renamed source** Pass 3 moves, stages or unlinks is inside `settings.datasets_dir` (looser on purpose, so a live row a pre-fix restore left under an old root can be moved home); and no target, renamed source or touched extra (keep mode: those on a restored filename; remove mode: all) is **another dataset's** `Image.file_path`, one chunked `IN` query. Snapshot paths are history — absolute, written when the snapshot was taken — so a dataset rename used to leave them naming the old root, and a new dataset reusing that name had its files overwritten (GPT-021, PM-025). `rename_dataset` now rebases them; the gate is for whatever still escapes. The order is the point: Pass 0/0b only read, so running the gate and then the safety snapshot means a refusal leaves no orphan pre-restore version, and Pass 1's COW backfill still finds that snapshot's NULL-hash rows. Re-created rows take the gated `p.target_path`.
  - **Pass 1 — gated, hash-once COW protection (undoable in auto mode)**: `protect_file_before_overwrite` fires *only* for files the restore will actually overwrite/move/delete (in-place restores hash the file once, decide `needs_restore`, and reuse the hash via `precomputed_sha256`; pure renames are moved, never backed up), so the pre-restore snapshot's NULL-hash rows get backfilled without hashing/copying the whole dataset. Protection is keyed on `p.img.id` (an adopted plan's current row is a different image than the snapshot recorded). Extras occupying a restore target are protected too (`keep` mode) or run through `mark_image_deleted_in_versions` (`remove` mode) before any file write. In Manual mode the pre-restore snapshot copied everything eagerly, so its own rows are hashed and the hook skips them — but Pass 1 still backs up the lazy rows of any *older* Auto snapshot (GPT-022). A file that fails to hash is protected anyway (the hook re-streams it), and a backup that raises aborts the restore — see the bullets below.
  - **Pass 2 — DB before filesystem, with DB-level rename staging**: all Image rows (re-creations, metadata, and the reverted `filename`/`original_filename`/`file_path`) are committed *before* any file moves, matching the CLAUDE.md DB-before-filesystem invariant. SQLite checks `uq_dataset_filename` **per statement**, so the commit is staged in three flushes: **2a** extras are cleared off restored names first (`remove`: deleted + flushed so the DELETEs precede any re-creation INSERT; `keep`: extras occupying a restored filename are renamed aside to a uniquified name via `unique_filename_with_thumb`, like import collisions — both images survive); **2b** every renamed image is parked on a unique `__dbtmp_{id8}{suffix}` temp filename (swaps/renumber chains would otherwise abort the whole restore with an IntegrityError); **2c** final values + re-creation INSERTs flush collision-free. A move that later fails gets a per-image compensating fixup (`_compensate_paths`) pointing the row back at the file's actual location.
  - **Pass 3 — collision-safe execution**: first the keep-mode extras renamed in 2a are physically moved to their new names (file + sidecar + thumbnail), *then* rename sources that are another image's restore target are staged to `{stem}.__restore_tmp_{id}{suffix}` temp names (swaps/renumber chains can't clobber a file that is still someone's current content). Content restores copy from the object store to `target_path`; a pure rename (auto mode leaves `file_hash=NULL`) *moves* the file (`rename_with_sidecar`). Stale files/sidecars/thumbnails at the old path are removed **only after the restore/move succeeded** — and when the object-store copy is missing, the current file is *moved* to the target, never deleted (it may be the only remaining copy; counted in `files_unavailable`). Each plan's file work is individually contained: an unexpected failure (disk full, permissions) logs, counts in `files_failed`, compensates that row's paths, and the batch continues; after the loop a sweep recovers any unconsumed `__restore_tmp` file to its row's committed path so none is ever left untracked. In `remove` mode, extras' files are unlinked last — **skipping any path in the restored target set** (a restored image owns it now; unlinking would delete the just-restored file). All unlinks go through the path-gated `_remove_stale_files` (V-83) via `run_in_executor`. Thumbnails are regenerated from the row's final `file_path`. Finally, `_sync_caption_sidecar` makes the on-disk `.txt` sidecar match the restored `caption_text` for every image (written when non-empty, deleted when empty) — without this, `rescan_dataset` treats the stale sidecar as a caption edit and silently reverts the restored caption seconds later when `auto_rescan_on_open` fires.
- **The pre-restore safety snapshot is complete or the restore does not start** (GPT-023, PM-026). Restore passes `create_snapshot(..., require_complete=True)`: in Manual mode any per-file copy failure rolls back and raises `SnapshotIncomplete` *before* `add_all` and the commit, so no partial safety version is committed and the branch head does not move; restore's wrapper reports "could not be backed up … aborted before any changes were made". A user-initiated Manual snapshot keeps the commit-with-`[warning]` behaviour. In Auto the flag does nothing — the backups are Pass 1's.
- **Pass 1 is all or nothing.** Its whole body (plans and extras) sits in one `try`: a backup that raises rolls back the flushed backfills, deletes the pre-restore snapshot it had already committed (`_discard_snapshot`, head back to its parent, itself unable to raise) and raises "restore aborted before any file was changed". Hashing the current file is the one step allowed to fail quietly: with no hash, the hook re-streams the file (new gap 6b — previously a hash failure skipped the backup while Pass 3 still overwrote the file).
- **Pass 3's failure contract** (GPT-025, PM-026). An object is copied to `objects/.tmp-{uuid}` (prune sweeps those; rescan never looks) and swapped in with `utils.replace_retrying` — the overwriting form, which on Windows retries a held file and then raises `FileInUseError` — with a `try/finally` removing any leftover temp. A failed write therefore leaves the old pixels intact; `shutil.copy2` onto the target used to truncate it first. Every counted failure — `files_failed`, `files_unavailable`, staging and pure-rename failures, keep-mode rename-aside failures (`extras_failed`) — gets one `{file, error}` entry (capped at 50); thumbnail failures count as `thumbnails_stale`. A plan that needed content and did not get it is **reconciled**: a re-created row is deleted with its `ImageLabel` and `Detection` rows (explicit deletes, not the FK cascade), any other row gets back the pixel values captured in Pass 0 (`_RestorePlan.pre_pixel`: the ten scores, `aesthetic_model`, `scores_stale`, `quality_flags`, `dino_layer_scores`, `processing_history`, geometry, phash) and is re-measured, and — when Pass 2c replaced them — its pre-restore detections (`_RestorePlan.pre_detections`), whose geometry is in the frame of the pixels still on disk. Caption, provenance, labels, `sort_order`, generation metadata and lineage keep the snapshot's values — the metadata restore succeeded; only the pixels did not. Every new step is wrapped, since Pass 3b sits between two commits (PM-013).
- **The outcome reaches `result_data`.** The return dict adds `failed_count` (`files_failed + files_unavailable + extras_failed`), `failure_summary` (≤ 300 chars, up to three files), `failed`, `extras_failed` and `thumbnails_stale`; the restore and checkout routes write it with `_store_result` inside `busy`, and the job stays `completed` (PM-023's convention). `checkout_branch` passes it through and **still switches branch after a partial restore**. `_sync_caption_sidecar` catches `ValueError` as well as `OSError`: a non-UTF-8 sidecar used to escape Pass 3b and skip the final commit. Known gaps: a staging failure is counted, not made safe; a keep-mode extra whose rename-aside fails can be overwritten if no snapshot row covers it; `_remove_stale_files` still swallows its errors.
- **phash, size, format and geometry are measured, not mirrored** (GPT-016). After a content write or a re-creation, `_measure_into` reads the written file through `get_image_info` (never raises; assigns only what it measured). A `VersionImageState.phash` mirror was rejected: its backfill would copy today's possibly stale `Image.phash` into history (resize and batch crop still leave it stale) and it needs a migration. The cost is one extra decode per restored file, beside the thumbnail's.
- **`duplicate_dataset`'s snapshot branch is the gate's read-side twin** (`backend/services/dataset_service.py`). A NULL-hash (Auto-mode) row is copied from its recorded `file_path`, which is history in exactly the sense above; a path that `within_datasets_dir` cannot place inside the *source* dataset's folder is logged and counted in `skipped` rather than copied, so a stale snapshot cannot pull another dataset's bytes into the clone. `test_versioning_restore.py::test_duplicate_from_snapshot_skips_an_out_of_tree_lazy_row` pins it. Each copy's phash is measured from the copied file, since `VersionImageState` carries none (GPT-016).
- `diff_versions(db, dataset_id, v1, v2)` — pure DB, no background job; uses `_DIFF_COLS` column-explicit select for efficiency. Compared fields: `caption_text`, `quality_flags`, `subfolder`, **all ten `*_score` columns** — every one is mirrored on `VersionImageState` and compared; migration `d1c7b4e9f0a3` added the last three (`nsfw_score`, `saturation_score`, `luminance_score`) and says why the earlier carve-out was wrong — `dino_layer_scores`, `generation_metadata`, the five provenance columns (`source_name`, `source_url`, `license`, `attribution`, `source_meta`), `sort_order`, `processing_history`, `scores_stale`, `aesthetic_model`, `label_ids`, `detections` (both detailed below), plus `file` (hash). The list is the module-level **`_DIFF_COMPARE_FIELDS`** tuple, hand-synced with `_DIFF_COLS`: adding a column to `_DIFF_COLS` alone selects it from both versions and then throws it away (which is how `source_meta` was loaded on every diff without ever being compared), while a name in `_DIFF_COMPARE_FIELDS` that is missing from `_DIFF_COLS` is never selected and so silently reports "unchanged". `test_provenance_http.py` asserts the compare list is a subset of the selected columns. The heavy JSON fields in `_HEAVY_DIFF_FIELDS` (`dino_layer_scores`, `generation_metadata` — full ComfyUI workflow payloads — and `source_meta`, a scraper's raw sidecar payload) are compared but reported only as a compact `{"changed": true}` marker, never embedded. `processing_history` changes render as `+`/`−` operation badges in `DiffModal`; `{"changed": true}` renders as "field: changed"; the generic `ChangeRow` renders any other field via `JSON.stringify`.
- **Labels are mirrored as `VersionImageState.label_ids` and written at the end of Pass 2c**, before the commit that is the DB→filesystem boundary. `create_snapshot` prefetches them with one `label_service.labels_by_image` call (a per-image query inside the state loop would be N+1 over 20k images). The restore keys on **`p.img.id`, not `p.state.image_id`** — Pass 0b can fork a fresh uuid or adopt a different row, and writing the snapshot's id would label an image in another dataset — skips `skip_recreate` plans, resolves ids through `live_label_ids` with one aggregate warning for labels deleted since the snapshot (there is no FK to catch it), and calls `set_labels`, which is an **authoritative replace, not a merge**: a label added after the snapshot disappears exactly as a caption edit does, while `handle_extra_images="keep"` images keep theirs because only ids in `wanted` are touched. A row Pass 0b forks (its image now lives in another dataset) needs no id remapping at all — the payoff of the vocabulary being global. `label_ids` is in `_DIFF_COLS` and `_DIFF_COMPARE_FIELDS` and **not** in `_HEAVY_DIFF_FIELDS`; because the comparison runs on ids, a rename produces no diff, and the ids are resolved to names once per diff (joined to a comma-separated string server-side, so `DiffModal` needs no change; an id with no row renders `(deleted)`). See `docs/dev/labels.md`.
- **Detections are mirrored as `VersionImageState.detections` and written right after the labels** (GPT-026), because their normalized geometry qualifies the pixels exactly as the scores do — restoring older pixels and leaving a later crop's boxes framed the wrong picture. One shape for both directions lives in `detection_service` (`serialize_detection`/`deserialize_detection`: label, bbox, score, model, task, mask, ISO `detected_at` — no ids, no `mask_area`, which the ORM listeners recompute when the restore constructs the row), stored sorted by `canonical_detections` since the diff compares with `!=`. `create_snapshot` prefetches with one chunked `detections_by_image` (a column select, so a dataset's masks never enter the identity map); restore captures each plan row's current list into `_RestorePlan.pre_detections` after Pass 0b (so an adopted row's are the ones read), then calls `set_detections` — the same keyed-on-`p.img.id`, authoritative-replace, only-named-ids contract as `set_labels` — skipping images whose list already matches, so a no-op restore does not churn detection ids.
- **`VersionImageState.detections` is nullable with no server default, unlike `label_ids`**: NULL is "not recorded" (a row older than migration `a6d2e8f4c1b3`) and leaves the image's detections alone, where a `'[]'` default would wipe them on restoring an old snapshot and a backfill would record geometry in the wrong pixel frame. New snapshots always write a list. The diff compares only when both sides are non-NULL and renders each side as a summary (`"3: face×2, hand"`, `"none"`), never the polygons; identical summaries over differing lists get `" (geometry changed)"` (a box or mask differs) or `" (re-detected)"` (only score/model/task/time) on the `to` side. Dataset duplication — from disk or from a snapshot — still does **not** carry detections. Guarded by `backend/tests/test_detections_snapshot.py`, whose structural test pins the `detections=` kwarg in `create_snapshot` and the `set_detections` call in `restore_snapshot`. See `docs/dev/detection.md`.
- **`scores_stale` is mirrored *and* diffed, because it is mutable.** `_DIFF_COLS`' carve-out is for immutable frame lineage — written once by extraction, so a comparison is a guaranteed "unchanged". An in-place pixel rewrite between two snapshots flips this column and nothing else, which is exactly the kind of difference the diff exists to show. It must also travel with the scores it qualifies: a restore that brought back stale numbers without the bit would silently present them as trustworthy. See `docs/dev/quality/scores-stale.md`.
- **`aesthetic_model` follows the same rule for the same reason.** It records which of the two aesthetic producers wrote `aesthetic_score`, and it is mutable — a re-score with the other model flips it — so it is mirrored *and* compared rather than falling under the immutable-lineage carve-out. Dropping the mirror would be the sharper failure: a restore would write back a snapshot's LAION score onto a row whose marker still read `v2_5`, so the number and its terms would disagree, silently disarming a guard that gates image *deletion*. See `docs/dev/quality/aesthetic-model.md` § The marker is a safety device.
- **Snapshot rows written before `d1c7b4e9f0a3` were backfilled** for those three columns from `images` by `image_id`, so an old snapshot claims *today's* score. That is the only knowable value, and it is exactly what a restore of that snapshot left in place before the migration (the columns were never written back), so behaviour is unchanged and no spurious diff row appears between two pre-migration versions. Rows whose image is gone stay NULL.
- `DELETE /{id}/versions/{version_id}` head reassignment: when the deleted version is the branch head, the head moves to the version's **parent** if it exists on the same branch, else to the newest remaining version on the branch. Parent-first matters after a restore: the newest-by-`created_at` version is then the pre-restore auto-snapshot — exactly the state the user restored away from.

| `backend/routers/lut.py` | `_run` coroutine, replace=True branch — calls `protect_file_before_overwrite` |
| `backend/routers/videos.py` | `_run_reextraction`'s per-frame `_rewrite` — calls `protect_file_before_overwrite` before swapping the full-resolution frame in. Unlike the rows above it verifies the new file re-opens *first*, so a frame that fails is never protected-then-not-overwritten (`docs/dev/video-reextract.md`) |

| `backend/routers/quality.py` | `resolve_duplicates`, delete branch — calls `mark_image_deleted_in_versions` per row, then `refresh_stats` per dataset |
| `backend/routers/images.py` | `batch_move_dataset` — calls `mark_image_deleted_in_versions` per moved image *before* the dataset_id updates (a cross-dataset move is a deletion from the source dataset's history; without the backup, pre-move snapshots could never materialize the image) |
| `backend/services/version_service.py` | `restore_snapshot`, Pass 1 — calls `protect_file_before_overwrite` (gated: only files that will actually be overwritten/moved/deleted, hash passed as `precomputed_sha256`) before any file operation, backing current content into the pre-restore snapshot so the restore is undoable in auto mode |
| `backend/services/version_service.py` | `restore_snapshot`'s extras loop in Pass 1 (before any FS write) — `mark_image_deleted_in_versions` per extra in `"remove"` mode, `protect_file_before_overwrite` for a `"keep"`-mode extra occupying a restore target. `utils.contained_path` gates the **whole loop**, not just the `"remove"` branch: both hooks end at `_store_object` and are the same read primitive. Files + `.txt` sidecars + thumbnails are unlinked later in Pass 3c via `_remove_stale_files` in an executor, which gates containment **inside** the helper (V-83): it has five call sites and this is the riskiest, handing over an arbitrary row's stored `file_path`/`thumbnail_path` untouched. `contained_path` never raises, which matters — that helper's body sits in a bare `except Exception: pass` that would swallow it silently |
