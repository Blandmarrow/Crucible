# Backend infrastructure: server lifecycle, database & SSE

This file covers production frontend serving, server shutdown/restart control, database conventions (subfolders, indexes, deferred columns), the SSE progress broadcaster, and job cancellation. Venv/dependency/GPU setup (`manage.ps1`/`manage.sh`) moved to `docs/dev/environment-setup.md`.

### Frontend serving (production)

`backend/main.py` serves the built React app after all API routers are registered. Two parts:

1. `app.mount("/assets", StaticFiles(directory=frontend_dist/"assets"))` — serves JS/CSS/fonts at their exact paths with correct content-type headers.
2. `@app.get("/{full_path:path}")` catch-all — for any unmatched path, serves the file directly if it exists in `frontend/dist/` (favicon, manifest, etc.), otherwise returns `index.html` so React Router handles client-side navigation.

**Do not replace this with a bare `StaticFiles(html=True)` mount.** Starlette's `html=True` only falls back to `index.html` for directory-style paths (`/`); it returns 404 for deep URLs like `/datasets/abc123` on hard refresh. The catch-all route is required for SPA routing to work correctly.

### Server control endpoints

Three endpoints are registered directly in `backend/main.py` (not via a router), immediately before the frontend-serving block:

| Endpoint | Behaviour |
|---|---|
| `POST /api/v1/shutdown` | Touches `.shutdown` sentinel, then spawns a daemon thread that sends `SIGTERM` to the current process, triggering uvicorn's graceful shutdown. The sentinel lets the manage script distinguish a clean shutdown from a crash. |
| `GET /api/v1/health` | Returns `{"status": "ok", "start_time": <float>}`. `start_time` is `time.time()` captured once at module load (`_START_TIME`). Used by the frontend to detect when a restarted server is a *new* process. |
| `POST /api/v1/restart` | Removes `.shutdown` (if present), creates `.restart` sentinel file (`_RESTART_SENTINEL = Path(__file__).parent.parent / ".restart"`), then sends `SIGTERM`. The manage-script restart loop detects the sentinel after uvicorn exits and re-launches the server. |

**Restart loop** — `Cmd-Start`/`cmd_start` in `manage.ps1`/`manage.sh` wrap the uvicorn call in a `while` loop. After uvicorn exits they check for `.restart`; if present they delete it and restart, otherwise they break. `Cmd-Dev`/`cmd_dev` have the same loop (bash uses a background subshell so the frontend Vite server can run concurrently). Stale `.restart` and `.shutdown` files left by a crash are deleted at the top of each start before the loop begins. The uvicorn call is written as `python -m uvicorn ... || true` in `manage.sh` so that `set -euo pipefail` does not abort the loop on a non-zero exit before the sentinel check runs.

**Terminal auto-close on shutdown** — after the restart loop exits (no `.restart` sentinel), `Cmd-Start` in `manage.ps1` checks for `.shutdown`. If found, it deletes the file and calls `exit 0`. `Crucible.bat` only runs `pause` when the PowerShell exit code is non-zero, so a clean shutdown closes the terminal window automatically while a crash keeps it open so the user can read the error output.

**Frontend restart flow** (`TopBar.tsx` `handleRestart`): (1) fetch `/api/v1/health` to record the current `start_time`; (2) POST `/api/v1/restart`; (3) poll `/api/v1/health` with `{ cache: "no-store" }` every second until the response carries a *different* `start_time` (confirming a new process, not the dying old one); (4) `window.location.reload()`. While this runs, a full-screen overlay shows the animated `CrucibleMark`. Both the restart and shutdown buttons are disabled while `restarting || shuttingDown`.

**The restart poll has no deadline, deliberately.** It previously gave up after 60 s and reset the UI "so the user can retry". That silently strands the page: a cold start importing torch can exceed 60 s, and a server not running under the restart loop (see above) needs a manual relaunch — in both cases the server comes back *after* the poll has stopped, so the page never reloads and looks hung. Polling now continues indefinitely; after `RESTART_SLOW_MS` (25 s) the overlay adds an explanation and a manual "Reload now" button rather than giving up. `restarting` is never reset to `false` — every exit from this state is a page load. Do not reintroduce a cutoff.

### Database

SQLite in WAL mode (`synchronous=NORMAL`). ORM models live in `backend/models/`. Alembic migrations in `backend/alembic/versions/`. The Alembic `env.py` strips `+aiosqlite` from the URL when running synchronous migrations.

**Per-connection pragmas / foreign-key enforcement**: `foreign_keys` and `synchronous` are *per-connection* SQLite settings (not persisted in the DB file), so they are applied in a `@event.listens_for(engine.sync_engine, "connect")` listener in `backend/database.py` that runs `PRAGMA foreign_keys=ON` and `PRAGMA synchronous=NORMAL` on every new DBAPI connection. `journal_mode=WAL` is persistent per-DB-file and stays a one-time `init_db()` call. **FK enforcement is ON**, so `ondelete` clauses actually fire: `images.dataset_id` → `CASCADE` (with `passive_deletes=True` on `Dataset.images`, so `delete_dataset` issues a single DELETE and the DB cascades images → `detections` also `CASCADE`); `videos.dataset_id` → `CASCADE` likewise (`passive_deletes=True` on `Dataset.videos`, mirroring `Dataset.images`); `background_jobs.dataset_id` → `SET NULL` (deleting a dataset keeps its job history, nulling the link); the versioning tables already cascade (`dataset_branches`/`dataset_versions`/`version_image_states` on `datasets`/`dataset_versions`). Of the intra-versioning links, only `dataset_versions.branch_id` has a real DB-level FK (`SET NULL`, created by migration `a2b3c4d5e6f7`); `dataset_versions.parent_id` and `dataset_branches.head_version_id` were created as **plain columns** in that migration (no FK), so their model-level `ForeignKey` declarations are decorative (the schema comes solely from Alembic, never `create_all`). Consequence: deleting a version leaves any children's `parent_id` dangling — harmless, it's informational only — and branch-head reassignment on delete is handled in code by `delete_version` (`backend/routers/versioning.py`), not by the DB. Migration `f7e8d9c0b1a2` purges pre-existing orphans and recreates the two enforced FKs (`images.dataset_id`, `background_jobs.dataset_id`; SQLite requires `batch_alter_table` table-recreates for FK changes). The Alembic migration engine keeps `foreign_keys` OFF (env.py doesn't enable it), which is required for batch recreates.

**Subfolders** (`Image.subfolder`, `Dataset.declared_subfolders`): images are physically flat in `{dataset.folder_path}/images/`; `subfolder` is pure string metadata (empty string = root/ungrouped; nested paths use `/`). `Dataset.declared_subfolders` (JSON column, default `[]`) stores explicitly-created subfolder paths so empty subfolders survive a `list_subfolders()` call — that function GROUP BYs images, so any path not in `declared_subfolders` with zero images would disappear. `declare_subfolder()` adds a path; `delete_subfolder()` bulk-moves images to root and removes the declared entry. `normalize_subfolder()` in `backend/utils.py` sanitizes path strings before storage. API: `GET/POST/DELETE /datasets/{id}/subfolders`.

Images-table indexes (spread across several migrations, all model-declared): from the initial migration (`5acbb04f2f10`) — `ix_images_dataset_id` on `dataset_id`, `ix_images_dataset_aesthetic` on `(dataset_id, aesthetic_score)`, `ix_images_dataset_blur` on `(dataset_id, blur_score)`, `ix_images_phash` on `phash`, and the `uq_dataset_filename` unique constraint on `(dataset_id, filename)`; from the performance-index migration (`a1b2c3d4e5f6`) — `ix_images_dataset_created_at` on `(dataset_id, created_at)` (gallery sort), `ix_images_file_path` on `file_path` (filesystem lookups), `ix_images_dataset_caption` on `(dataset_id, caption_text)` (caption filter + listing); plus `ix_images_dataset_similarity` on `(dataset_id, style_similarity_score)` (`bdd17cfef66d`), `ix_images_dataset_subfolder` on `(dataset_id, subfolder)` (`f3a9b2c1d4e7`), `ix_images_dataset_sort_order` on `(dataset_id, sort_order)` (`a3b4c5d6e7f8`), and `ix_images_dataset_caption_tokens` on `(dataset_id, caption_token_count)` (`d9f4a1c7b2e8`, the migration that also adds the persisted `caption_token_count` column and backfills it from existing captions — see CLAUDE.md § Shared utilities for the `caption_text` sync listener).

**Datetime serialization (UTC on the wire)**: all timestamp columns are stored **naive UTC** via `datetime.utcnow()`. A naive datetime serializes to JSON with *no* timezone suffix, which the frontend's `new Date(...)` then parses as *local* time — shifting every displayed timestamp by the browser's UTC offset (this was the "job ran 3h ago" bug). Fix: **every `datetime` field on an API response schema must use the `UtcDatetime` type** from `backend/schemas/__init__.py` (a `PlainSerializer` that attaches `+00:00`), never bare `datetime`. This makes the wire format unambiguously UTC. Applies to any new schema field or any router that hand-builds a response dict — route it through a schema with `UtcDatetime`, or attach UTC before `.isoformat()`. Exception: `filesystem.py`'s `modified_at` comes from `datetime.fromtimestamp(st_mtime)` (local naive) and is *intentionally* left naive so the file browser shows local file-modification times.

**Dataset-folder deletion & the startup orphan sweep**: deleting a dataset is DB-first — `delete_dataset` (`routers/datasets.py`) removes the row and commits, then removes the on-disk folder via `remove_dataset_dir(folder)` (`services/dataset_service.py`). That helper replaces the old `shutil.rmtree(..., ignore_errors=True)`: it uses `rmtree`'s error callback (with an `onexc`/`onerror` fallback so it works on Python ≥3.12 and older) to **log a warning** naming exactly what couldn't be removed, instead of silently swallowing a partial delete. Because folder cleanup is bolted onto the row-delete path, a folder is orphaned whenever a dataset row disappears by another route (DB reset/migration/swap, manual edit). `sweep_orphan_dataset_folders(db)` reconciles this at startup: the `lifespan` hook in `main.py` calls it (via `_sweep_orphan_dataset_folders`, right after `init_db()` and before `job_queue.start()`), and it removes every child directory of `settings.datasets_dir` whose resolved path is not referenced by any `Dataset.folder_path`, logging what it removed. It runs before any job starts, and folder import creates the DB row before populating the folder, so an unreferenced folder is genuinely orphaned — but the sweep does auto-delete without confirmation, so keep those two invariants (no in-flight jobs at startup; row-before-folder on create) if you touch that path. Both helpers no-op safely on a missing path.

**Deferred blob columns**: `clip_embedding`, `dino_embedding`, and `dino_layer_embeddings` are declared with `deferred=True` on their `mapped_column`. SQLAlchemy omits them from `SELECT *` queries — they are only fetched when explicitly accessed or when `undefer()` is passed as a load option. The `GET /images/{image_id}` endpoint undefers `dino_layer_embeddings` so the `has_dino_layer_embeddings` property on `ImageOut` works. Quality/similarity routers use column-explicit selects (`select(Image.id, Image.clip_embedding, ...)`) and are unaffected. Never access these columns from a full-row ORM load without adding `undefer()`.

### Migration drift check

`scripts/check_migrations.py` (run from anywhere with the venv active; CI runs it as the `migration-drift` job in `.github/workflows/backend-tests.yml`) upgrades a throwaway SQLite file to `head` and compares the result against `Base.metadata` with `alembic.autogenerate.compare_metadata`. It fails on more than one revision head, on an upgrade error, or on any diff not listed in its `ACCEPTED_DRIFT` set. Two implementation constraints are load-bearing: it must `os.chdir` into `backend/` (revision `d9f4a1c7b2e8` imports `backend.utils` at module scope, which only resolves after `env.py` fixes `sys.path`), and it sets `DATABASE_URL` before the first import so `config.settings` never points at the live DB — `env.py::get_url()` reads it lazily.

`ACCEPTED_DRIFT` holds 14 exact fingerprints, not a filter by diff *kind* — a kind filter would swallow the next real drift, which is the entire point of the check. They are the pre-existing, deliberate disagreements: eight `modify_nullable` (columns typed non-`Optional` on the model whose `CREATE TABLE` left them nullable), the two decorative self-referential FKs described above, and four indexes created by migration but never mirrored onto a model's `__table_args__`. A fingerprint that stops appearing is a WARN telling you to delete the line. Adding to the set to make a red check green is the wrong fix; the right one is a migration.

### Startup database backup

`services/db_maintenance.py::run_startup_maintenance_sync` runs `PRAGMA quick_check` on the SQLite file behind `settings.database_url`, then copies it to `<db dir>/backups/<stem>-<timestamp>-<nnn>.db`, keeping the newest `BACKUP_KEEP` (5). `main.py`'s lifespan fires it as a **detached task** after `job_queue.start()` (held in `_background_tasks` so it is not garbage-collected mid-run) and never awaits it — the work is seconds of disk I/O on a large database and nothing user-facing depends on it. Failures log and are never fatal.

Three details that exist for a reason: a failed integrity check **skips the backup** (rotating a corrupt copy in would age out the newest good one); the copy goes through sqlite3's backup API rather than a file copy, because the live DB has a WAL sidecar and copying the `.db` alone captures a torn state; and the filename carries milliseconds *and* an always-present zero-padded counter, because rotation orders copies by name and a bare `-{stamp}.db` sorts **after** its own `-{stamp}-001.db` (`-` precedes `.`), which would delete the newest copy. Request-level tests never reach this — `api_env` does not run the lifespan; e2e boots a fresh tiny DB, where it is a no-op-sized copy. User-facing behaviour is documented in `docs/workspace.md` (§ Database backups).

A fourth, added later: the run **returns immediately** when the newest backup is younger than `BACKUP_MIN_AGE_SECONDS` (15 min), checked *before* `quick_check` because that scan is most of the cost. `manage.sh dev` runs uvicorn with `--reload --reload-dir backend` and uvicorn re-runs the lifespan on every reload, so each backend file save was integrity-checking and copying the whole database — and five saves flushed the entire pre-session history out of a 5-slot rotation. The restart loop above has the same shape at lower frequency. Age comes from the newest backup's **mtime**, not its filename stamp; a future-dated file (clock skew) falls through and backs up, so skew can never wedge the guard permanently. Tests that drive the routine repeatedly must pin `BACKUP_MIN_AGE_SECONDS` to 0 — `test_db_maintenance.py` does this in the rotation and corrupt-database tests, which would otherwise pass without reaching the behaviour they name.

### SSE progress

`ProgressBroadcaster` (singleton in `workers/progress.py`) maintains per-job `asyncio.Queue`s. Emitting a progress event pushes to the job-specific channel and the `"all"` channel. A 25-second heartbeat keeps proxies from closing idle connections. Per-job streams (`GET /jobs/stream/{job_id}`) close when status becomes `completed`, `failed`, or `cancelled`. The global stream (`GET /jobs/stream/all/events`) uses `stop_on_terminal=False` and stays open for the session lifetime. All progress events include `dataset_id` (nullable for jobs with no associated dataset) and `label` (the job's display name, nullable — always taken directly from `job.label` on the in-memory `BackgroundJob` object).

### Job cancellation

`DELETE /jobs/{job_id}` calls `job_queue.request_cancel(job_id)`, which adds the id to an in-memory `set` on the single-process, single-worker `JobQueue`. Running loops poll this set cooperatively — no DB access from `ml/` modules.

- **Only a `pending` job gets `status="cancelled"` written at request time** — the worker's dequeue check reads that status to skip it, and nothing is running to report a different outcome. A **running** job's status is left alone and the worker writes the real final status when the job actually stops.
- **Why the running job's row is not marked terminal immediately**: cancellation is cooperative, so a running job keeps working until its next poll (for `comfy_prompts`, a whole LLM call — up to 120 s). Marking the row terminal at request time put a `cancelled` badge on the Logs page for a job still doing work, and was wrong outright when the job went on to finish what was asked. It also freed the "one job at a time" guards (`comfy_generate`/`comfy_prompts` per plan, `rescan` per dataset) while the old job was still writing.
- **Two check helpers**: `raise_if_cancelled(job_id)` raises `asyncio.CancelledError` (used by loops that commit per item or produce additive file output, where nothing needs preserving); `cancel_requested(job_id)` is a non-raising check (used by loops that `break` → commit partial progress → then `raise_if_cancelled` after the commit so the worker still marks the job `cancelled`).
- **Scope**: all per-item jobs are cancellable and **keep partial progress** (work finished before the stop is committed). A job cancelled while still queued is skipped by the worker before it starts. Snapshot, restore, and branch-checkout jobs are intentionally **not** cancellable (they must complete atomically to leave the version store consistent). The flag is cleared in the worker's `finally` block and in the pending-skip path.

### Stale job cleanup at startup

The queue is in-memory, so a shutdown/restart orphans any `running`/`pending` job rows — nothing will ever resume them, and they render as stuck-forever in the UI. `mark_interrupted_jobs()` (in `workers/job_queue.py`, called from the `lifespan` hook before `job_queue.start()`) marks them all `failed` with error "Interrupted by server shutdown or restart".

### Job retention sweep

`background_jobs` otherwise only grows — every captioning/export/detection/import run appends a row and nothing removes them. `sweep_old_jobs()` (`workers/job_queue.py`, called from `lifespan` immediately **after** `mark_interrupted_jobs()`, wrapped so a failure can't block startup) deletes rows that are `completed`/`failed`/`cancelled` **and** older than `JOB_RETENTION_DAYS` (30) **and** outside the newest `JOB_RETENTION_MIN_KEEP` (500) rows overall. The min-keep floor is a second `created_at` bound derived from an `OFFSET 499 LIMIT 1` query, so an install idle for a year still shows its last runs; ordering matters — the interrupted-jobs pass runs first so nothing eligible is still labelled `running`. Unfinished rows are never touched. Consumers are safe by construction: `routers/jobs.py` lists at most 500 newest, LogsPage requests 200, and the comfy duplicate-job guards query only `pending`/`running`. `BackgroundJob.created_at` is indexed (`ix_background_jobs_created_at`, migration `d8200045f01b`) for both the sweep's filter and the listing's `ORDER BY`. User-facing consequence — the 30-day Logs history horizon — is documented in `docs/workspace.md` (§ Logs).

### Per-image start events for slow jobs

`batch_upscale` and `batch_lut` emit a progress event (`"Upscaling {filename}…"` / `"Applying LUT to {filename}…"`, `done=i`) *before* each image is processed, not only after. On CPU-only machines (e.g. the dev container — no GPU) a single upscale can take minutes; without the pre-start event a small job sits at "Starting…" the whole time, looking hung. Note cancellation is cooperative and only checked between images, so cancelling mid-image doesn't interrupt the current upscale.
