# ML model lifecycle

This file covers the ML model lifecycle (loading, VRAM management, device abstraction), the model ID registry used by captioning and quality scoring, and the LaMa inpainter's download-and-verify loader.

The subsystems that consume these models have their own files: `docs/dev/detection.md` (object detection) and `docs/dev/scoring.md` (quality scorers and flags), the latter with `docs/dev/image-similarity.md` for duplicate detection and style similarity. The two image-processing pipelines that used to live at the bottom of this file — upscaling and LUT grading — are `docs/dev/image-processing-models.md`.

### ML model management

`ml/model_manager.py` is a singleton that tracks loaded models and their VRAM usage. Before loading a model it calls `_evict_lru(needed_mb)` to free space. Each model_id gets its own `asyncio.Lock` to serialize inference. All inference runs in `loop.run_in_executor(None, _sync_fn)` to avoid blocking the event loop. Ollama models are not tracked — Ollama manages its own VRAM.

After a successful load, `_registry[model_id]["vram_mb"]` is updated with the measured GPU delta so eviction decisions reflect reality.

**Explicit unload methods** — two public async methods allow callers to free VRAM on demand:

| Method | Effect |
|---|---|
| `await model_manager.unload(model_id)` | Acquires per-model lock, moves weights to CPU, deletes model + processor objects, removes entry, calls `torch.cuda.empty_cache()`. |
| `await model_manager.evict_all()` | Calls `unload()` for every registered model + final `cuda.empty_cache()`. Returns list of unloaded IDs. Used by `POST /api/v1/models/unload-all`. |

**`POST /api/v1/models/unload-all`** (router: `backend/routers/models.py`, prefix `/models`) — evicts all ML models from VRAM without restarting. Returns `{ "status": "ok", "unloaded": [model_id, ...] }`. Its docstring says to call it after quality scoring; **nothing does**, frontend or backend, and that is deliberate rather than an omission. Scoring frees its own models now, and it must free *only* its own — see below.

**Scoped unloads, by subsystem.** Two subsystems free VRAM without going through `evict_all`, each covering the models it loaded and nothing else:

| Caller | Scope |
|---|---|
| `DELETE /captioning/model/{id}/unload` | The one captioning model the page names. |
| `POST /quality/models/unload`, and the auto-unload in the `quality_score` job's `finally` | The four ids in `routers/quality.py::SCORING_MODEL_IDS`. Gated by the `auto_unload_after_scoring` setting for the job; the endpoint is unconditional. |

Prefer one of these over `evict_all()` in anything new: a scoring run that swept the registry would evict a Florence-2 or SAM2 someone loaded for other work. `evict_all` remains right for the caption *pipeline*, which is a multi-step job that owns the VRAM for its whole duration. See `docs/dev/scoring.md` § The model lifecycle.

`HF_TOKEN` is written into `os.environ` by `backend/services/secrets_service.py::sync_env`, its only writer, so every loader that passes no `token=` picks it up: early in `main.py` from the `.env`/OS-env chain, again in the lifespan from the DB, and on every `PATCH /settings/secrets`. A token saved in Settings → API Keys therefore applies to the next download with no restart — `huggingface_hub` re-reads the variable on every call. See `docs/dev/settings.md` § API Keys tab for the precedence rules.

Every registry entry also carries a `kind` (`"caption"` / `"score"` / `"detect"` / `"embed"`) and a `description`, both authored beside the loader that knows the repo id and the VRAM figure — `kind` is the model's *primary* role, singular, and `description` is the copy the pickers render verbatim. `GET /captioning/models` filters on `kind == "caption"`, so a new entry declaring the wrong one silently changes what the captioning picker offers; see `docs/dev/captioning.md` for that filter and the `_caption_backend` validator behind it.

**JoyCaption inference details** (`ml/joycaption_captioner.py`): Uses `LlavaForConditionalGeneration` with a system + user chat template via `processor.apply_chat_template`. After the processor call, `inputs["pixel_values"]` is explicitly cast to bfloat16 via `safe_dtype_for_device` — required by LLaVA's architecture. Generation uses `do_sample=True, temperature=0.6, top_p=0.9, max_new_tokens=512`. The four tag-producing styles (`danbooru`, `e621`, `rule34`, `booru_like`) are members of `_TAG_STYLES` in `routers/captioning.py` — the router splits their output on commas and stores individual tags, the same as WD14/booru output. Custom prompts override the style prompt entirely.

**`_TAG_STYLES`** (`backend/routers/captioning.py`): module-level `frozenset` containing all comma-separated-output styles: `{"tags", "booru", "danbooru", "e621", "rule34", "booru_like"}`. Both `_run()` and `_run_pipeline_job()` use this set to decide whether to split caption output into individual tags. Do not duplicate this set locally — import or reference it from the module.

**EXIF-consistent opening (mandatory for inference)**: every ML inference path must open images through `ml/image_utils.py::open_rgb(path)` — `Image.open().convert("RGB")` + `ImageOps.exif_transpose`. This guarantees all predictors (captioners, quality scorers, SAM2/SAM3, NudeNet) see pixels in the same EXIF-transposed frame, so normalized point/box coordinates denormalize consistently and detection overlays align with the subject on rotated images. Never open with a bare `Image.open(...)` in an inference path; `preprocess_for_caption` itself calls `open_rgb`. Close the returned image right after handing pixels to the model (per the "Close PIL Images after preprocessing" invariant).

The rule is now **enforced**, not just stated: `backend/tests/test_ml_image_opens.py` walks the AST of every module in its `INFERENCE_MODULES` list and fails on an `Image.open`/`PILImage.open` call. That list covered four scorer files while eight more inference paths shipped, and now names all twelve — the four scorers, `nudenet_scorer`, both SAM predictors and all five captioners; a companion test fails when a new `*_scorer`/`*_captioner`/`*_predictor` module is in neither it nor the annotated `NOT_INFERENCE` set, so the next one cannot ship unenforced. It exists because the rule was silently false for seven sites until 2026-07-30 — all four in `aesthetic_scorer.py`, both in `dino_scorer.py`, and `nsfw_scorer.py` — while this paragraph asserted it held everywhere. Nothing had broken, and the reason is worth knowing before trusting a green quality run: this app's images are overwhelmingly generated (PNG/WebP from ComfyUI), which carry no orientation tag, so the bug needs a folder import of phone photos to surface. What it produced there was an *inconsistency*, not a uniform error — `technical_scorer.py` reads through `cv2.imread`, which applies EXIF orientation itself, so on a rotated image the technical scores and the aesthetic/NSFW/DINO scores described pixels in two different orientations within one quality run.

`open_rgb_bytes(image_bytes)` is the in-memory twin, for callers that never touch disk. The pair exists so `extract_clip_embedding_sync` (path) and `extract_clip_embedding_from_bytes_sync` (bytes) cannot drift: both feed the same style-similarity comparison, so transposing in only one makes a reference image uploaded as bytes compare against stored embeddings in a different orientation — a subtler failure than the original, since both sides still return a well-formed normalized vector. Fix or add to one form, do the same to the other.

Two inference-adjacent sites deliberately stay outside `open_rgb`: `ml/lut_processor.py` and `ml/upscaler.py` transpose inline because they are image-*processing* paths that write their result to disk, governed by the `image_service._open_safe` half of the invariant rather than this one.

**Target resolution preprocessing**: `CaptionJobRequest` accepts optional `target_width` / `target_height`. When set, `ml/image_utils.py::preprocess_for_caption()` center-crops each image to the target aspect ratio and resizes it to the exact target resolution before inference. This ensures captions describe the composition the model will actually see at training time. All captioners (Florence-2, PaliGemma-2, JoyCaption, Ollama) call this utility; Ollama's existing `max_px` scale-down runs afterward on the already-cropped image. Omitting both fields leaves behavior unchanged.

**Config validation** (`backend/config.py`): `@model_validator(mode="after")` enforces at startup: (1) `max_vram_mb < 1000` → `ValueError` (fail fast); (2) an `hf_token` absent from the `.env`/OS-env chain → debug-level warning, worded to note it may still be set in Settings → API Keys, since the validator runs before any DB read and cannot see one saved there; (3) unrecognised `.env` keys → WARNING log; `extra="ignore"` retained so OS env vars are never flagged. `config.py` still declares `watermark_threshold` for legacy `.env` compatibility but the quality router reads all six flag thresholds (blur, noise, uniformity, watermark, duplicate, NSFW) from the `threshold_settings` DB table instead.

**TorchDynamo is disabled** (`TORCHDYNAMO_DISABLE=1` set in `main.py`). Triton is unavailable on Windows and single-image inference gains nothing from `torch.compile`, so it is disabled for the entire process. Do not remove this without re-testing all ML inference paths on Windows.

**Florence-2 PromptGen v2 compatibility patches** (in `_load_florence2_sync`, `ml/model_manager.py`): Two runtime patches are applied after loading `MiaoshouAI/Florence-2-large-PromptGen-v2.0` to fix breakage with `transformers >= 4.50`:
1. `_initialize_missing_keys` is temporarily replaced with a version that swallows `AttributeError` during `from_pretrained`, because the DaViT vision encoder doesn't implement `_initialize_weights` and newer transformers always calls the missing-keys hook after loading.
2. `GenerationMixin` is appended to `Florence2LanguageForConditionalGeneration.__bases__` (after `PreTrainedModel`, as the library requires) because `transformers >= 4.50` removed `GenerationMixin` from `PreTrainedModel`'s inheritance chain, leaving the sub-model's `.generate()` undefined. `generation_config` is then initialised via `GenerationConfig.from_model_config(model.language_model.config)` because it is not set on the sub-model instance. Do not remove either patch without verifying on `transformers >= 4.50`.

**Why V2.5 gets its own registry entry.** `aesthetic`'s `ModelEntry.model` is a three-tenant dict `{"clip", "mlp", "preprocess"}`, and only `mlp` is aesthetic-specific: `clip` + `preprocess` also serve zero-shot watermark scoring, CLIP-embedding extraction and the `POST /quality/embed-references` upload endpoint. Swapping the backbone under that entry would silently break three features that have nothing to do with aesthetics, so `aesthetic_v2_5` is a **separate** entry and both backbones may be resident during one run (~2000 + ~3500 MB, which no realistic setup evicts over). The existing entry is untouched: `_evict_lru(3500)`, its `vram_mb=3500` floor and its `"LAION Aesthetic Predictor"` registry row all stay exactly as they were.

**The two halves of V2.5 come from different places, and neither is `models_cache_dir`.** `convert_v2_5_from_siglip` pulls the SigLIP backbone from the hub in the ordinary way, but fetches the predictor head itself via `torch.hub.load_state_dict_from_url` from the project's GitHub — so it lands in the *torch hub* cache and no HF-cache probe can see it. The first-run SSE proxy therefore checks the backbone only, which is the download worth warning about anyway. That checkpoint's own filename is `aesthetic_predictor_v2_5.pth` — exactly the name LAION's MLP was stored under in `models_cache_dir` until this feature renamed it. The two never actually collided, because they live in different caches; the rename is insurance against any later change that writes the head by hand, plus a filename that stops lying.

`_load_aesthetic_v2_5_sync` returns the **plain** `ModelEntry(model, processor, vram_mb=max(2000, delta))`, not the dict shape. That used to matter for unloading and no longer does: `_evict_lru` and `unload` now both go through `model_manager._release_to_cpu`, which walks a dict entry's tenants instead of calling `.cpu()` on the dict itself. See § Releasing an entry's weights below for why "reclaimed by refcount anyway" was wrong. It passes **no `trust_remote_code=True`** despite the package README: SigLIP has been natively supported by `transformers` for many releases, so it buys nothing and is an arbitrary-code switch on a hub repo. `low_cpu_mem_usage=True` only. No `token=` either — like the other hub loaders it relies on the ambient `HF_TOKEN` that `services/secrets_service.py::sync_env` maintains. The 2000 MB floor is SigLIP-so400m's figure (~428M params in the vision tower), not CLIP's 3500.

**The VRAM budget setting is dead code, and has been.** `settings.max_vram_mb` never reaches `ModelManager`: `model_manager = ModelManager()` at the bottom of `model_manager.py` passes no argument, so `_evict_lru` compares against the class default of 20000 and the user's setting is inert. That is the defect — **not** that eviction never runs. It does: `_used_vram()` sums every resident entry, so JoyCaption's `_evict_lru(17000)` fires the moment anything else is loaded (with `aesthetic`'s 3500 resident, 3500 + 17000 > 20000), and this branch's fifth resident model makes it more reachable still. One latent bug sits behind that and a fix has to handle it: `entry.in_use` is never set `True` anywhere, so eviction is free to select a model a running job is mid-way through using. (The second — the dict-shaped `.cpu()` that skipped the move to host memory — is fixed; see § Releasing an entry's weights.) It has not bitten because `workers/job_queue.py` runs a **single** worker task — jobs are serialized, so the evicted model is never one another running job holds; it is latent because of that serialization, not because eviction is dormant. Wiring the setting through is **its own branch** — it changes the ceiling for the first time, and doing that without those two fixes trades a user-visible knob for a live crash.

### The LaMa inpainter

`lama` is the registry's one `kind: "edit"` entry — a model that rewrites pixels rather than describing them. None of `caption`/`score`/`embed`/`detect` is honest for an inpainter, and a new *value* costs nothing: `kind == "caption"` in `routers/captioning.py::list_models` is its only behavioural reader, so every other value is inert there. Do not read that as licence to generalise `kind` into a capability *set* — that still needs a second reader. `backend/tests/test_captioning_model_registry.py` partitions the registry in both directions, so a fourteenth model lands in neither set and fails there.

**TorchScript, not a package and not a state_dict, and the reasons are all environmental.** `simple-lama-inpainting` pins `Pillow>=9.5,<10` and `numpy<2.0` against this repo's Pillow 12 / numpy 2; `IOPaint` pins `fastapi==0.108.0`, `Pillow==9.5.0` and gradio. Installing either would wreck the venv. The HuggingFace `anyisalin/big-lama` mirror is a 473 MB bare state_dict that would require vendoring LaMa's FFC ResNet generator — ~400 lines this repo would then own forever. The TorchScript archive carries its own architecture, so `torch.jit.load` plus `lama_inpainter`'s ~60 lines of pre/post-processing is the entire inference path, which is exactly what `simple-lama` does internally. **No new pip dependency was added.**

**The weights are a pickle, and the SHA-256 pin is what makes that acceptable.** `_WEIGHTS_SHA256` is checked after every download *and* on every load of a cached file; a mismatch deletes the file and refuses, rather than warning. The SAM 3 loader's "safetensors only, never `.pt`" rule is stated in `sam3_predictor.py`'s own docstring and is SAM-3-specific, not repo-wide — `scan_upscale_models` already globs and loads arbitrary `*.pth` through spandrel with no verification at all, so a hash-pinned archive is strictly the more verified of the two. LaMa's code is Apache-2.0 (`advimman/lama`); the weights are Places2-trained and distributed through community mirrors.

**`_ensure_weights` is a plain GET, so `progress_tqdm_patch` does not apply.** That helper monkeypatches `huggingface_hub`'s tqdm and there is no hub call here; the byte loop calls `emit_sync(job_id, loop, msg, pct, dataset_id)` directly instead, roughly every 4 MB. It downloads to a `.part` file and `replace()`s only after the hash verifies, so an interrupted first run leaves nothing a later load would trust. `_load_lama_sync` resolves and verifies the weights **before** touching the accelerator — fail fast, no VRAM spent — and carries the same failure tail every loader here does: `.cpu()` → `del` → `_device.empty_cache()` → `raise`. `vram_mb` is `max(2000, measured delta)`.

**`torch` is imported inside the functions, never at module scope**, for the same reason `device.py` does it: `routers/inpaint.py` imports `inpaint_image_sync` at module import and `main.py` imports that router, so a module-level torch import would put torch on the `from backend.main import app` path and take down collection of the whole backend suite in CI. `backend/tests/test_inpaint_http.py` runs torch-free because of it.

**Inference is crop-and-composite, not whole-image.** `inpaint_image_sync` takes the mask's bounding box, expands it generously, snaps the span to a multiple of 8 (LaMa's stride) and runs the model on that crop alone, downscaling above 1536 px. This bounds VRAM independently of the source resolution — a fully-convolutional model on a 4K image otherwise blows up — and improves the fill, since LaMa was trained at 512². The painted crop is then composited back **through the mask**, so every pixel outside it is bit-identical to the source rather than making a round trip through the model. The image opens through `image_utils.open_rgb`, never a bare `Image.open`: detection polygons are normalized against the EXIF-transposed frame, so any other open misplaces the mask.

**It returns `phash`, unlike `upscale_image_sync`.** Inpainting changes pixels without changing geometry, and `phash` is the only thing duplicate detection keys on, so a stale one is the entire failure mode. Follow `crop_image_to_dest`, not the upscaler. The `normalize_image_format` PNG fallback applies here as everywhere: `out_path` is the path actually written and every caller must follow it (PM-009).

### Releasing an entry's weights

**`unload` and `_evict_lru` free an entry through `_release_to_cpu`, because `ModelEntry.model` is not always a module.** Two loaders store a **dict** of tenants — `aesthetic`'s `{"clip", "mlp", "preprocess"}` and `nsfw`'s `{"model", "processor", "nsfw_idx"}` — so the `entry.model.cpu()` both call sites used to do raised `AttributeError` on the dict, straight into a swallowing `except`. `_release_to_cpu` walks a dict's values and tries each independently (a dict entry mixes weights with a transform and an int, neither of which has `.cpu()`, and one of those must not abort the loop), and passes a plain entry through unchanged.

**"The `del` + `empty_cache()` reclaim it anyway" was the wrong model, and it shipped a leak.** That reasoning holds only when the `del` drops the *last* reference before the flush runs, and an unload cannot know that it does. The `quality_score` job binds `handle = entry.model` — a second reference to `aesthetic`'s dict — and its `finally` runs the auto-unload while that local is still live. So `del entry.model` dropped one reference of two, `empty_cache()` had nothing to hand back, and the frame died a moment later with no second flush to follow: ~3.5 GB stayed with the process until it exited. The fix is both ends. `_release_to_cpu` moves the weights regardless of who else holds them, and `_run` clears `handle`/`entry`/`dino_entry`/`nsfw_entry` before awaiting the unloads so the flush has nothing live to skip.

**Test this at the entry shape, not at the id.** `backend/tests/test_quality_model_unload.py` originally monkeypatched `unload` itself and asserted on the ids it received, which is why the leak passed CI: the ids were right and nothing was freed. The three cases added with the fix drive the **real** `unload` over a dict-shaped entry of fakes and assert each tenant was moved — including one end-to-end through the scoring job. A stub of the function under test cannot see this class of bug.

**ML device abstraction** (`backend/ml/device.py`): centralises all device-detection and device-aware utilities. Every module under `backend/ml/` that touches the GPU imports from here — ten of them, plus `routers/captioning.py` and `routers/detection.py`. Five direct `torch.cuda.*` calls survive on purpose and are the exceptions to look for: `torch.cuda.OutOfMemoryError` in an `except` clause in `florence_captioner.py` (twice), `paligemma_captioner.py` and `joycaption_captioner.py`, and `torch.cuda.is_available()` behind sam3's pin-memory probe. Routing those through `is_oom_error()` / a device-level availability check is the tidy-up; until then, "nothing else calls `torch.cuda.*`" is an aspiration rather than a fact. Detection priority: `cuda` (NVIDIA or ROCm, identical API) → `mps` (Apple Silicon) → `cpu`. Key helpers: `get_device()`, `empty_cache()`, `memory_allocated_bytes()`, `memory_reserved_mb()`, `autocast_ctx()`, `safe_dtype_for_device()`, `is_oom_error()`. **`torch` is imported inside each function, never at module scope** — this is the one module the router import chain reaches (`routers/captioning.py` → `model_manager.py` → here), so a module-level import makes `from backend.main import app` require torch, which took down collection of the entire backend suite in CI. Don't "tidy" the per-function imports back to the top; the docstring explains it.
