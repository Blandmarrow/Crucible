# The captioning model picker

This file covers which models a captioning picker offers and which ids a caption request accepts: the registry's `kind`/`description` fields, the `GET /captioning/models` filter, the `_caption_backend` validator that turns an unknown id into a 422, the four surfaces that render the one query, and the two frontend predicates over a model id. Where `kind` is declared per model is `docs/dev/model-registry.md`; what a job does once its model passes is `docs/dev/captioning.md`; the `openai_compat:` providers the list includes are `docs/dev/llm-providers.md`.

## The registry owns what a model is

Each entry of `model_manager.list_models()` carries a `kind` (`"caption"` / `"score"` / `"detect"` / `"embed"` / `"edit"`) and a `description` that the pickers render verbatim. Both live beside the loader that knows the repo id and the VRAM figure, because the alternative — model copy authored in the frontend — is what drifted: a two-way ternary in `CaptioningPage` gave Florence-2 one blurb and *everything else* PaliGemma-2's `"Google · requires HF token"`, so JoyCaption (`fancyfeast/llama-joycaption-*-hf-llava`, ungated) claimed to be Google's and to need a token. Only PaliGemma-2's description mentions gating, deliberately: every other loader merely passes the ambient `HF_TOKEN` along (`docs/dev/ml-models.md`) and needs no token, so "ungated" on the rest would be noise. `wd14_tagger.py::_VARIANTS` carries a `description` too, but no `kind` — those arrive in their own `wd14_models` array, every one is a captioner by construction, and the field would have no reader.

`kind` is singular, the model's *primary* role: `florence2_large` is `"caption"` even though detection also drives it, because detection's model list is frontend constants (`constants/detectionModels.ts`) that read nothing from here. A multi-valued capability set would be a field with no second reader.

## Two mechanisms, both required

`GET /captioning/models` filters `local_models` to `kind == "caption"`, on the registry's own field rather than an id allowlist in the router — an allowlist would be a second list of model ids to drift from the registry, which is the failure this exists to kill. The filter alone is not the fix, though. Selecting a non-captioner was a **silent no-op**: both per-image loops are `if/elif` chains on id prefixes over a `caption = ""` starting value, so an id matching no branch fell through, failed the `if caption:` save, and finished the job green claiming every image processed and zero failures. A stale `CAPTION_DEFAULT_MODEL_KEY`, a saved workflow blob or a direct API call all still reach the endpoint, so `_caption_backend(model) -> str | None` is now the dispatch chains' single source of truth, enforced by a `@field_validator("model")` on `CaptionJobRequest` **and** on `PipelineStep` (on the step, not the request, so every step is covered for free). An unrecognised id is a 422 with no `BackgroundJob` row. The `else: raise RuntimeError` in each loop is unreachable behind that validator; it is there so a *future* prefix mistake becomes a per-image failure with a traceback instead of a green empty job. `backend/tests/test_captioning_model_registry.py` partitions the registry into `CAPTIONERS`/`NOT_CAPTIONERS` and checks both directions, so a thirteenth model fails CI rather than appearing in the picker.

## Four surfaces read the one query

`CaptioningPage` and `SelectionToolbar`'s Caption modal render the description as a line under the name; `ImageDetailPage` takes it as `title=` instead — that sidebar is already `text-xs` and scrolls, so a second line per model is a regression for one-off recaptioning. `SettingsPage`'s Default-model `<select>` shows names only, and *blanks* on a saved default the endpoint no longer offers — derived during render, so no `setState` in an effect, and deliberately with no `localStorage.removeItem` behind it. The offered list is empty for a whole group whenever that service is merely unavailable (the backend swallows a dead Ollama daemon and returns `[]`) or its query has yet to resolve (`providers` is a separate query defaulting to `[]`; see `docs/dev/llm-providers.md`), so a delete would destroy a good `ollama:llava` or `openai_compat:{id}` preference, permanently and with no toast, on a transient outage. A blank `<select>` recovers on the next render; the delete does not.

## Two predicates over a model id, deliberately not the same one

`captionBackend` in `frontend/src/constants/captionModels.ts` hand-mirrors `_caption_backend` — the same six prefixes in the same order — and answers *will the validator 422 this*. The Run / Start Captioning / Generate Caption buttons on `CaptioningPage`, `SelectionToolbar` and `ImageDetailPage` are disabled on it, naming the offending step: a pipeline is one request, so a stale step 3 stops step 1 from running and the error names no step. Membership in the offered list (`captionModelOptions`, lifted into that same file from `SettingsPage`) is the *other* predicate and never blocks — it produces an informational note only, for the reason above. Reusing `modelType` (`constants/captionStyles.ts`) for either is the trap: it returns null for the perfectly runnable `wd14:` and `openai_compat:`, which have no `STYLE_LABELS` vocabulary, so gating on it disables the two most-used backends. `test_captioning_model_registry.py` parses `captionBackend` out of the TypeScript and evaluates it against the real function over every registry id, every wd14 id and the runtime-constructed forms; `frontend/e2e/captioning-run-gate.spec.ts` covers the gate itself, its wd14 negative control being the regression test for that trap.

## The three pickers are deliberately not one component

The three pickers are deliberately **not** one component. They share *shape*, not markup: `.mr-desc` exists only in `CaptioningPage` and `QualityPage`, while the other two are hand-rolled Tailwind at different densities (`p-2.5 text-sm` vs `p-2 text-xs`). A shared component would need ~8 props plus two style variants and would drag two surfaces onto a third's visual language. The drift being fixed was in the data, and the data is now shared — one query key feeds all four.
