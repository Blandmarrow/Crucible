# Caption jobs

This file covers what a caption job does with a model's output: the post-processing and merge fields on `CaptionJobRequest` and `PipelineStep`, job execution and its durable failure reporting (timeouts, empty captions, `result_data`), the `has_ai_artifacts` flag, tag-producing styles, job queuing, requests in flight (several remote requests at once), the Ollama timeout, which job the CaptioningPage panel binds to, and keeping sidecar writes off the event loop. Which models a request may name is `docs/dev/caption-model-picker.md`; the `openai_compat:` provider rows and their client are `docs/dev/llm-providers.md`.

### Captioning post-processing

`CaptionJobRequest` (in `backend/routers/captioning.py`) accepts the following fields for post-processing, merging, and job display:

| Field | Default | Effect |
|---|---|---|
| `label` | `null` | Optional display name shown in the job queue. When omitted, the router auto-generates `"{model_short} — N images"`. |
| `delimiter_mode` | `"overwrite"` | How to merge new caption with existing: `"overwrite"` replaces, `"append"` adds new text after (`existing + delimiter + new`), `"prepend"` adds new text before (`new + delimiter + existing`). Merge only runs when an existing caption is non-empty; images with no prior caption always receive just the new caption regardless of mode. |
| `delimiter` | `", "` | Text inserted between the two strings when `delimiter_mode` is `"append"` or `"prepend"`. |
| `strip_refusals` | `true` | Remove common AI refusal phrases from generated captions via `_REFUSAL_RE` compiled regex. The regex is narrowly scoped: `"This image appears to be X"` (Florence-2 PromptGen v2 standard output) is NOT stripped; only actual refusal phrasing like `"be depicting"` is matched. |
| `strip_thinking` | `false` | Strips `<think>…</think>` / `<thinking>…</thinking>` blocks and a first-line thinking preamble ("Let me think/analyze…", "I'll describe…", "Alright, let's…"). Thinking is **detected regardless** of this flag — a match always writes `has_ai_artifacts` to `quality_flags`. |
| `strip_underscores` | `false` | `word_word` → `word word` (`(?<=\w)_(?=\w)`). Prose styles: applied to the whole text. Tag styles (`_TAG_STYLES`): applied per-tag before rejoining with `, `. |
| `strip_hedges` | `false` | Strips sentence-level hedging prefixes ("It appears that…", "Possibly,…", "Looking at this image,…"), re-capitalising the remainder. Hedges are **detected regardless** — a match always sets `has_ai_artifacts`. |
| `dedupe_tags` | `false` | Tag styles only. Drops any freshly generated tag that is a whole-word subsequence of a longer tag in the same list (`tail` when `long tail` present; `shirt` when `white shirt` present) and collapses case-insensitive exact duplicates, via `subsume_tags()` in `backend/utils.py`. Applied to `new_tags` **before** the append-merge, so existing/prev tags merged in afterwards are untouched (mirrors `strip_underscores`). No-op for prose styles. (`PipelineStep.dedupe_tags` defaults `false`.) |
| `min_aesthetic_score` | `null` | Pre-filter applied in the initial DB query: only caption images with `aesthetic_score ≥` this value. `null` = no filter. |
| `exclude_flags` | `null` | Pre-filter: skip images with any of the listed quality flags set truthy; validated against `ALLOWED_FLAG_KEYS` via a `field_validator`. |
| `append_tags` | `true` | Tag styles only. When `delimiter_mode != "overwrite"`, new tags are deduplicated against the existing comma-separated `caption_text` (new tags win; remaining existing tags are appended). `false` = no merge. (`PipelineStep.append_tags` defaults `false` and merges against `prev_captions`.) |
| `save_backup` | `false` | Before calling `set_caption`, write the existing `.txt` sidecar to `.txt.bak`. |
| `rename_on_caption` | `false` | After saving each caption, rename the image file to `{subfolder_slug}_{NNN}.ext` (or `image_{NNN}.ext` for root). Sets `is_auto_named=True`. Subfolder and original filename are fetched from the initial bulk query — no per-image DB round-trip. |
| `wd14_threshold` | `0.35` | Minimum confidence (0–1) for a WD14 tag to be included in output. Only used when `model` starts with `wd14:`. |

`PipelineStep` has its own `delimiter_mode`, `delimiter`, `strip_refusals`, `strip_thinking`, `strip_underscores`, `strip_hedges`, `target_width`, `target_height`, and `wd14_threshold` fields — all configurable per step in the UI. `save_backup` and `rename_on_caption` live on `CaptionPipelineRequest` (pipeline-wide, not per-step). `prev_captions` is fetched from the DB at the start of each pipeline step when `delimiter_mode != "overwrite"` so the merge has the current caption text. When `delimiter_mode == "overwrite"` and `body.overwrite` is `False`, only images with empty captions are queued; append/prepend modes always process all images (the merge requires the existing caption).

### Captioning job execution

`_run` in `routers/captioning.py` sends each image's request (up to N at once for a remote captioner, see § Requests in flight), then saves it and emits SSE one image at a time, in input order.

- **Progress and failures**: each event carries `image_id`, `throughput_ips`, and `vram_used_mb` (sampled every 10 images; Ollama always 0; WD14 and OpenAI-compat always 0). Failed images accumulate in `failed_image_ids`; a `caption_summary` SSE event is emitted after the loop if any failed. Both loops catch `openai.APITimeoutError` in a branch **ahead** of the broad `except Exception`, logging the provider's name and its configured `timeout_s` (`docs/dev/llm-providers.md` § Model) instead of a bare traceback — the image still fails, only the diagnosis changes, and a provider that hung up mid-generation is what a bare traceback made read as "nothing happened". The import is guarded with a no-op subclass fallback, since `openai` ships in `requirements.txt` but not in `requirements-ci.txt`. The client is built with an explicit `max_retries=0` — the SDK's default is 2 and it retries timeouts, which made one image cost up to 3 × `timeout_s` and the configured number a lie. Cancellation is checked before each new request via `job_queue.cancel_requested(job_id)` (an in-memory set check, in both `_run` and `_run_pipeline_job`); see `docs/dev/backend-infrastructure.md` § Job cancellation. Because that poll is the only one, **Stop waits out the requests in flight** — up to N that started together, so about one `timeout_s` now that retries are off (§ Requests in flight).
- **A partial failure is durable, not just an SSE event.** A run that loses images still *returns*, so `job_queue.py` marks the row `completed` with `error_msg` unset and the Logs page would show it green — `logger.error` reaches uvicorn's stdout and nothing else. Both tails therefore write `BackgroundJob.result_data` (only when something failed; a clean job's row stays `{}`) in the same `AsyncSessionLocal()` block that calls `refresh_stats`, **before** that call and with its own explicit `commit()` — `refresh_stats` committing internally is an implementation detail of `dataset_service`. The shape follows the import-summary convention: `{failed_count, timed_out, rate_limited, empty, stripped, failure_summary, failed: [{file, error}]}`, capped at `_MAX_FAILED_DETAILS = 50` entries (a restated twin of the constant in `dataset_service.py`, not an import of a private name).
  - **`failure_summary`** comes from `_failure_headline(timed_out, timeout_provider, empty, stripped, empty_provider)`, which composes one sentence per **non-zero** tally and joins them with a space — the three are independent, so one run can time some images out, get nothing back for others and post-process a third group down to nothing. It returns `None` only when all three are zero, so a run with no diagnosis keeps the badge's generic wording. The `empty` sentence appends "Raise Max tokens in Settings → LLM Providers." **only when `empty_provider is not None`**: a local Florence-2/WD14 run has no such setting, and the advice would be noise. The same string rides the `caption_summary` SSE event as a field of the same name.
  - **The two provider arguments are separate because `/pipeline`'s `openai_provider` is a *step* variable**, reset to `None` at the top of every step, so by the tail it holds the **last** step's — which is nobody's diagnosis. Passing it for both sentences dropped the Max-tokens advice from a `[LM Studio, WD14]` pipeline (the empties earned it; the last step reset the variable) and attached it to `[WD14, LM Studio]`, where it named a setting irrelevant to a threshold problem. `/pipeline` therefore keeps `timeout_provider` and `empty_provider` beside the tallies, each set **once**, at the step that actually recorded that kind of failure — the timeout in its `except APITimeoutError` branch, the empty inside `_record_empty`, which reads `is_openai_compat`/`openai_provider` off the enclosing step exactly as its log line reads `step_idx`. `/run` has one model for the whole run and passes the same object for both. `empty_provider` defaults to `None`, so a caller that forgets it understates the diagnosis rather than inventing a setting the run does not have; a side effect is that the tail no longer reads a loop variable at all, so a zero-step pipeline reaches it without a `NameError`.

  **Known gap**: a *cancelled* run reaches neither tail (`raise_if_cancelled` propagates out), so it writes no `result_data` and emits no summary — already true of the SSE event before this. Surviving cancellation needs a `try/finally` around each loop.
- **`/run` writes `done_items` after every call, and it is a count of calls made** (M9 stage 10, PM-037). Right after the per-image `try/except`, the loop runs a core `UPDATE background_jobs SET done_items = i + 1` on its own session and commits. An automated run's paid-call cap sums that column over its caption children (`docs/dev/comfyui/run-budgets.md` § Who writes the paid-call counts), so three things about the write are load-bearing. It runs **whatever the call returned**: a failed call was still billed. It sits **before** post-processing and `set_caption`, which are outside the `try`, so a save that fails the whole job keeps the call. And it is **committed per image**, so a cancelled, failed or interrupted job keeps every call before it; the cancelled job that writes no `result_data` above still has its count, and a failed or hard-cancelled one also counts its requests in flight (§ Requests in flight). The value is the `done` the progress event carries a few lines later, which keeps the row and the event one unit (`docs/dev/job-invalidation.md`, PM-008); the row leads the event by the length of the save. The write is outside the per-image `try`, like `set_caption`, so a database error there fails the job. It is one more commit per image for every model, local ones included. `/pipeline` does not write it: a run never starts a pipeline job, and its counter is image × step.
- **An empty caption is a counted failure, not a silent skip.** Both loops used to guard the save with a bare `if caption:`, so an image that produced no caption text fell through with no exception: no tally, no log, no `.txt` sidecar, job green (issue #94). It is the same silent no-op `_caption_backend`'s docstring describes for an unmatched model id (`docs/dev/caption-model-picker.md` § Two mechanisms, both required), closed there by a request validator and left open here for an empty *response*. Each loop now carries a `_record_empty(img_id, file_path, reason, *, stripped=False)` closure beside the accumulators — one per loop rather than a module-level helper, because `/run` collects ids in a list and `/pipeline` in a set — which puts the image on the same `failed_image_ids` → `caption_summary` → `result_data` path as a timeout. Three reasons, guarded at three different points and applied identically in both loops (the file's "See the matching branch in /run's loop" convention, not a shared helper):
  - **A — nothing came back.** Checked right after the try/except, gated on a per-image `errored` flag both `except` branches set, so an already-counted exception is not counted again as an empty. The reason names the backend: WD14 gets "no tags above the confidence threshold" (the honest diagnosis when the threshold ate everything), Ollama gets a request-returned-nothing wording because `ollama_captioner.caption_image` swallows its own exceptions and hands back `""` — that outage was silent too — and everything else gets "provider returned an empty caption".
  - **B — the reply was entirely a refusal**, removed by `_strip_refusals`. An `else:` on the inner `if caption:`.
  - **C — post-processing removed everything** (thinking/hedge stripping, or a tag join that produced no tags). Guarded **after** the tag join and **before** the delimiter merge, which is what makes it a bug fix rather than a counted skip: the old code reached `set_caption(…, "")`, **blanking an existing caption and writing an empty `.txt` sidecar** over a good one, and with `delimiter_mode == "append"` wrote `"existing, "`. Skipping the write leaves both untouched. B and C count under `stripped`; A counts under `empty`.

  `backend/tests/test_caption_empty_guard.py` pins all of this at request level, with `backend.ml.openai_compat_captioner.caption_image` monkeypatched (the router imports that name *inside* the loop, so patching the module attribute reaches it) — torch-free, so it runs in CI with no new gate.
- **`has_ai_artifacts` is written** to `quality_flags` whenever `_has_thinking()` or `_has_hedges()` matches the generated caption, **regardless** of whether `strip_thinking` / `strip_hedges` are enabled (stripping is independent of detection); `strip_refusals` does **not** set this flag. The flag flows through `set_caption(..., has_ai_artifacts=)`.
- **Flag lifecycle**: because `has_ai_artifacts` describes cruft *in the caption text*, emptying the caption must clear it — an empty caption can't contain artifacts. This is enforced by `_maybe_clear_ai_artifact(img, caption_text)` in `caption_service.py`, which sets the flag to `False` (matching the quality-router convention of setting flags false rather than deleting the key) only when it is currently set and the new caption is empty/whitespace, copying the JSON dict before mutating (per the never-mutate-in-place invariant). **Call it in every caption-write path that can produce an empty caption** — it already runs in `set_caption` (manual editor + captioning save) and in the bulk paths (`bulk_edit_captions`, `find_replace_captions`); see `docs/dev/bulk-ops.md` § Bulk caption editing.
- **Tag-producing styles** (WD14, booru-style outputs, and the four JoyCaption tag styles) produce comma-separated text stored directly in `caption_text` — there is no longer a separate tags table. The `_TAG_STYLES` frozenset in `routers/captioning.py` identifies them; see `docs/dev/model-registry.md` § JoyCaption and tag styles for the definition and JoyCaption tag-style details.

### Requests in flight

M10 T2. Both loops send a remote captioner up to N requests at once, and still finish each image serially, in input order.

- **The split.** Each image's work is a *call*, the captioner request in an inner `_call(item)` that holds the dispatch chain, and a *finish*: the `done_items` write, the empty, refusal, thinking and hedge handling, the tag merge, `_backup_sidecar`, `set_caption`, rename-on-caption and the progress event. `utils.InOrderCalls` runs the calls as asyncio tasks, at most N at once, and hands the results back oldest first. The finish runs in the `async for` body on the loop's one session. Because finishing stays in input order, `done_items = i + 1` stays monotonic and equal to the event's `done`, and rename-on-caption picks the same names as a serial loop: its shared name sets are touched only in the finish.
- **N.** For `openai_compat:` it is the provider's `max_concurrent` (`docs/dev/llm-providers.md` § Model). For `ollama:` it is `ThresholdSettings.ollama_max_concurrent`, read once per job or pipeline step. Every local backend gets 1: Florence-2, PaliGemma and JoyCaption share the one GPU thread anyway, and WD14 stays as it was. `_clamp_bound` keeps it within 1 to `MAX_CONCURRENT_REQUESTS = 16` (`schemas/openai_provider.py`). N=1 is the old loop exactly, because `InOrderCalls` starts a call only when the loop asks for the next result: call k+1 starts after image k's finish.
- **One client per job.** `_open_remote_client` builds the job's client, one per step in `/pipeline`, on an `AsyncExitStack` that closes it after the calls have drained or been cancelled. It is an `AsyncOpenAI` from `openai_compat_captioner.make_client`, or Ollama's `httpx.AsyncClient` from `ollama_captioner.make_client`. The OpenAI request is async now, so a hard cancel aborts it instead of leaving an executor thread on the socket (checked by hand on SDK 3.41: the cancel propagates, unwrapped). The image encode stays on the default pool.
- **Stop.** The loop no longer calls `raise_if_cancelled` at the top of each image. `InOrderCalls` checks the flag before each new request and sends nothing more once it is set. The requests already in flight still come back through the finish, so they are saved and counted; only then does `if calls.stopped: job_queue.raise_if_cancelled(job_id)` end the job `cancelled`. A Stop that lands after the last image's request was sent leaves the job `completed`, as before; at N above 1 that window covers up to the last N requests.
- **A failed or hard-cancelled job counts what it sent.** When a save fails the job, or shutdown's forced cancel lands, up to N−1 requests are in flight past the last `done_items` write. `/run`'s `except BaseException` around the loop calls `_record_calls_started(job_id, calls.started)` from a fresh session, raising the count to every request started and never lowering it, so the paid-call cap does not under-count them ([decision 16](decisions/16-concurrent-caption-requests.md)). The row can then lead the last progress event by up to N. Only a process death leaves calls uncounted: at most N.
- **HTTP 429.** A failure whose `status_code` is 429 (read like `prompt_generator._status`, so a test's stand-in exception works without the SDK) counts in a `rate_limited` tally. `_failure_headline`'s keyword-only `rate_limited` and `rate_limit_provider` add a sentence telling the user to lower Max concurrent requests. There is no retry: PM-023's `max_retries=0` stands. `/pipeline` names the first step's provider that hit it, as it does for `timeout_provider`. Ollama cannot reach either tally: `ollama_captioner.caption_image` turns every failure into `""`, so at N above 1 its empty reason gains `_OLLAMA_QUEUED_HINT`, saying a queued request may have timed out.
- **Measured** on 2026-11-12 against Gemini 2.5 Flash's free tier through its OpenAI-compatible endpoint, 6 small images, style `short`: 20.5 s at N=1 and 8.7 s at N=3 (2.4×), each caption on its own image. A Stop sent just after the start at N=3 ended `cancelled` with the 3 requests in flight saved and `done_items = 3`. On LM Studio with `google/gemma-4-e4b` loaded on first use, 16 images of 512 px took 29.8 s at N=1, 20.7 s at N=2, 16.2 s at N=4 (1.8×) and 16.6 s at N=8: the gain stops at the server's parallel slots, and requests above them only queue. A one-slot Strata server took 11.2 s for 8 images at N=1, 8.8 s at N=2 and 9.8 s at N=4: its log shows it still served one request at a time, so N=2 only fills the gap between requests. Requests reach the server in the order their encodes finish, so the first image can be served last; the captions are still saved in input order. The free tier then refused Gemini bursts: 9 of 16 images at N=8, and later every request once the quota was spent. Each refusal was a `RateLimitError` counted under `rate_limited`, the job ended `completed` with the 429 headline, and nothing else failed.

`backend/tests/test_in_order_calls.py` pins the helper and `backend/tests/test_caption_concurrency.py` the two loops.

### Job queuing

The backend `asyncio.Queue` in `workers/job_queue.py` runs caption and pipeline jobs serially — any number of jobs may be submitted while one is running. `enqueue()` emits a `"pending"` SSE event immediately after putting the job on the queue (before the worker picks it up), so the frontend knows the job exists right away. The worker checks the DB status after dequeuing; if a job was cancelled while pending it emits a `"cancelled"` SSE event and skips without running. The cancel endpoint (`DELETE /jobs/{id}`) accepts both `"running"` and `"pending"` status, and also calls `job_queue.request_cancel(job_id)` so a *running* caption/pipeline job sends no new request and stops once the ones in flight are saved (see `docs/dev/backend-infrastructure.md` § Job cancellation).

### Which job the CaptioningPage panel shows

The frontend tracks all submitted job IDs in `submittedJobIds: string[]`; `submittedActiveJobId` is the oldest non-terminal entry (gated only by `seenTerminalJobIds` ref, not live store status, to avoid the effectiveJobId race where the gallery invalidation never fires) — and **falls back to the most recently submitted id when every entry is terminal**, which is what keeps the panel bound long enough to render its own Done state. Without that fallback `effectiveJobId` went null on the first re-render after completion (the terminal effect mutates a ref, so the drop landed on whatever render its `invalidateQueries` triggered), the panel unmounted back to "Run captioning to see progress here", and both the "✓ Captioning complete" line and the amber failed-images badge were unreachable — confirmed with a `MutationObserver` over the whole run, not just by polling. Starting another job puts a non-terminal id back at the front of the `find`, and `submittedJobIds` resets on remount, so nothing stale is resurrected. `otherPendingJobs` (the queue list displayed in the CaptioningPage live-progress panel) is derived from `allActiveJobs` (the persistent Zustand store), not from `submittedJobIds`, so the list survives navigation/remount. `globalCaptionJob` (the fallback when `submittedActiveJobId` is null) also includes `"pending"` status for the same reason. Cancelling a pending job in either `CaptioningPage` or `TopBar` calls `useJobStore.getState().updateJob(id, { status: "cancelled" })` optimistically before the API call so the job disappears from the queue list immediately without waiting for an SSE event.

### Ollama timeout

The job's one `httpx.AsyncClient` (`ollama_captioner.make_client`) uses `CAPTION_TIMEOUT_S = 300` per request to accommodate slow hardware and cold model loads. With several requests in flight, a request Ollama queues behind the others spends that wait inside its 300 seconds too.

### Sidecar writes never run on the event loop

`_write_txt_sidecar` (`caption_service.py`) is blocking file I/O, and a bulk edit or import calls it once per image — inline, that stalls the whole server for the length of the batch. Two shapes, picked by how tight the surrounding loop is:

- **Tight loops batch.** `bulk_edit_captions` and `find_replace_captions` accumulate `(file_path, text)` pairs while assigning captions, then make **one** `run_in_executor` call to `_write_sidecars_async(pairs)` **before** `db.commit()` — one hop per batch, since a hop per tiny file costs more than the write. Keeping it before the commit preserves the fail-before-commit ordering the inline writes had. Use this helper for any new batch caption path.
- **Already-slow loops hop per file.** The captioning loop (`routers/captioning.py::_backup_sidecar`, for `save_backup`) and the standalone caption import (`dataset_service.py::_copy_caption_file_sync`) are GPU- or disk-dominated per item, so a per-image executor hop is free. Folder import writes the sidecar *inside* `_ingest_file_sync`, which already runs in an executor — zero extra hops. Export's `_write_sidecar` is wrapped to match its `_write_image`/`_write_mask` siblings.

The ORM caption assignment always stays on the event loop: `Image.caption_text` must be set by attribute assignment or `caption_token_count` goes stale (`docs/dev/shared-utilities.md`). Sync helpers therefore return the text rather than touching the session.
