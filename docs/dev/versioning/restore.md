# Snapshot restore

This file covers `version_service.restore_snapshot`: its four passes (plan → protect →
DB-commit → execute) and the invariant each holds, the complete-or-abort safety snapshot,
Pass 3's failure contract and the outcome it reports, the pixel values measured after a
write, and `duplicate_dataset`'s read-side twin of the Pass 0c gate. It is the part of
versioning that is read line by line when a restore has gone wrong.

Two CLAUDE.md invariants point at Pass 2 and Pass 3 — DB-before-filesystem, and "nothing
fallible between an irreversible filesystem mutation and the `commit()`". The copy-on-write
hooks Pass 1 fires are `docs/dev/versioning/hooks.md`; what Pass 2c writes back for labels,
detections and scores is `docs/dev/versioning/mirrors.md`; the restore and checkout routes
are `docs/dev/versioning/routes.md`.

## The four passes

- `restore_snapshot(db, dataset_id, version_id, handle_extra_images, pre_restore_snapshot, job_id)` — refuses a version of another dataset (GPT-024); optionally auto-snapshots current state before it mutates anything — after planning and the Pass 0c gate, before Pass 1 (**a failed safety snapshot aborts the restore** with a `RuntimeError` — proceeding would silently make it non-undoable; the UI checkbox is the explicit opt-out); after all files are restored, sets `branch.head_version_id = version_id` so the UI "Current" badge moves to the restored snapshot. Runs as **four passes** (plan → protect → DB-commit → execute), each with an invariant:
  - **Pass 0/0b — plan, and resolve foreign IDs**: builds a per-image `_RestorePlan`. Pass 0b handles snapshot images whose `image_id` now lives in *another* dataset (moved out via batch move — the ID cannot be re-inserted here): a same-name current image whose content hash matches the snapshot is **adopted** (keeps repeat restores from duplicating), otherwise the row is **forked** under a fresh UUID and its content restored from the object store; with no recorded hash there is nothing to materialize (counted in `files_unavailable`).
  - **Pass 0c — path gate, before the pre-restore snapshot**: `_refuse_unsafe_restore_paths` proves every path the restore will write or move is safe, collects every violation, and raises `RestoreRefused` (a `RuntimeError`, so the job ends `failed` with the count and one example in `error_msg`, ending "Nothing was changed."). Three rules: every **target** of a plan that yields a row — and its derived thumbnail, which `generate_thumbnail` would mkdir — resolves strictly inside the dataset folder and not under `.versions`; every **renamed source** Pass 3 moves, stages or unlinks is inside `settings.datasets_dir` (looser on purpose, so a live row a pre-fix restore left under an old root can be moved home); and no target, renamed source or touched extra (keep mode: those on a restored filename; remove mode: all) is **another dataset's** `Image.file_path`, one chunked `IN` query. Snapshot paths are history — absolute, written when the snapshot was taken — so a dataset rename used to leave them naming the old root, and a new dataset reusing that name had its files overwritten (GPT-021, PM-025). `rename_dataset` now rebases them; the gate is for whatever still escapes. The order is the point: Pass 0/0b only read, so running the gate and then the safety snapshot means a refusal leaves no orphan pre-restore version, and Pass 1's COW backfill still finds that snapshot's NULL-hash rows. Re-created rows take the gated `p.target_path`.
  - **Pass 1 — gated, hash-once COW protection (undoable in auto mode)**: `protect_file_before_overwrite` fires *only* for files the restore will actually overwrite/move/delete (in-place restores hash the file once, decide `needs_restore`, and reuse the hash via `precomputed_sha256`; pure renames are moved, never backed up), so the pre-restore snapshot's NULL-hash rows get backfilled without hashing/copying the whole dataset. Protection is keyed on `p.img.id` (an adopted plan's current row is a different image than the snapshot recorded). Extras occupying a restore target are protected too (`keep` mode) or run through `mark_image_deleted_in_versions` (`remove` mode) before any file write. In Manual mode the pre-restore snapshot copied everything eagerly, so its own rows are hashed and the hook skips them — but Pass 1 still backs up the lazy rows of any *older* Auto snapshot (GPT-022). A file that fails to hash is protected anyway (the hook re-streams it), and a backup that raises aborts the restore — see § The safety snapshot and Pass 1's abort.
  - **Pass 2 — DB before filesystem, with DB-level rename staging**: all Image rows (re-creations, metadata, and the reverted `filename`/`original_filename`/`file_path`) are committed *before* any file moves, matching the CLAUDE.md DB-before-filesystem invariant. SQLite checks `uq_dataset_filename` **per statement**, so the commit is staged in three flushes: **2a** extras are cleared off restored names first (`remove`: deleted + flushed so the DELETEs precede any re-creation INSERT; `keep`: extras occupying a restored filename are renamed aside to a uniquified name via `unique_filename_with_thumb`, like import collisions — both images survive); **2b** every renamed image is parked on a unique `__dbtmp_{id8}{suffix}` temp filename (swaps/renumber chains would otherwise abort the whole restore with an IntegrityError); **2c** final values + re-creation INSERTs flush collision-free. A move that later fails gets a per-image compensating fixup (`_compensate_paths`) pointing the row back at the file's actual location.
  - **Pass 3 — collision-safe execution**: first the keep-mode extras renamed in 2a are physically moved to their new names (file + sidecar + thumbnail), *then* rename sources that are another image's restore target are staged to `{stem}.__restore_tmp_{id}{suffix}` temp names (swaps/renumber chains can't clobber a file that is still someone's current content). Content restores copy from the object store to `target_path`; a pure rename (auto mode leaves `file_hash=NULL`) *moves* the file (`rename_with_sidecar`). Stale files/sidecars/thumbnails at the old path are removed **only after the restore/move succeeded** — and when the object-store copy is missing, the current file is *moved* to the target, never deleted (it may be the only remaining copy; counted in `files_unavailable`). Each plan's file work is individually contained: an unexpected failure (disk full, permissions) logs, counts in `files_failed`, compensates that row's paths, and the batch continues; after the loop a sweep recovers any unconsumed `__restore_tmp` file to its row's committed path so none is ever left untracked. In `remove` mode, extras' files are unlinked last — **skipping any path in the restored target set** (a restored image owns it now; unlinking would delete the just-restored file). All unlinks go through the path-gated `_remove_stale_files` (V-83) via `run_in_executor`. Thumbnails are regenerated from the row's final `file_path`. Finally, `_sync_caption_sidecar` makes the on-disk `.txt` sidecar match the restored `caption_text` for every image (written when non-empty, deleted when empty) — without this, `rescan_dataset` treats the stale sidecar as a caption edit and silently reverts the restored caption seconds later when `auto_rescan_on_open` fires.

## The safety snapshot and Pass 1's abort

- **The pre-restore safety snapshot is complete or the restore does not start** (GPT-023, PM-026). Restore passes `create_snapshot(..., require_complete=True)`: in Manual mode any per-file copy failure rolls back and raises `SnapshotIncomplete` *before* `add_all` and the commit, so no partial safety version is committed and the branch head does not move; restore's wrapper reports "could not be backed up … aborted before any changes were made". A user-initiated Manual snapshot keeps the commit-with-`[warning]` behaviour. In Auto the flag does nothing — the backups are Pass 1's.
- **Pass 1 is all or nothing.** Its whole body (plans and extras) sits in one `try`: a backup that raises rolls back the flushed backfills, deletes the pre-restore snapshot it had already committed (`_discard_snapshot`, head back to its parent, itself unable to raise) and raises "restore aborted before any file was changed". Hashing the current file is the one step allowed to fail quietly: with no hash, the hook re-streams the file (new gap 6b — previously a hash failure skipped the backup while Pass 3 still overwrote the file).

## Pass 3's failure contract and the outcome

- **Pass 3's failure contract** (GPT-025, PM-026). An object is copied to `objects/.tmp-{uuid}` (prune sweeps those; rescan never looks) and swapped in with `utils.replace_retrying` — the overwriting form, which on Windows retries a held file and then raises `FileInUseError` — with a `try/finally` removing any leftover temp. A failed write therefore leaves the old pixels intact; `shutil.copy2` onto the target used to truncate it first. Every counted failure — `files_failed`, `files_unavailable`, staging and pure-rename failures, keep-mode rename-aside failures (`extras_failed`) — gets one `{file, error}` entry (capped at 50); thumbnail failures count as `thumbnails_stale`. A plan that needed content and did not get it is **reconciled**: a re-created row is deleted with its `ImageLabel` and `Detection` rows (explicit deletes, not the FK cascade), any other row gets back the pixel values captured in Pass 0 (`_RestorePlan.pre_pixel`: the ten scores, `aesthetic_model`, `scores_stale`, `quality_flags`, `dino_layer_scores`, `processing_history`, geometry, phash) and is re-measured, and — when Pass 2c replaced them — its pre-restore detections (`_RestorePlan.pre_detections`), whose geometry is in the frame of the pixels still on disk. Caption, provenance, labels, `sort_order`, generation metadata and lineage keep the snapshot's values — the metadata restore succeeded; only the pixels did not. Every new step is wrapped, since Pass 3b sits between two commits (PM-013).
- **The outcome reaches `result_data`.** The return dict adds `failed_count` (`files_failed + files_unavailable + extras_failed`), `failure_summary` (≤ 300 chars, up to three files), `failed`, `extras_failed` and `thumbnails_stale`; the restore and checkout routes write it with `_store_result` inside `busy`, and the job stays `completed` (PM-023's convention). `checkout_branch` passes it through and **still switches branch after a partial restore**. `_sync_caption_sidecar` catches `ValueError` as well as `OSError`: a non-UTF-8 sidecar used to escape Pass 3b and skip the final commit. Known gaps: a staging failure is counted, not made safe; a keep-mode extra whose rename-aside fails can be overwritten if no snapshot row covers it; `_remove_stale_files` still swallows its errors.

## Measured, not mirrored

- **phash, size, format and geometry are measured, not mirrored** (GPT-016). After a content write or a re-creation, `_measure_into` reads the written file through `get_image_info` (never raises; assigns only what it measured). A `VersionImageState.phash` mirror was rejected: its backfill would copy today's possibly stale `Image.phash` into history (resize and batch crop still leave it stale) and it needs a migration. The cost is one extra decode per restored file, beside the thumbnail's.

## duplicate_dataset's read-side twin

- **`duplicate_dataset`'s snapshot branch is the gate's read-side twin** (`backend/services/dataset_service.py`). A NULL-hash (Auto-mode) row is copied from its recorded `file_path`, which is history in exactly the sense above; a path that `within_datasets_dir` cannot place inside the *source* dataset's folder is logged and counted in `skipped` rather than copied, so a stale snapshot cannot pull another dataset's bytes into the clone. `test_versioning_restore.py::test_duplicate_from_snapshot_skips_an_out_of_tree_lazy_row` pins it. Each copy's phash is measured from the copied file, since `VersionImageState` carries none (GPT-016).
