# Bulk image jobs (resize, crop, thumbnails)

This file covers the bulk operations that rewrite pixels or files as a `BackgroundJob`: batch
resize and aspect crop, the thumbnail rebuild, and detection-driven cropping. All three share
one loop shape — per-item failure counting that never aborts the run, `job_queue`
cancellation checks, and a `result_data` counters dict — so a reader debugging one of them is
usually reading the right file for the others. Three things they do **not** share, each worth
knowing before assuming: only `bulk_thumbnails` calls `contained_path`, the others passing
`img.file_path` raw; `regenerate_thumbnails` writes no `thumbnails_stale` counter, being
itself the repair; and the PM-013 per-item commit ordering, though now universal here, was
reached at three different times by three different fixes.

The metadata side of "bulk" lives in `docs/dev/bulk-ops.md`: `_apply_bulk_filters`, the
endpoint table, caption find/replace, `BulkEditPage`'s tabs and Renumber's two-phase rename.
The detector whose boxes the crop job consumes is `docs/dev/detection.md`; the job-completion
toasts and invalidations are `docs/dev/frontend-jobs.md`; the commit-ordering invariant is
CLAUDE.md § Key invariants and `docs/dev/postmortems/PM-013-fs-mutation-before-the-commit.md`.

## Batch resize and aspect crop

`POST /images/batch/resize` (`{image_ids, width?, height?, scale?, maintain_ar, label?}`) and `POST /images/batch/crop` (`{image_ids, target_ar, strategy, label?}`) enqueue `batch_resize` / `batch_crop` jobs that overwrite each image **in place** via `image_service.resize_image` / `crop_to_aspect`. Both take a bare id list with no dataset constraint, so `_guard_batch_datasets` resolves every dataset the selection touches and `ensure_not_busy`-guards each one before the job row is created; it also sets `BackgroundJob.dataset_id` when the selection resolves to exactly one dataset. `result_data` carries the same four counters as the LUT and upscale runs (`processed`, `skipped`, `failed`, `thumbnails_stale`), and both loops honour `job_queue.cancel_requested`.

The loop shape is the Tier-1 PM-013 one: `protect_file_before_overwrite` + commit, the fallible geometry call in a `try` that counts a failure and continues, the row fields and (crop only) `remap_detections_for_crop` — DB-only work, so it stays *above* the commit — then a per-image `commit()`, then a post-commit epilogue for the thumbnail and the SSE emit.

Both record the rewrite through `backend/utils.py::record_in_place(img, op, **params)`, and so does every other in-place path in the repo — the `crop_to_detection` job below, `batch_inpaint`, `batch_lut`, `batch_upscale`, `crop_upscale`, the two single-image twins, and `video_reextract`. It was `images.py`'s private `_record_in_place` until 2026-07-31; the four routers that could not import it had each hand-rolled a copy. Promoting it to `utils.py` made it the single writer of `processing_history` **and** `Image.scores_stale` (set only when the row already carries a score), which is the point: a site that appends the history entry by hand records the edit and leaves the scores looking trustworthy. A structural AST guard in `backend/tests/test_scores_stale.py` fails CI for the eleventh site that tries. It sits strictly between the irreversible overwrite and the per-image `commit()`, never in the epilogue — it is pure attribute access and cannot raise. See `docs/dev/scores-stale.md`.

**Both endpoints were unreachable until 2026-07-31**, declared below `POST /images/{image_id}/resize` and `/{image_id}/crop`, which match first because `image_id: str` accepts the literal `"batch"`. They now sit above those routes, and any future `/batch/*` route on this router belongs in the same block — declaration order *is* the routing table (`docs/dev/postmortems/PM-018-batch-routes-shadowed-by-a-path-parameter.md`). Three consequences of that history remain open on purpose: neither handler refreshes `file_size_bytes`/`phash` after the overwrite (nor do the single-image twins); neither job type is in `TopBar.tsx`'s `IMAGE_MODIFYING_JOB_TYPES`; and neither is in its `THUMBNAIL_EPILOGUE_JOB_TYPES` either, so a run whose previews all failed to rebuild writes `thumbnails_stale` and tells the user nothing. All three are open because no UI can start them — `frontend/src/api/images.ts` defines `batchResize`/`batchCrop` and nothing calls either. Wiring a UI means touching both `TopBar` sets, not one. `backend/tests/test_batch_resize_crop_http.py` covers the route order, the per-image commit, the epilogue and the 409.

## Rebuilding thumbnails

`POST /images/bulk-thumbnails` is the **repair** for every job that re-cuts an image thumbnail as a best-effort post-commit epilogue. When that epilogue raises, the image is correct and committed but the gallery keeps drawing the old tile, and nothing self-heals it: `GET /images/{image_id}/thumbnail` only regenerates when the file is *missing*, and the stale file exists.

**Eight jobs write `result_data["thumbnails_stale"]`; six surface it.** The writers are `batch_lut`, `batch_upscale`, `crop_upscale`, `crop_to_detection`, `batch_inpaint`, `video_reextract`, `batch_resize` and `batch_crop`. `TopBar`'s `THUMBNAIL_EPILOGUE_JOB_TYPES` holds the first six, so those turn the count into the one warning toast (`docs/dev/frontend-jobs.md`); the two batch jobs record it and nothing reads it, because no UI can start them yet — see § Batch resize and aspect crop.

The request body carries a **scope, never the affected id list**. The realistic trigger — a full volume, a read-only `thumbnails/` — is deterministic, so "the affected images" is "everything the run touched"; an id list would be thousands of uuids serialized into every `GET /jobs/` row, and it is least available exactly when it matters (`job_queue` fails a raising job from a separate session and never persists the worker's dict). Over-scoping is safe here in a way it never is for delete or rename: regenerating a correct thumbnail costs one re-encode.

- **Scope**: the shared `_apply_bulk_filters` triple, plus `Image.dataset_id == body.dataset_id` **only** when `image_ids` is empty — a `SelectionToolbar` selection can span datasets, exactly as in `bulk_provenance`. `ensure_not_busy` runs for every dataset the rows actually touch.
- **Preflight**: `require_free_space` → **507**, on the request path so no job row is created. This is the repair you run *because* the volume filled up, so a 507 is the right answer rather than 400 more log lines.
- **Job body** (`regenerate_thumbnails`): rows are loaded through `utils.chunked` — `_apply_bulk_filters` builds one query and does not chunk, but it never binds the ids; this loader does. Per row: cancel check, progress emit, then `contained_path` on **both** `file_path` and `thumbnail_path` — `generate_thumbnail` `mkdir(parents=True)`s its destination's parent, so an ungated stored path is an arbitrary-file-*write* primitive, not merely a stale tile. A `None` gate or an absent source counts `skipped`; a row with no `thumbnail_path` falls back to `thumbnail_path_for`. The re-encode runs in an executor under a per-row `try/except → failed += 1; continue`, so the repair does not inherit the failure mode it exists to fix.
- **`updated_at` is bumped on every repaired row, and that is load-bearing**: `imagesApi.thumbnailUrlVersioned` builds `?v=${Date.parse(updatedAt)}`, so a repair that rewrites the `.webp` without moving the row leaves the `<img src>` byte-identical and the browser serves the stale tile from cache — the repair would visibly do nothing. The column value written to `thumbnail_path` is the *stored* form (derived from `img.file_path`), never the `.resolve()`d path the write uses, so the stored-path form does not drift mid-table.
- Commits every 50 rows; `result_data = {regenerated, failed, skipped}` is written above `raise_if_cancelled`, so a cancelled run keeps what it repaired. **No `refresh_stats`** — a thumbnail is not counted in `total_size_bytes`, and nothing else this job writes appears in a dataset rollup.
- Tests: `backend/tests/test_regenerate_thumbnails_http.py` (the `updated_at` bump, the out-of-tree refusal, subfolder scoping, an unreadable source, the 507, a cross-dataset selection) and `frontend/e2e/thumbnails.spec.ts`.

`RegenerateThumbnailsForm` (`frontend/src/components/image/RegenerateThumbnailsForm.tsx`) — the `UpscaleForm` props contract, the single-job `jobId` + `useJobStore` pattern, and a `resultToast` in the `CropToDetectionForm` shape. Two surfaces: the **Thumbnails** tab on `BulkEditPage` and a **Thumbnails** button + modal in `SelectionToolbar`. The tab is the one that matters — a deterministic failure means "the whole dataset", and `SelectionToolbar` only exists when there is a selection. `targetsFlaggedImages` stays `tab === "delete"`, so the shared scope panel and its cache key are unchanged.

## Detection-driven cropping (crop to detected subject)

`POST /detection/crop` (`backend/routers/detection.py::crop_to_detection`, schema `DetectionCropRequest`) — batch-crops images to their detection bboxes as a `crop_to_detection` BackgroundJob. Structured as a close mirror of `upscaling.py`'s `_run` (same scope triple, replace/new-file branches, progress-before-item, per-item failure continue, cancel handling) — including, since 2026-07-31, the same PM-013 ordering: its replace branch used to run an un-`try`-wrapped `generate_thumbnail` after `tmp_path.replace(src_path)` with the loop's only `commit()` afterwards, so a raise rolled back the geometry, `processing_history` and detection remaps of every image already overwritten on disk. It now commits per image and regenerates the thumbnail in a post-commit `try` that counts `thumbnails_stale`. `backend/tests/test_detection_crop_replace_http.py` pins the shape, the epilogue and the blast radius.

- **Scope**: `image_ids` > `dataset_id` + `subfolder` + `quality_flags` (flag exclusion, `ALLOWED_FLAG_KEYS`-validated). `labels: list[str] | None` filters which detection labels drive the crop (None/[] = all); `label` (singular) is the job-label override — do not confuse the two.
- **Crop rect math** is the pure helper `backend/ml/mask_utils.py::detection_crop_rect(bboxes, img_w, img_h, mode, padding_pct, target_ar) -> (x, y, w, h) | None` (unit-tested in `backend/tests/test_detection_crop_rect.py`): sanitizes normalized bboxes, selects `mode="union"` (envelope of all matches) or `"largest"` (max area), pads each side by `padding_pct`% of the box's own extent, then optionally **grow-only** snaps to `target_ar` (never shrinks below the subject; clamps to the image; if no legal rect of that ratio contains the subject, the exact ratio is sacrificed rather than cutting the subject). Denormalizes against the DB `Image.width/height` — consistent because detection predictors open through `backend/ml/image_utils.py::open_rgb` (EXIF-transpose) and `crop_image_to_dest` opens through `image_service._open_safe` (also EXIF-transpose), so both work in the same transposed frame.
- Detections are prefetched with the chunked pattern (`_fetch_bboxes_by_image`, ≤10k ids per `IN`); images with no matching detections are counted request-side and returned as `skipped` in `{job_id, total, skipped}` (`total_items` counts only matched images, keeping the progress denominator honest).
- Per image: `None` rect → `skipped_no_detection`; full-image rect → `skipped_noop` (a no-op crop would only re-encode the file). **Replace** mode calls `protect_file_before_overwrite` then crops via `crop_image_to_dest` to a `{stem}_croptmp{suffix}` temp + `Path.replace()`, updates `width/height/file_size_bytes/format/phash`, calls `record_in_place(img, "crop_to_detection", …)` for the history entry, the `updated_at` stamp and `scores_stale` (set only when the row already carries a score), remaps the detections in the same transaction, commits, and only then regenerates the thumbnail in the epilogue. **New-file** mode derives `{stem}_crop` via `slugify_filename` + `unique_filename_with_thumb` and creates a new Image row. It carries the per-thumbnail-directory `occupied_by_dir`/`planned_by_dir` dicts rather than one flat set, because a selection can span datasets and each has its own `thumbnails/` — a single set would false-share stems across them. `docs/dev/image-files.md` § occupied-stem set points at this worker as the shape to copy. The new row's `subfolder` comes from the optional `dest_subfolder` field (`None` = inherit the source's subfolder — the default/backward-compatible behavior; `""` = root; any other string = that subfolder). `dest_subfolder` is `normalize_subfolder`-validated request-side (a `..` path 400s before the job starts) and ignored when `replace=True`. It is a logical label only — files still live flat in `{dataset}/images/`, so no filesystem move happens; the subfolder appears in listings automatically once the first cropped row exists (`dataset_service.list_subfolders` merges image-derived subfolders). The new row also inherits the parent's provenance verbatim (`**copy_provenance(img)`), which is why the worker's image query carries `undefer(Image.source_meta)` — see `docs/dev/provenance.md` § Derived-image rule.
- Final counts land in `BackgroundJob.result_data` (`{cropped, skipped_no_detection, skipped_noop, failed}`); the terminal SSE message is always "Done.", so the frontend fetches the job on completion and toasts from `result_data`.

**Remapping detections through replace-mode crops.** Any crop that *replaces* the image changes its geometry, so its normalized detection coordinates must be re-expressed relative to the crop.

- **The pure remap** is `backend/ml/mask_utils.py::remap_detection_geometry(mask_json, bbox, rect, old_size)`. `rect` is `(x, y, w, h)` **in pixels of the OLD image's EXIF-transposed frame** (the frame detection coords live in — captured *before* `Image.width/height` are overwritten), `old_size` is `(old_w, old_h)` of that frame. Each coordinate maps `new = clamp((n*old_dim − offset)/extent, 0, 1)`.
- **Dropping rows.** The bbox is the primary (non-nullable) geometry: if its remapped extent < 0.002 on either axis the detection is outside the crop and the fn returns `None` (delete the row). Polygon vertices are remapped+clamped (edge polygons flatten against the border — accepted); a remapped polygon with shoelace area < 1e-4 is dropped, and a masked detection that loses every polygon keeps its bbox with `mask=None`.
- **The async orchestrator** `backend/services/detection_service.py::remap_detections_for_crop(session, image_id, rect, old_size) -> (remapped, dropped)` selects all of an image's detections, deletes the `None` results and writes `det.mask` **then** `det.bbox` via ORM assignment (bbox last so the final `mask_area` listener recompute sees both — see `docs/dev/detection.md`). It does **not** commit; the caller owns the transaction.
- **Call sites** (each captures `old_size` before mutating dimensions): the `crop_to_detection` worker replace branch, `routers/images.py::crop` sync-replace path, `_run_crop_upscale_replace` (remapped only after a successful upscale — a failed upscale must not remap), and `routers/images.py::batch_crop` (`crop_to_aspect` returns its rect + orig dims for this single caller).
- **Exempt** (normalized coords are invariant under pure scaling): resize/`batch_resize` and all upscaling; new-file crop paths (the new row has no detections to remap). Coordinates are invariant under scale because they are already fractions of the image.
- **Known limitation:** a version-restore that swaps in an older image file does not remap detections (pre-existing, out of scope).

**Frontend**: `CropToDetectionForm` (`frontend/src/components/crop/CropToDetectionForm.tsx`) — shared form with the `UpscaleForm` props contract plus `disabled`; label chips from `["detection-labels", datasetId]`, mode radio, padding %, aspect `<select>` fed by `frontend/src/constants/aspectRatios.ts::ASPECT_PRESETS` (also consumed by the ImageDetailPage crop tool), New file/Replace radio, and a **Destination subfolder** `<select>` shown only in New-file mode (Same as source / root / existing subfolders from `["subfolders", datasetId]` / New subfolder… free-text, mirroring the `MoveToDatasetModal` sentinel pattern; resolved into the optional `dest_subfolder` payload field, and the completion effect also invalidates `["subfolders", datasetId]`). Surfaced as the **Crop** modal in `SelectionToolbar`, the **Crop to Subject** tab on `BulkEditPage`, and the **Crop to Subject** button in the `ImageDetailPage` toolbar beside Crop/Upscale/LUT (rendered only when the image has detections and crop mode is off; scoped to `imageIds=[imageId]`; passes the optional `availableLabels: {label, count}[]` prop so the chips show only that image's labels with per-detection counts instead of running the dataset-wide query, and its `onSuccess` additionally invalidates `["image", imageId]`). Job type `crop_to_detection` is registered in `TopBar`'s `IMAGE_MODIFYING_JOB_TYPES`.

## Painting detections out (watermark removal)

`POST /inpaint/run` (`backend/routers/inpaint.py::run_inpaint`, schema `InpaintRunRequest`) enqueues a `batch_inpaint` job that rasterizes an image's existing `Detection` rows into a mask and paints that region out with LaMa. It is the fourth job in this file and structurally the closest to `crop_to_detection`: the same scope triple, the same replace/copy branches, the same per-thumbnail-directory collision dicts, the same PM-013 loop ordering, the same `result_data` placement above `raise_if_cancelled`. The model half is `docs/dev/ml-models.md` § The LaMa inpainter.

**It consumes detections; it never produces them.** The flow is two steps and the first is a grounding detection pass (`docs/dev/detection.md`). Nothing in this router runs a detector, so an image with no matching detection is `skipped_no_detection` — pre-filtered in the *handler*, before the job row is created, so `total_items` is honest and the response carries `{job_id, total, skipped}` like `POST /detection/crop`. `_fetch_masks_by_image` is `detection.py::_fetch_bboxes_by_image` widened to `(id, mask_json, bbox)` triples, keeping the `chunked()` wrapper for SQLite's bind ceiling.

**`rasterize_detections`, never `compose_loss_mask`.** The latter's empty-`include` case deliberately returns full white, which trains an image unmasked — and here would repaint the *entire* image. `rasterize_detections` fails safe in the other direction: empty geometry rasterizes to all black and nothing is painted. The mask is then grown by `dilate_px` (a `MaxFilter` over an odd window, exact for a binary mask; default 6) because a segmentation boundary sits tight against a semi-transparent watermark and leaves a halo of its edge pixels behind. Measured against a synthetic watermark, 6 costs nothing and 12 starts eating neighbouring detail.

**The whole mask build runs in an executor, and `_dilate` is bbox-limited.** Rasterize → dilate → PNG-encode is `_build_mask_png`, a module-level sync helper called through `run_in_executor` — full-resolution Pillow work with no `await` in it, which on the event loop freezes every other request (the SSE progress stream included) for its duration. `export_service._write_mask` is the precedent. The dilation is the expensive half: `MaxFilter` is a `RankFilter` selecting over all *k*² window pixels per output pixel, so the cost scales with `canvas_area × (2·px+1)²` — 2.0 s at the default `px=6` on a 4000×3000 mask and 168 s at the schema's max of 64. `_dilate` therefore filters only `mask.getbbox()` grown by `px` and pastes the result back, which is **exactly** equivalent (dilation cannot reach further than `px` from a white pixel; outside the crop every window sees black either way, and at the image border both runs face the same padding). `backend/tests/test_inpaint_dilate.py` pins that equivalence against a naive full-canvas filter, empty and border-touching masks included.

**Every stored path goes through `utils.contained_path` first, which makes this router stricter than its `lut.py`/`upscaling.py` siblings — deliberately.** `img.file_path` is gated at the top of each iteration, above `protect_file_before_overwrite`: that helper copies the bytes into `{ds}/.versions/objects/`, so an out-of-tree value is an arbitrary-file *read* primitive even before the overwrite, and the copy branch derives its destination from the path's parent. `img.thumbnail_path` is gated in the replace epilogue, because `generate_thumbnail` mkdirs its parent and an out-of-tree value is an arbitrary-file *write* primitive — the reasoning CLAUDE.md gives for `images.bulk_thumbnails`. `contained_path`, not `safe_dataset_path`: a 403 is wrong inside a job loop, so a refusal logs, counts (`failed` for the source, `thumbnails_stale` for the thumbnail) and `continue`s, and everything downstream uses the **resolved** path the helper hands back. Read the difference from the siblings as intent, not as a sweep that stopped early.

**Replace mode writes four things above the commit** and nothing fallible sits between the overwrite and it: `file_size_bytes`, `phash` (returned by `inpaint_image_sync` precisely because nothing else would refresh it), the filename/path/format trio when the PNG fallback moved the file, and the `record_in_place(img, "inpaint", …)` that stamps `processing_history` and `scores_stale`. Geometry is unchanged, so — unlike `crop_to_detection` — there is **no** `remap_detections_for_crop` and no `width`/`height` write. Two more DB-only writes share that transaction: the consumed `Detection` rows are deleted by id, and `has_watermark` is cleared under the rule below. The post-commit epilogue is the usual pair: unlink a superseded original, re-cut the thumbnail, `thumbnails_stale += 1` on failure.

**`has_watermark` is cleared iff the image has no detection left at all**, and the `iff` is the whole rule. Crucible has **no vocabulary of "watermark labels"** — `detection._apply_watermark_flag` sets the flag from `bool(detections)` on a watermark-sync grounding run, whatever the phrase was — so a run scoped to some other label cannot tell whether what survived is a watermark; clearing anyway would let the image escape both the *Flagged: watermark* filter and export's `exclude_flags` and ship with the watermark visible. Deciding it costs one extra batched `select(Detection.id, Detection.image_id)` over `matched_ids` (`_fetch_detection_ids_by_image`, unfiltered by label — the companion to `_fetch_masks_by_image`), never a per-image query. The write is copy-then-reassign (`flags = dict(img.quality_flags or {})`), because SQLAlchemy compares JSON columns by equality and an in-place mutation is silently skipped; when nothing is cleared the column is not written at all rather than reassigned to an equal dict. The common workflow — detect `watermark`, then paint that label — still clears.

**`watermark_score` is left standing, stale.** `record_in_place` sets `scores_stale`, so the number is visibly flagged rather than silently trusted, and clearing the *flag* while leaving the *score* is the honest pair — nothing here measures anything. The Quality page therefore shows a stale score beside a cleared flag until the user re-scores. See `docs/dev/scores-stale.md`.

Copy mode writes a `{stem}_nowm` derivative through `unique_filename_with_thumb` with `**copy_provenance(img)`, records `derivative_ids` and calls `copy_labels` after the loop so a cancelled run still labels what it copied — the fifth same-dataset derivative site, pinned by `backend/tests/test_labels_survive_rebuild_paths.py`. It touches the parent not at all: the parent still has the watermark, so its detections and its flag stay. Only the copy branch `undefer`s `Image.source_meta`; undeferring in replace mode would load a scraper's full raw payload for the whole batch and discard it. **Its ordering is PM-013 Tier 1, not the Tier 3 the four sibling routers still carry**: `new_img` is built with its `thumbnail_path` set, `session.add` → `commit()` (the id read back afterwards, `expire_on_commit=False`), and only then is the thumbnail cut, inside a `try/except` that counts `thumbnails_stale` and cannot change the item's outcome. Cutting first lets an `OSError` on image 300 of 500 propagate out of `_run`, where `job_queue` marks the job failed from a separate session and this one rolls back **every** uncommitted derivative row while their `_nowm` files stay on disk.

Counts are `{inpainted, skipped_no_detection, skipped_name_taken, failed, thumbnails_stale}`. `skipped_name_taken` is the PNG-fallback squatter branch — an unregistered file already sitting at the `.png` the write would take — and is a separate key precisely so `skipped_no_detection` keeps only its two real causes (a row that vanished between enqueue and run, and one whose label filter matched nothing); blaming the detection pass for a stray file on disk sends the user looking in the wrong place. `InpaintForm.resultToast` surfaces it as `N skipped (name already taken)`. **Frontend**: `InpaintForm` (`frontend/src/components/inpaint/InpaintForm.tsx`) — the `CropToDetectionForm` props contract and single-job pattern, plus `apiErrorDetail` in `onError` so a missing-weights `FileNotFoundError` or a 507 reaches the toast. Mounted twice: a **Remove Watermark** button in the `ImageDetailPage` toolbar (gated on the image having detections, scoped to `imageIds=[imageId]`, `onSuccess` also invalidating `["image", imageId]`) and a **Remove WM** modal in `SelectionToolbar`. `batch_inpaint` is registered in all three `TopBar` sets it belongs to — `IMAGE_MODIFYING_JOB_TYPES`, `THUMBNAIL_EPILOGUE_JOB_TYPES`, and the detection branch, since it deletes `Detection` rows — and deliberately **not** in `LIVE_IMAGE_JOB_TYPES`. `backend/tests/test_inpaint_http.py` covers the whole loop torch-free.
