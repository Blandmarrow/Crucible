# Version service internals

This file covers `backend/services/version_service.py` — the copy-on-write and deletion
hooks, `create_snapshot`, `restore_snapshot`'s four passes, `diff_versions` — and the table
of call sites in other routers where the two hooks fire. It is the half of versioning that
is read line by line when something has gone wrong.

The model, the object store, the busy guard, the `/datasets/{id}/versions` routes and the
frontend are in `docs/dev/versioning.md`. Two CLAUDE.md invariants point at restore's Pass 2
and Pass 3 — DB-before-filesystem, and "nothing fallible between an irreversible filesystem
mutation and the `commit()`" — and the Path traversal guard names both hooks by symbol.

## Service

**Backend service** (`backend/services/version_service.py`):

Key functions:
- `protect_file_before_overwrite(image_id, file_path, db)` — COW hook; no-op unless `"auto"` mode and the image has NULL-hash snapshot rows. It only *flushes* the hash backfill — every caller that overwrites the file before its own final commit must `commit()` right after the hook (all current call sites do), otherwise a crash during the overwrite rolls the backfill back and the snapshot rows silently claim "content unchanged"
- `mark_image_deleted_in_versions(image_id, file_path, db)` — deletion hook; no-op if `"off"` or no snapshot rows exist for image
- **Both hooks sit behind the path-containment gate** (`utils.contained_path`, per the CLAUDE.md Path traversal guard). They are not just bookkeeping: *both* reach `_store_object` and copy `file_path`'s bytes into `{ds}/.versions/objects/`, so an out-of-tree `file_path` is an arbitrary-file read primitive retrievable through a snapshot restore — even if the caller skipped the unlink. A destructive route that refuses a path must therefore skip the hook too, not only the `unlink`; and a site that fires *both* hooks must gate the whole loop, not the deletion branch alone. Two sites gated only their unlinks until 2026-07-31: `routers/filesystem.py::delete_path`'s row loop (reachable because the endpoint validates with `sanitize_abs_path`, which proves a path absolute, not contained) and `restore_snapshot`'s extras loop, whose `else` branch reaches the same primitive through `protect_file_before_overwrite`. Both are now gated per row and the row deletes stay unconditional. Tests: `backend/tests/test_path_containment_http.py` and `test_versioning_restore.py` — both must switch `versioning_mode` on, or the hook no-ops and the test proves nothing; the restore one needs **two** snapshots, since an extra added after the only snapshot has no `VersionImageState` row and the hook returns on its first query.
- `_backup_and_record_hash(image_id, file_path, dataset_folder, db, precomputed_sha256=None)` — shared helper: store via `_store_object` → backfill all NULL `file_hash` rows for the image in one `UPDATE` with the hash of the bytes *actually stored*. `precomputed_sha256` is only a fast path: when its object already exists, all I/O is skipped (the content is safely stored — correct even if the file changed since the caller hashed it); otherwise the file is re-streamed through `_store_object`, so a stale caller hash can never poison the store or the state rows.
- `create_snapshot(db, dataset_id, name, description, branch_id, job_id, source)` — creates snapshot; `source` is `"manual"` (user-triggered), `"pre_restore"` (auto before restore), or `"branch_init"` (new branch). When `branch_id` is omitted it resolves to the dataset's **current branch** (`dataset.current_branch_id`), falling back to `main` only for never-branched datasets — so pre-restore/checkout auto-snapshots land on the branch the user is actually on and never move `main`'s head. `"manual"` mode also copies every file eagerly; per-file backup failures are counted, appended as a `[warning]` line to the version description, and emitted in the job progress (a NULL hash would otherwise restore as "content unchanged" with no trace). `create_branch` resolves its `from_version_id` default from the current branch's head the same way.
- `restore_snapshot(db, dataset_id, version_id, handle_extra_images, pre_restore_snapshot, job_id)` — optionally auto-snapshots current state first (**a failed safety snapshot aborts the restore** with a `RuntimeError` — proceeding would silently make it non-undoable; the UI checkbox is the explicit opt-out); after all files are restored, sets `branch.head_version_id = version_id` so the UI "Current" badge moves to the restored snapshot. Runs as **four passes** (plan → protect → DB-commit → execute), each with an invariant:
  - **Pass 0/0b — plan, and resolve foreign IDs**: builds a per-image `_RestorePlan`. Pass 0b handles snapshot images whose `image_id` now lives in *another* dataset (moved out via batch move — the ID cannot be re-inserted here): a same-name current image whose content hash matches the snapshot is **adopted** (keeps repeat restores from duplicating), otherwise the row is **forked** under a fresh UUID and its content restored from the object store; with no recorded hash there is nothing to materialize (counted in `files_unavailable`).
  - **Pass 1 — gated, hash-once COW protection (undoable in auto mode)**: `protect_file_before_overwrite` fires *only* for files the restore will actually overwrite/move/delete (in-place restores hash the file once, decide `needs_restore`, and reuse the hash via `precomputed_sha256`; pure renames are moved, never backed up), so the pre-restore snapshot's NULL-hash rows get backfilled without hashing/copying the whole dataset. Protection is keyed on `p.img.id` (an adopted plan's current row is a different image than the snapshot recorded). Extras occupying a restore target are protected too (`keep` mode) or run through `mark_image_deleted_in_versions` (`remove` mode) before any file write. Manual mode is unaffected (its pre-restore snapshot copies everything eagerly).
  - **Pass 2 — DB before filesystem, with DB-level rename staging**: all Image rows (re-creations, metadata, and the reverted `filename`/`original_filename`/`file_path`) are committed *before* any file moves, matching the CLAUDE.md DB-before-filesystem invariant. SQLite checks `uq_dataset_filename` **per statement**, so the commit is staged in three flushes: **2a** extras are cleared off restored names first (`remove`: deleted + flushed so the DELETEs precede any re-creation INSERT; `keep`: extras occupying a restored filename are renamed aside to a uniquified name via `unique_filename_with_thumb`, like import collisions — both images survive); **2b** every renamed image is parked on a unique `__dbtmp_{id8}{suffix}` temp filename (swaps/renumber chains would otherwise abort the whole restore with an IntegrityError); **2c** final values + re-creation INSERTs flush collision-free. A move that later fails gets a per-image compensating fixup (`_compensate_paths`) pointing the row back at the file's actual location.
  - **Pass 3 — collision-safe execution**: first the keep-mode extras renamed in 2a are physically moved to their new names (file + sidecar + thumbnail), *then* rename sources that are another image's restore target are staged to `{stem}.__restore_tmp_{id}{suffix}` temp names (swaps/renumber chains can't clobber a file that is still someone's current content). Content restores copy from the object store to `target_path`; a pure rename (auto mode leaves `file_hash=NULL`) *moves* the file (`rename_with_sidecar`). Stale files/sidecars/thumbnails at the old path are removed **only after the restore/move succeeded** — and when the object-store copy is missing, the current file is *moved* to the target, never deleted (it may be the only remaining copy; counted in `files_unavailable`). Each plan's file work is individually contained: an unexpected failure (disk full, permissions) logs, counts in `files_failed`, compensates that row's paths, and the batch continues; after the loop a sweep recovers any unconsumed `__restore_tmp` file to its row's committed path so none is ever left untracked. In `remove` mode, extras' files are unlinked last — **skipping any path in the restored target set** (a restored image owns it now; unlinking would delete the just-restored file). All unlinks go through the path-gated `_remove_stale_files` (V-83) via `run_in_executor`. Thumbnails are regenerated from the row's final `file_path`. Finally, `_sync_caption_sidecar` makes the on-disk `.txt` sidecar match the restored `caption_text` for every image (written when non-empty, deleted when empty) — without this, `rescan_dataset` treats the stale sidecar as a caption edit and silently reverts the restored caption seconds later when `auto_rescan_on_open` fires.
- `diff_versions(db, dataset_id, v1, v2)` — pure DB, no background job; uses `_DIFF_COLS` column-explicit select for efficiency. Compared fields: `caption_text`, `quality_flags`, `subfolder`, **all ten `*_score` columns** — every one is mirrored on `VersionImageState` and compared; migration `d1c7b4e9f0a3` added the last three (`nsfw_score`, `saturation_score`, `luminance_score`) and says why the earlier carve-out was wrong — `dino_layer_scores`, `generation_metadata`, the five provenance columns (`source_name`, `source_url`, `license`, `attribution`, `source_meta`), `sort_order`, `processing_history`, plus `file` (hash). The list is the module-level **`_DIFF_COMPARE_FIELDS`** tuple, hand-synced with `_DIFF_COLS`: adding a column to `_DIFF_COLS` alone selects it from both versions and then throws it away (which is how `source_meta` was loaded on every diff without ever being compared), while a name in `_DIFF_COMPARE_FIELDS` that is missing from `_DIFF_COLS` is never selected and so silently reports "unchanged". `test_provenance_http.py` asserts the compare list is a subset of the selected columns. The heavy JSON fields in `_HEAVY_DIFF_FIELDS` (`dino_layer_scores`, `generation_metadata` — full ComfyUI workflow payloads — and `source_meta`, a scraper's raw sidecar payload) are compared but reported only as a compact `{"changed": true}` marker, never embedded. `processing_history` changes render as `+`/`−` operation badges in `DiffModal`; `{"changed": true}` renders as "field: changed"; the generic `ChangeRow` renders any other field via `JSON.stringify`.
- **Snapshot rows written before `d1c7b4e9f0a3` were backfilled** for those three columns from `images` by `image_id`, so an old snapshot claims *today's* score. That is the only knowable value, and it is exactly what a restore of that snapshot left in place before the migration (the columns were never written back), so behaviour is unchanged and no spurious diff row appears between two pre-migration versions. Rows whose image is gone stay NULL.
- `DELETE /{id}/versions/{version_id}` head reassignment: when the deleted version is the branch head, the head moves to the version's **parent** if it exists on the same branch, else to the newest remaining version on the branch. Parent-first matters after a restore: the newest-by-`created_at` version is then the pre-restore auto-snapshot — exactly the state the user restored away from.

## Copy-on-write injection points

**Copy-on-write injection points** (existing routers, all fire before the file operation):

| File | Operation |
|---|---|
| `backend/routers/images.py` | `resize` endpoint, batch crop `_run`, batch resize `_run` — calls `protect_file_before_overwrite` |
| `backend/routers/images.py` | `crop` endpoint, replace=True branch — calls `protect_file_before_overwrite` |
| `backend/routers/images.py` | `delete_image`, `batch_delete`, `bulk_delete_filtered` (`POST /images/bulk-delete`) — calls `mark_image_deleted_in_versions` |
| `backend/routers/upscaling.py` | `_run` coroutine, replace=True branch — calls `protect_file_before_overwrite` |
| `backend/routers/detection.py` | `crop_to_detection` `_run` coroutine, replace=True branch — calls `protect_file_before_overwrite` |
| `backend/routers/lut.py` | `_run` coroutine, replace=True branch — calls `protect_file_before_overwrite` |
| `backend/routers/videos.py` | `_run_reextraction`'s per-frame `_rewrite` — calls `protect_file_before_overwrite` before swapping the full-resolution frame in. Unlike the rows above it verifies the new file re-opens *first*, so a frame that fails is never protected-then-not-overwritten (`docs/dev/video-reextract.md`) |
| `backend/routers/videos.py` | `_delete_previous_frames` — replace-mode extraction's step that clears a video's previous frames; calls `mark_image_deleted_in_versions` per row before the row delete and the unlink, inside the `busy(dataset_id, "Replacing extracted frames")` block (`docs/dev/video-extract.md`) |
| `backend/routers/filesystem.py` | `delete_path` (`POST /filesystem/delete`), both branches — calls `mark_image_deleted_in_versions` per `Image` row under the deleted file or folder, each gated by `utils.contained_path` (the row delete below it stays unconditional). This site must fire before the *row* delete as well as before the file operation: the hook loads the image with `db.get`, which after a staged Core delete autoflushes and returns None (PM-014) |
| `backend/routers/quality.py` | `resolve_duplicates`, delete branch — calls `mark_image_deleted_in_versions` per row, then `refresh_stats` per dataset |
| `backend/routers/images.py` | `batch_move_dataset` — calls `mark_image_deleted_in_versions` per moved image *before* the dataset_id updates (a cross-dataset move is a deletion from the source dataset's history; without the backup, pre-move snapshots could never materialize the image) |
| `backend/services/version_service.py` | `restore_snapshot`, Pass 1 — calls `protect_file_before_overwrite` (gated: only files that will actually be overwritten/moved/deleted, hash passed as `precomputed_sha256`) before any file operation, backing current content into the pre-restore snapshot so the restore is undoable in auto mode |
| `backend/services/version_service.py` | `restore_snapshot`'s extras loop in Pass 1 (before any FS write) — `mark_image_deleted_in_versions` per extra in `"remove"` mode, `protect_file_before_overwrite` for a `"keep"`-mode extra occupying a restore target. `utils.contained_path` gates the **whole loop**, not just the `"remove"` branch: both hooks end at `_store_object` and are the same read primitive. Files + `.txt` sidecars + thumbnails are unlinked later in Pass 3c via `_remove_stale_files` in an executor, which gates containment **inside** the helper (V-83): it has five call sites and this is the riskiest, handing over an arbitrary row's stored `file_path`/`thumbnail_path` untouched. `contained_path` never raises, which matters — that helper's body sits in a bare `except Exception: pass` that would swallow it silently |
