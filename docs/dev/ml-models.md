# ML model lifecycle

This file covers what every model shares on its way in: the `model_manager` singleton and how it loads, the ambient `HF_TOKEN` every hub loader relies on, the EXIF-consistent `open_rgb` rule for inference, caption target-resolution preprocessing, startup config validation, TorchDynamo, the `backend/ml/device.py` abstraction, and the single GPU thread every load and inference runs on (`run_on_gpu`).

Its siblings: `docs/dev/model-residency.md` covers what keeps a model resident and how its weights leave — eviction, the unload paths, leases and `_release_to_cpu` — and `docs/dev/model-registry.md` covers the model IDs themselves and each model's loader quirks. The subsystems that consume these models have their own files: `docs/dev/detection.md` (object detection), the Quality family that `docs/dev/quality.md` routes to (quality scorers and flags, duplicate detection, style similarity), and `docs/dev/image-processing-models.md` for the pipelines that rewrite pixels — upscaling, LUT grading and LaMa inpainting.

### ML model management

`ml/model_manager.py` is a singleton that tracks loaded models and their VRAM usage. Before loading a model it calls `_evict_lru(needed_mb)` to free space. Each model_id gets its own `asyncio.Lock`, which serializes **loading and unloading** of that id — not inference; what keeps a model resident while something is using it is a lease (`docs/dev/model-residency.md` § Leases). Loads and inference run off the event loop on the single GPU thread (§ One GPU thread, below). Ollama models are not tracked — Ollama manages its own VRAM.

After a successful load, `_registry[model_id]["vram_mb"]` is updated with the measured GPU delta so eviction decisions reflect reality.

`HF_TOKEN` is written into `os.environ` by `backend/services/secrets_service.py::sync_env`, its only writer, so every loader that passes no `token=` picks it up: early in `main.py` from the `.env`/OS-env chain, again in the lifespan from the DB, and on every `PATCH /settings/secrets`. A token saved in Settings → API Keys therefore applies to the next download with no restart — `huggingface_hub` re-reads the variable on every call. See `docs/dev/settings.md` § API Keys tab for the precedence rules.

**EXIF-consistent opening (mandatory for inference)**: every ML inference path must open images through `ml/image_utils.py::open_rgb(path)` — `Image.open().convert("RGB")` + `ImageOps.exif_transpose`. This guarantees all predictors (captioners, quality scorers, SAM2/SAM3, NudeNet) see pixels in the same EXIF-transposed frame, so normalized point/box coordinates denormalize consistently and detection overlays align with the subject on rotated images. Never open with a bare `Image.open(...)` in an inference path; `preprocess_for_caption` itself calls `open_rgb`. Close the returned image right after handing pixels to the model (per the "Close PIL Images after preprocessing" invariant).

The rule is now **enforced**, not just stated: `backend/tests/test_ml_image_opens.py` walks the AST of every module in its `INFERENCE_MODULES` list and fails on an `Image.open`/`PILImage.open` call. That list covered four scorer files while eight more inference paths shipped, and now names all twelve — the four scorers, `nudenet_scorer`, both SAM predictors and all five captioners; a companion test fails when a new `*_scorer`/`*_captioner`/`*_predictor` module is in neither it nor the annotated `NOT_INFERENCE` set, so the next one cannot ship unenforced. It exists because the rule was silently false for seven sites until 2026-07-30 — all four in `aesthetic_scorer.py`, both in `dino_scorer.py`, and `nsfw_scorer.py` — while this paragraph asserted it held everywhere. Nothing had broken, and the reason is worth knowing before trusting a green quality run: this app's images are overwhelmingly generated (PNG/WebP from ComfyUI), which carry no orientation tag, so the bug needs a folder import of phone photos to surface. What it produced there was an *inconsistency*, not a uniform error — `technical_scorer.py` reads through `cv2.imread`, which applies EXIF orientation itself, so on a rotated image the technical scores and the aesthetic/NSFW/DINO scores described pixels in two different orientations within one quality run.

`open_rgb_bytes(image_bytes)` is the in-memory twin, for callers that never touch disk. The pair exists so `extract_clip_embedding_sync` (path) and `extract_clip_embedding_from_bytes_sync` (bytes) cannot drift: both feed the same style-similarity comparison, so transposing in only one makes a reference image uploaded as bytes compare against stored embeddings in a different orientation — a subtler failure than the original, since both sides still return a well-formed normalized vector. Fix or add to one form, do the same to the other.

Two inference-adjacent sites deliberately stay outside `open_rgb`: `ml/lut_processor.py` and `ml/upscaler.py` transpose inline because they are image-*processing* paths that write their result to disk, governed by the `image_service._open_safe` half of the invariant rather than this one.

**Target resolution preprocessing**: `CaptionJobRequest` accepts optional `target_width` / `target_height`. When set, `ml/image_utils.py::preprocess_for_caption()` center-crops each image to the target aspect ratio and resizes it to the exact target resolution before inference. This ensures captions describe the composition the model will actually see at training time. All captioners (Florence-2, PaliGemma-2, JoyCaption, Ollama) call this utility; Ollama's existing `max_px` scale-down runs afterward on the already-cropped image. Omitting both fields leaves behavior unchanged.

**Config validation** (`backend/config.py`): `@model_validator(mode="after")` enforces at startup: (1) `max_vram_mb < 1000` → `ValueError` (fail fast); (2) an `hf_token` absent from the `.env`/OS-env chain → debug-level warning, worded to note it may still be set in Settings → API Keys, since the validator runs before any DB read and cannot see one saved there; (3) unrecognised `.env` keys → WARNING log; `extra="ignore"` retained so OS env vars are never flagged. `config.py` still declares `watermark_threshold` for legacy `.env` compatibility but the quality router reads all six flag thresholds (blur, noise, uniformity, watermark, duplicate, NSFW) from the `threshold_settings` DB table instead.

**TorchDynamo is disabled** (`TORCHDYNAMO_DISABLE=1` set in `main.py`). Triton is unavailable on Windows and single-image inference gains nothing from `torch.compile`, so it is disabled for the entire process. Do not remove this without re-testing all ML inference paths on Windows.

### ML device abstraction

`backend/ml/device.py` centralises all device-detection and device-aware utilities. Every module under `backend/ml/` that touches the GPU imports from here — twelve of them, plus `routers/captioning.py`, `detection.py`, `images.py`, `inpaint.py` and `quality.py`, and `services/image_edit_job.py` and `tag_consolidation_service.py`, the last five for `run_on_gpu`. Five direct `torch.cuda.*` calls survive on purpose and are the exceptions to look for: `torch.cuda.OutOfMemoryError` in an `except` clause in `florence_captioner.py` (twice), `paligemma_captioner.py` and `joycaption_captioner.py`, and `torch.cuda.is_available()` behind sam3's pin-memory probe. Routing those through `is_oom_error()` / a device-level availability check is the tidy-up; until then, "nothing else calls `torch.cuda.*`" is an aspiration rather than a fact. Detection priority: `cuda` (NVIDIA or ROCm, identical API) → `mps` (Apple Silicon) → `cpu`. Key helpers: `get_device()`, `empty_cache()`, `memory_allocated_bytes()`, `memory_reserved_mb()`, `autocast_ctx()`, `safe_dtype_for_device()`, `is_oom_error()`. **`torch` is imported inside each function, never at module scope** — this is the one module the router import chain reaches (`routers/captioning.py` → `model_manager.py` → here), so a module-level import makes `from backend.main import app` require torch, which took down collection of the entire backend suite in CI. Don't "tidy" the per-function imports back to the top; the docstring explains it.

### One GPU thread

**Every call that runs torch on the accelerator goes through `await device.run_on_gpu(fn, *args)`**, which runs it on one process-wide thread (`gpu_executor()`, named `crucible-gpu`). That covers model loads, inference, an upscale and a LaMa inpaint. Never send such a call to asyncio's default pool with `loop.run_in_executor(None, …)` or `asyncio.to_thread`. Every thread that runs CUDA math keeps its own cuBLAS, cuBLASLt and cuDNN handles, plus a cuBLAS workspace (32 MiB on recent cards), until the thread exits. The default pool has up to 32 threads that live as long as the server, and sequential per-image awaits still spread across them. A 625-image scoring run left 3.7 GB on the card after every model had unloaded, against 0.64 GB on one thread. Windows pages that out under pressure; Linux does not (PM-035).

Loaders stay on the GPU thread too: some launch kernels while loading. CPU-only executor work stays on the default pool and keeps its parallelism. That covers the GPU scorers' `prepare_*` halves (decode and preprocess to a CPU tensor, run a few images ahead by `prefetch.run_prefetched`, `docs/dev/quality/scoring-job.md` § The GPU checks prepare images ahead), `technical_scorer`, the WD14 tagger's CPU session, NudeNet, the Ollama and OpenAI-compatible captioners, `tag_embedder.cluster_texts_sync`, LUT grading (`EditSpec.gpu=False` in `services/image_edit_job.py`) and all file, video and thumbnail work. `unload` and `evict_all` still run their `.cpu()` moves on the event-loop thread. `_evict_lru` runs wherever its loader calls it: on the event loop for `load_sam2`, `load_sam3` and `load_lama`, on the GPU thread inside the other loaders and `_ensure_upscaler_loaded`. Either is fine: weight moves are copies and frees, which create no handles, and moving the unloads onto the GPU thread would make them wait behind inference.

Calls queue one behind another. A job's per-image loop loses nothing, and an HTTP inference request such as `POST /quality/embed-references` waits at most for the call in flight. Two costs follow. A first-run download inside a loader (several GB for some models) now holds up every other GPU call until it finishes. And a sync function already on the GPU thread must call other GPU code directly: awaiting `run_on_gpu` from there, or blocking on its result, deadlocks. The thread is one on every device, though the cost it avoids is CUDA's alone; on a CPU-only or Apple (MPS) install it buys nothing, and an HTTP inference request there queues behind a slow CPU inference call it could have run beside.

`backend/tests/test_gpu_executor_guard.py` enforces the rule in CI with a pure AST walk, since CI has no torch. In `backend/ml/`, any executor call outside `device.py` fails unless `ML_CPU_DISPATCHES` names its function with a reason. In `backend/` itself, `routers/`, `services/` and `workers/`, a call off the GPU thread fails when its callable leads into GPU code. That means a module that imports torch, one listed in `GPU_MODULES_WITHOUT_TORCH` (`tag_embedder`, `prefetch`), or a model entry's `.model`/`.processor`. Every torch-free module must be triaged into that list or `CPU_ONLY_MODULES`. The guard follows names, dotted imports, `functools.partial`, lambdas, the local defs a call can see, and local assignments, both arms of an `if`/`else` included. It cannot see through an attribute of anything but an import or a model entry (`spec.process`, which is why `EditSpec` carries its own `gpu` flag), nor through a helper in another non-`ml` module that calls GPU code itself. Rule A exempts `prefetch.run_prefetched` by name and never sees the callable it is handed, so `backend/tests/test_prefetch_halves.py` checks the other side: every `prepare_*` half opens through `open_rgb`, closes the image, and never calls `.to`, `get_device`, autocast or `run_on_gpu` or reads a model, and every `run_prefetched` call anywhere in `backend/` is handed `functools.partial(prepare_*, …)` with nothing bound into it but a model entry's `preprocess` or `processor`, so a model cannot be passed in as the "transform".

**A lazy import moves the failure from import time to call time, and the callers' guards did not follow.** `memory_allocated_bytes()` and `memory_reserved_mb()` document `cpu → 0`, and every caller wraps the *import* — `try: from backend.ml.device import memory_reserved_mb as _vram_mb / except Exception: _vram_mb = lambda: 0` (both captioning loops, three sites in `routers/detection.py`) — but that guard catches nothing on a torch-free install, because importing the *function* succeeds and only the call raises `ModuleNotFoundError`. Both reporters therefore keep `import torch` **and** the `get_device()` call inside their own `try`, so the documented 0 covers "no accelerator" and "no torch" alike. It stayed invisible until `test_caption_empty_guard.py` became the first CI-runnable test to drive a caption job through its VRAM sampling; the repo venv has torch, so only a torch-free venv reproduces it (`docs/dev/video/tests.md` § cv2 in CI describes the same class for cv2). `get_device()` itself still raises on purpose — a caller that genuinely needs a device cannot be handed a fallback.

### One CLIP builder

**OpenAI's CLIP ViT-L/14 is built only by `aesthetic_scorer.build_clip_vit_l14()`**, which
`model_manager._load_aesthetic_sync` and every script that must match the app's stored vectors
call (`dino_embed_offline.py`, `style_crossed_probe.py`). That one model serves the LAION
aesthetic score, the watermark check, `clip_embedding` and `POST /quality/embed-references`.

The weights were trained with QuickGELU, but open_clip's plain `"ViT-L-14"` config uses
`nn.GELU`, and the app ran that way until 2026-11-13. The builder passes
`force_quick_gelu=True`, which loads the same checkpoint file on every open_clip version
`requirements.txt` allows. It then walks the model's modules and raises unless it finds
QuickGELU and no GELU, so a future open_clip that ignored the flag fails at load rather than
quietly writing wrong vectors. Its `quick_gelu=False` switch rebuilds the old model for
`scripts/clip_build_delta.py` alone.

`backend/tests/test_clip_build_guard.py` enforces this with an AST walk: no open_clip model
is built outside the builder, the builder passes `force_quick_gelu`, and no other caller asks
for the old build. The build itself is checked only by hand, since CI has no torch. What the
fix changed, and how the stored values were cleared or re-labelled, is in
[decision 17](decisions/17-clip-quickgelu-fix.md).

### Timing a GPU path

`backend/scripts/bench_score_decode.py` splits each GPU scoring check's time per image into decode, preprocess, the copy to the card and the forward pass, and simulates what preparing images ahead of the GPU thread would gain. No gate runs torch, so it is run by hand on a real card; its module docstring is the manual. It times **instrumented twins** of the scorers' `*_sync` functions, which since T5 compose each scorer's `prepare_*` and `infer_*` halves, and before timing it checks each twin bit for bit against the real function: the tensors into and out of every model, the autocast state, and the returned value. **Change a scorer's per-image steps and its twin there must change too**, or the next run aborts at that check. Its torch-free parts are covered by `backend/tests/test_bench_score_decode_smoke.py`. M10's T4 used it (`docs/dev/throughput-plan/README.md` § T4).
