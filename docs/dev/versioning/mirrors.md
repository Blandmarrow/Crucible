# Snapshot mirrors and the diff

This file covers what a `VersionImageState` row mirrors beyond plain metadata and why each
mirror has the shape it has — the ten scores and the frame-lineage triple, the two join-table
mirrors `label_ids` and `detections`, the mutable qualifiers `scores_stale` and
`aesthetic_model`, and the five provenance columns — and `diff_versions`, which compares
them. CLAUDE.md's mirror invariants are the rule; this is how snapshot, restore and diff
carry it out.

The `version_image_states` table itself is `docs/dev/versioning/storage.md`; the restore
passes that write the mirrors back (Pass 2c, and Pass 3's reconcile) are
`docs/dev/versioning/restore.md`.

## The diff

- `diff_versions(db, dataset_id, v1, v2)` — pure DB, no background job; uses `_DIFF_COLS` column-explicit select for efficiency. Compared fields: `caption_text`, `quality_flags`, `subfolder`, **all ten `*_score` columns** — every one is mirrored on `VersionImageState` and compared; migration `d1c7b4e9f0a3` added the last three (`nsfw_score`, `saturation_score`, `luminance_score`) and says why the earlier carve-out was wrong — `dino_layer_scores`, `generation_metadata`, the five provenance columns (`source_name`, `source_url`, `license`, `attribution`, `source_meta`), `sort_order`, `processing_history`, `scores_stale`, `aesthetic_model`, `label_ids`, `detections` (both detailed below), plus `file` (hash). The list is the module-level **`_DIFF_COMPARE_FIELDS`** tuple, hand-synced with `_DIFF_COLS`: adding a column to `_DIFF_COLS` alone selects it from both versions and then throws it away (which is how `source_meta` was loaded on every diff without ever being compared), while a name in `_DIFF_COMPARE_FIELDS` that is missing from `_DIFF_COLS` is never selected and so silently reports "unchanged". `test_provenance_http.py` asserts the compare list is a subset of the selected columns. The heavy JSON fields in `_HEAVY_DIFF_FIELDS` (`dino_layer_scores`, `generation_metadata` — full ComfyUI workflow payloads — and `source_meta`, a scraper's raw sidecar payload) are compared but reported only as a compact `{"changed": true}` marker, never embedded. `processing_history` changes render as `+`/`−` operation badges in `DiffModal`; `{"changed": true}` renders as "field: changed"; the generic `ChangeRow` renders any other field via `JSON.stringify`.

## Join-table mirrors

- **Labels are mirrored as `VersionImageState.label_ids` and written at the end of Pass 2c**, before the commit that is the DB→filesystem boundary. `create_snapshot` prefetches them with one `label_service.labels_by_image` call (a per-image query inside the state loop would be N+1 over 20k images). The restore keys on **`p.img.id`, not `p.state.image_id`** — Pass 0b can fork a fresh uuid or adopt a different row, and writing the snapshot's id would label an image in another dataset — skips `skip_recreate` plans, resolves ids through `live_label_ids` with one aggregate warning for labels deleted since the snapshot (there is no FK to catch it), and calls `set_labels`, which is an **authoritative replace, not a merge**: a label added after the snapshot disappears exactly as a caption edit does, while `handle_extra_images="keep"` images keep theirs because only ids in `wanted` are touched. A row Pass 0b forks (its image now lives in another dataset) needs no id remapping at all — the payoff of the vocabulary being global. `label_ids` is in `_DIFF_COLS` and `_DIFF_COMPARE_FIELDS` and **not** in `_HEAVY_DIFF_FIELDS`; because the comparison runs on ids, a rename produces no diff, and the ids are resolved to names once per diff (joined to a comma-separated string server-side, so `DiffModal` needs no change; an id with no row renders `(deleted)`). See `docs/dev/label-consumers.md` § Versioning and cross-dataset hooks.
- **Detections are mirrored as `VersionImageState.detections` and written right after the labels** (GPT-026), because their normalized geometry qualifies the pixels exactly as the scores do — restoring older pixels and leaving a later crop's boxes framed the wrong picture. One shape for both directions lives in `detection_service` (`serialize_detection`/`deserialize_detection`: label, bbox, score, model, task, mask, ISO `detected_at` — no ids, no `mask_area`, which the ORM listeners recompute when the restore constructs the row), stored sorted by `canonical_detections` since the diff compares with `!=`. `create_snapshot` prefetches with one chunked `detections_by_image` (a column select, so a dataset's masks never enter the identity map); restore captures each plan row's current list into `_RestorePlan.pre_detections` after Pass 0b (so an adopted row's are the ones read), then calls `set_detections` — the same keyed-on-`p.img.id`, authoritative-replace, only-named-ids contract as `set_labels` — skipping images whose list already matches, so a no-op restore does not churn detection ids.
- **`VersionImageState.detections` is nullable with no server default, unlike `label_ids`**: NULL is "not recorded" (a row older than migration `a6d2e8f4c1b3`) and leaves the image's detections alone, where a `'[]'` default would wipe them on restoring an old snapshot and a backfill would record geometry in the wrong pixel frame. New snapshots always write a list. The diff compares only when both sides are non-NULL and renders each side as a summary (`"3: face×2, hand"`, `"none"`), never the polygons; identical summaries over differing lists get `" (geometry changed)"` (a box or mask differs) or `" (re-detected)"` (only score/model/task/time) on the `to` side. Dataset duplication — from disk or from a snapshot — still does **not** carry detections. Guarded by `backend/tests/test_detections_snapshot.py`, whose structural test pins the `detections=` kwarg in `create_snapshot` and the `set_detections` call in `restore_snapshot`. See `docs/dev/detection.md`.

## Mutable qualifiers

- **`scores_stale` is mirrored *and* diffed, because it is mutable.** `_DIFF_COLS`' carve-out is for immutable frame lineage — written once by extraction, so a comparison is a guaranteed "unchanged". An in-place pixel rewrite between two snapshots flips this column and nothing else, which is exactly the kind of difference the diff exists to show. It must also travel with the scores it qualifies: a restore that brought back stale numbers without the bit would silently present them as trustworthy. See `docs/dev/quality/scores-stale.md`.
- **`aesthetic_model` follows the same rule for the same reason.** It records which of the two aesthetic producers wrote `aesthetic_score`, and it is mutable — a re-score with the other model flips it — so it is mirrored *and* compared rather than falling under the immutable-lineage carve-out. Dropping the mirror would be the sharper failure: a restore would write back a snapshot's LAION score onto a row whose marker still read `v2_5`, so the number and its terms would disagree, silently disarming a guard that gates image *deletion*. See `docs/dev/quality/aesthetic-model.md` § The marker is a safety device.

## Scores and frame lineage

The ten `*_score` columns and the three frame-lineage columns are recent groups, and each
carries a rule. A `*_score` column counts as **authored** data to a snapshot — nothing
recomputes one on restore — so all ten are mirrored *and* diffed, and `NOT_MIRRORED` in
`backend/tests/test_video_lineage_mirrors.py` holds no score. The lineage triple is mirrored
but deliberately **not** diffed, since extraction writes it once and nothing edits it; and
`source_video_id` is the one column a restore cannot write back verbatim —
`VersionImageState` carries no FK while `Image.source_video_id` does, so restore resolves the
snapshotted ids against live `videos` and writes NULL for any that are gone. See
`docs/dev/video/extract.md` § Frame lineage and PM-016.

- **Snapshot rows written before `d1c7b4e9f0a3` were backfilled** for its three columns (`nsfw_score`, `saturation_score`, `luminance_score`) from `images` by `image_id`, so an old snapshot claims *today's* score. That is the only knowable value, and it is exactly what a restore of that snapshot left in place before the migration (the columns were never written back), so behaviour is unchanged and no spurious diff row appears between two pre-migration versions. Rows whose image is gone stay NULL.

## Provenance

**Provenance mirror**: `VersionImageState` mirrors the five `Image` provenance columns (`source_name`, `source_url`, `license`, `attribution`, `source_meta`) — they are set in the snapshot loop's `VersionImageState(...)` construction and written back field-by-field in restore Pass 2c, alongside `generation_metadata` in both, and all five are diffed. `create_snapshot`'s `select(Image)` must carry `options=[undefer(Image.source_meta)]`: that column is `deferred=True`, and the snapshot build reads it, so without the undefer it lazy-loads on an async session and raises `MissingGreenlet`. `restore_snapshot` only assigns it, which triggers no load. Omitting any of them makes a restore silently wipe provenance; `test_provenance.py::test_snapshot_restore_preserves_provenance` guards it. See `docs/dev/provenance.md`.
