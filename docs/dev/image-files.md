# Image files: naming, collisions, moves & caption import

This file covers how image files are named and renamed on disk, cross-dataset moves and copies, and the three paths that bring images and captions in from a folder (import, rescan/sync, standalone caption import). The gallery UI that triggers them is in `docs/dev/gallery.md` and `docs/dev/datasets-page.md`.

### Image file naming

Images receive human-readable names derived from their original filename via `slugify_filename`. Collision handling is done by `unique_filename_with_thumb` (counter suffix `_001`, `_002`, …) in every path that creates or renames an image file with an associated thumbnail — upload, bulk-rename, rename-image, crop new-file, batch-move-subfolder, batch-move-dataset, batch-copy-dataset, rename-on-caption, upscale non-replace, LUT non-replace, and folder rescan (which adopts a name off disk rather than picking one — see § Importing captions & folder rescan). Use `unique_filename_with_thumb` for any new image-creation path; `unique_filename` alone is only appropriate where no thumbnail is involved (e.g. import before thumbnail generation).

**Upload reporting goes through `frontend/src/utils/uploadToast.ts`** — `tallyUpload(results, errors)` folds one or more responses into a tally, `showUploadSummaryToast(tally)` reports it. Both `GalleryPage.handleUpload` and `DatasetsPage.handleCardDrop` (the dataset-card file drop) use it. It exists to enforce one contract: `POST /images/upload` answers `{added, files, videos_added, videos, skipped}` and returns **201 even when it declined a file** — an unsupported or unreadable file comes back as a `skipped: [{file, reason}]` entry, never as an HTTP error, because one bad file must not fail the rest of a multi-file upload. Counting thrown requests therefore reports a rejected upload as a successful one, which is how the two call sites had already drifted: the card reported every dropped file as an uploaded image. The tally keeps `errors` (thrown requests) and `skipped` (server-declined) apart — a network failure and an unsupported type need different wording — and the toast names the reason for the first three skips. `videos_added` counts files routed to the `videos` table instead of `images` (`docs/dev/video.md`); the client-side pre-filter that decides what is worth POSTing is `constants/mediaTypes.ts` (`docs/dev/frontend-core.md` § Frontend constants).

`Image.is_auto_named: bool` (default `False`) — set to `True` when a file is renamed by the captioning job or by a subfolder move. Used to distinguish auto-named files from manually named ones. `PATCH /images/{image_id}/rename` sets it back to `False`.

**Subfolder-based naming**: when `rename_on_caption=True` or when images are moved between subfolders (`POST /images/batch/move-subfolder`) or between datasets (`POST /images/batch/move-dataset` / `POST /images/batch/copy-dataset`), filenames are derived from the target subfolder slug (e.g. images in `"animals"` become `animals.jpg`, `animals_001.jpg`, …; images in root become `image.jpg`, `image_001.jpg`, …). Cross-dataset moves and copies always rename. For same-dataset subfolder moves, renaming is conditional: `BatchMoveSubfolderRequest.rename_on_move: bool = True` — when `False`, only the `subfolder` metadata column is updated and filenames are preserved (the user's preference is stored in `localStorage` under `SUBFOLDER_RENAME_KEY` and read by `SelectionToolbar` at mutation time).

**Cross-dataset moves** (`POST /images/batch/move-dataset`): accepts either `image_ids` (explicit list) or `source_dataset_id + source_subfolder` (moves the whole subfolder). Files are renamed to the target subfolder slug, moved to `{target_dataset.folder_path}/images/`, thumbnails are copied then the originals removed. Calls `refresh_stats` on both source and target after the filesystem operations. **DB is committed before the filesystem operations** so the DB is always the authoritative record of where files should live; if a rename fails mid-batch, already-moved files remain accessible via their new DB paths while not-yet-moved files are temporarily unreachable.

**Cross-dataset copies** (`POST /images/batch/copy-dataset`): same request schema as move. Source images and files remain untouched; new `Image` records are inserted in the target dataset with all metadata copied (scores, captions, flags, generation metadata — deferred blob embeddings are not copied). Uses `copy_with_sidecar` for the image file and `shutil.copy2` for the thumbnail. Calls `refresh_stats` on the target only. **DB inserts are staged before file copies** so that a filesystem failure prevents commit and leaves no orphaned DB records (opposite ordering to move — here an incomplete copy should leave nothing rather than partial records).

**Regression tests**: `backend/tests/test_rename_collisions_http.py` pins rename/bulk-rename placement over HTTP (thumbnail-stem uniquify, sidecar-follows-rename, mixed-suffix distinct stems, the two-phase swap-permutation rename — PM-001 class); `backend/tests/test_move_copy_placement_http.py` pins move/copy file + thumbnail + sidecar placement and both DB-vs-filesystem ordering invariants above under mid-batch fault injection.

Frontend entry points for both: `SelectionToolbar` ("Move to Dataset" / "Copy to Dataset" buttons) and `GalleryPage` subfolder sidebar (arrow icon for move, copy icon for copy). Shared modal: `MoveToDatasetModal` (`frontend/src/components/common/MoveToDatasetModal.tsx`) — accepts an optional `mode?: "move" | "copy"` prop (default `"move"`) which changes the icon, title, and confirm button label. Callback prop is `onConfirm(targetDatasetId, subfolder)`.

### Importing captions & folder rescan

Captions are persisted *out* to `{stem}.txt` sidecars (`caption_service._write_txt_sidecar`) and read *in* via `utils.read_caption_sidecar(image_path) -> str | None`. Three import paths feed captions/images in from disk; all overwrite existing captions and stamp `captioned_by="import"`:

- **Captions during folder import** — `import_images_from_folder(..., import_captions=True)` reads a `{src_stem}.txt` next to each source image and applies it after the copy. Toggled by `DatasetImportWithOptions.import_captions` (default `True`); the Import modal in `DatasetsPage` exposes an "Import captions (.txt sidecars)" checkbox. Returns a summary dict `{added, videos_added, failed_count, failed}` (was a bare `int`) stored in `BackgroundJob.result_data`; the shared `utils/importToast.ts::showImportSummaryToast(jobId)`, called by the import-job completion handlers in both `DatasetsPage` and `GalleryPage`, reads it via `jobsApi.get` and shows `Imported N images and M videos` (the video clause is dropped at zero, so an image-only import reads as before) or, when `failed_count > 0`, a warning `Imported N images · M failed (see server log)`. `videos_added` is only ever non-zero when the import was started with `include_videos` (see `docs/dev/video.md` § Ingest). Per-file failures are logged with `logger.warning(..., exc_info=True)` (no longer silently swallowed); `failed` retains at most the first 50 `{file, error}` details while `failed_count` is the full tally.

  **Per-file I/O** (copy + PIL decode/phash + generation-metadata parse + thumbnail) runs off the event loop via a single `run_in_executor(_ingest_file_sync, ...)` hop so a large import doesn't stall other requests/SSE. The directory walk and the source-size sum share **one** `run_in_executor(_scan_source_files, …)` hop before the loop: `is_file()` already stats every entry, so summing in the same pass is free, and neither an `rglob` over a deep tree nor N `stat()` calls belongs on the event loop. The total then goes through `utils.require_free_space(dataset.folder_path, …)` (the local `_file_size` treats a vanished file as 0) so a too-small disk fails the job with a readable `error_msg` instead of leaving a half-imported folder — the same helper the export loop uses, see `docs/dev/export.md` § Disk-space preflight.
- **Folder rescan / sync** — `rescan_dataset(db, dataset, job_id, import_captions=True)` walks `{folder_path}/images` and reconciles **by `filename` alone** (unique per dataset via `uq_dataset_filename`). Endpoint `POST /datasets/{id}/rescan`; `job_type="rescan"`.
  - **Never derive subfolder from the on-disk path.** Image files are always stored flat in `images/` — `subfolder` is a purely logical DB column, never reflected on disk — so deriving it would mis-key every subfoldered image, hit the unique constraint on commit, and fail the whole job.
  - **Reconciliation**: files on disk absent from the DB are registered at root (`subfolder=""`, thumbnail via `thumbnail_path_for`, sidecar caption; the decode/metadata/thumbnail work runs in a `run_in_executor(_register_file_sync, ...)` hop); existing rows pick up changed/added sidecars (compared against the stripped stored caption to avoid re-stamping provenance on whitespace-only diffs); DB rows whose file is gone are **reported (never removed)**.
  - **Rescan is the one path that renames a file it did not create.** Thumbnails are `.webp` keyed by stem, so `a.png` and `a.jpg` hand-dropped into `images/` both resolve to `{dataset}/thumbnails/a.webp` and the second written clobbers the first, leaving two rows sharing one picture. Every other creation path avoids this by picking a free name through `unique_filename_with_thumb`; rescan adopts the name off disk, so it runs the adopted name through the same helper and renames the loser to `a_001.jpg` before registering it. **`disk_exclude={f.name}` is mandatory** — the file is already sitting in `images/`, so without it the uniquifier sees every file's own name occupied and steps all of them to `_001`. The `.txt` sidecar deliberately does **not** move with it (the sanctioned exception to the `rename_with_sidecar` rule): the two files share a stem, so one `a.txt` belongs to both equally, and the caption is read before the rename either way. Only flat `images/` files are disambiguated — a nested file is already mis-keyed by the filename-only reconcile above and `thumbnail_path_for` resolves it to the wrong directory, so guarding on `f.parent == images_dir` leaves that untouched rather than half-fixing it.
  - **It renames the file, where video rescan renames the poster** (`docs/dev/video.md` § Poster stems and collisions). The asymmetry is load-bearing: eleven sites re-derive an image's thumbnail path from its filename, so an image whose thumbnail stem drifted from its own would have that thumbnail orphaned by the next rename, move, copy, crop or restore. Nothing re-derives a poster path — every consumer reads `Video.poster_path`.
  - **Result**: `{added, renamed, captions_updated, missing, total_on_disk, failed_count, failed}` (same failure-reporting fields as import), stored in `BackgroundJob.result_data` and surfaced as a toast. `renamed` is reported rather than silent because rescan otherwise never touches a file — both the `DatasetsPage` and `GalleryPage` toasts name it.
  - **The endpoint dedupes**: if a pending/running rescan job for the same dataset already exists it returns that job's id instead of creating another — auto-rescan-on-open fires on every gallery mount (the "already rescanned" guard is a per-mount ref), so without this, duplicate rescans pile up behind any long-running job in the serial queue (two *simultaneous* requests can still race past the check; sequential ones cannot).
  - **UI**: a per-card "Rescan folder from disk" button in `DatasetsPage`, a **"Rescan" button in the `GalleryPage` toolbar** (next to Upload), and an auto-rescan-on-open in `GalleryPage` gated by the `auto_rescan_on_open` setting (off by default — see `docs/dev/settings.md`). In `GalleryPage` the manual button and the auto-on-open path share one `runRescan(manual)` helper + `rescanJobId` state; a `rescanManualRef` decides whether to show the `jobsApi.get`-fetched summary toast (manual only — auto rescans invalidate silently).
- **Standalone caption import** — `import_captions_from_folder(db, dataset, folder_path, job_id)` matches each `*.txt` in a folder to an image by stem (`original_filename` stem first, then `filename` stem) and overwrites. Returns `{matched, unmatched}`. When several images share an `original_filename`/`filename` stem only the first (`setdefault`) is matched. Endpoint `POST /datasets/{id}/import-captions`; `job_type="import_captions"`. UI: per-card "Import captions" button → modal with a folder-path input.

The `GalleryPage` toolbar also carries an **"Import folder" button** (next to Rescan/Upload) that opens the shared `ImportFolderModal` for the current dataset, so folder import is reachable without returning to `DatasetsPage`. See `docs/dev/datasets-page.md` for `ImportFolderModal` and the in-app `DirPickerModal` Browse button.

**Drag a `.txt` onto an image** sets that image's caption (issue #47 approach 2). In `ImageCard` (gallery grid) the card's `onDragOver/onDrop` only intervene when the drag carries a `text/plain` (or empty-type — Windows/some browsers report `.txt` with no MIME type) file and `stopPropagation()` so a `.txt` is consumed as a caption while image-file drops still bubble up to the gallery grid's upload drop zone; in `ImageDetailPage` the caption `<textarea>` accepts a `.txt` drop. Both read the file client-side and call `captionsApi.update(imageId, { caption_text })` (the `PUT /captions/image/{id}` endpoint), then invalidate `["images", datasetId]` (and `["caption", imageId]` in the detail view).
