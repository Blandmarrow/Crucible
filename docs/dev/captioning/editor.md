# Caption editor: the detail page's caption panel

This file covers the caption editor on `ImageDetailPage`: the textarea and its token counter, the image-keyed draft and the rule every async caption writer follows, the Generate with AI and Fix modes, and the helpers that edit only the unsaved draft, starting with the *Other captions* panel. The rest of the detail page, from the crop tool and labels to generation metadata and style match, is in `docs/dev/image-detail.md`. Caption jobs themselves, and the `{previous_caption}` placeholder Fix mode relies on, are in `docs/dev/captioning/jobs.md`.

## ImageDetailPage caption panel

**ImageDetailPage caption panel**: Contains only the caption text textarea and Save button (plus the collapsible AI Generate section). The `caption_style` field is still present in the DB schema, the `PUT /captions/image/{id}` endpoint, and the save mutation — read from `captionData` and re-persisted unchanged — but no style picker is exposed in the UI. The `tags_json` column and `tags` table were removed by migration `a8c3e1f2b9d0_drop_tags_system`; `TagEditor.tsx` and the panel's `tags` state are deleted accordingly. A live **token counter** (`N words · N tokens`) is displayed right-aligned beside the "Caption Text" label. The token count comes from `utils/tokenCount.ts::useTokenCount`, which lazily one-time `import()`s the GPT-2 (`r50k_base`) encoder from `gpt-tokenizer` so that sizeable encoder chunk stays out of the page's static graph; this also aligns the client count with the backend `caption_token_count` (`backend/utils.py::count_caption_tokens`, a GPT-2 tiktoken encoder). The word count shows immediately; tokens render as `…` until the encoder resolves, then recount as `captionText` changes. The counter turns amber at ≥ 70 tokens and red at ≥ 77 to signal the CLIP truncation limit.

**Caption textarea auto-resize**: The textarea auto-expands to fit its content via a `useLayoutEffect` keyed on `[captionText, imageId, image?.id]`. Measuring sets `height: auto` for a moment, which lays the page out shorter: a right-hand panel scrolled near its bottom had its scroll clamped, and the caption jumped under the pointer on every keystroke and synonym swap. So the measurement runs inside `utils/keepScroll.ts::keepScroll`, which puts every scrolled ancestor back, and as a layout effect, before paint. `frontend/e2e/detail-synonyms.spec.ts` pins it with a long caption in a short window (573 → 291 without it). Three dependencies are required: (1) `captionText` — resize when the text changes; (2) `imageId` — resize immediately on navigation (covers same-text-on-two-images edge case); (3) `image?.id` — the critical one: the component has an early return `if (imageLoading || !image) return <Loading/>`, so the textarea is not in the DOM while the image query is pending. `captionData` (the lighter query) typically resolves before `image`, so `captionRef.current` is null when `captionText` first changes on a fresh navigation. Adding `image?.id` ensures the resize fires again once the loading phase ends and the ref becomes valid. Do not remove any of these three dependencies.

**The caption draft is keyed to its image** (GPT-027). The only caption state is `draft: { imageId, text } | null`, set by the textarea's `onChange`. Everything else is derived in render: `captionDirty` is `draft.imageId === imageId`, `captionText` is the draft while dirty and `captionData.caption_text` otherwise, and `captionStyle` is always `captionData.caption_style`, since no picker edits it. The page used to copy `captionData` into state with a copy-unless-dirty effect plus a reset-on-id effect. Arrowing to a neighbour whose `["caption", id]` query is warm changes `imageId` and `captionData` in the **same** render, so the copy effect saw the stale dirty flag and skipped. The unsaved draft then sat on the neighbour, and Save wrote it there. Do not reintroduce a copy of `captionData` into state. Keeping the draft keyed also means a same-image refetch, such as `TopBar`'s per-row caption invalidation during a job, cannot clobber typing. A cleanup-only `[imageId]` effect still drops a draft on leaving its image. That keeps the old discard-on-navigate behaviour, but correctness does not depend on it.

**Every async caption writer keys on the id it started with, never on the render's `imageId`.** The writers are Save, the `.txt` drop, **Merge redundant tags** and the AI job. The first, third and fourth pass the id, text and dataset as mutation **variables**, and the drop captures them in locals. This matters because TanStack v5's `useMutation` pushes every render's options onto a pending mutation (`MutationObserver.setOptions` → `mutation.setOptions`). A hook-level `onSuccess` closure therefore sees the image the user has navigated *to*. On success, Save and the drop `setQueryData(["caption", id], result)` first, so the editor never flashes the pre-save text. They then clear the draft only if it is still the text that was written, so a draft on another image, or typing that continued during the request, survives. The AI job is tracked as `aiJob: { jobId, imageId, datasetId }`. Its completion effect invalidates that image's caption, and its progress bar and `aiRunning` are gated on `aiJob.imageId === imageId`. `frontend/e2e/caption-edit.spec.ts` covers the warm neighbour, a cold control and a save that lands after navigating away.

The **AI Generate** collapsible (`showAi` state, gated `enabled: showAi`) uses the same four-model-type picker pattern and `resolveModelId` helper as `SelectionToolbar`. WD14 models show only the threshold slider and hide `PromptPresetManager` and `ResolutionPicker` (both are wrapped in `{aiModel && !aiModel.startsWith("wd14:") && (...)}` — keep this consistent with `SelectionToolbar`'s ternary). The Custom Prompt box is gated on `takesPrompt(aiModel)`, since Florence-2 and PaliGemma-2 ignore a prompt. Generate always sends `overwrite: true`; there is no overwrite checkbox. The `["captioning-models"]` query is defined at component level (not inside the collapsible) but gated on `enabled: showAi` to avoid loading until the section is first opened.

**Fix mode** (#105). An `aiMode: "generate" | "fix"` switch heads the panel. Fix shares the model picker and `ResolutionPicker`, hides the style, prompt, preset and delimiter controls, and adds a note box (`fixNote`). Its button is disabled unless the model is `takesPrompt`, the note is non-blank and the caption box is non-blank. `fixMutation` follows the async-writer rule above: id, dataset, text, style and dirty flag travel as variables. When the draft is dirty it first `PUT`s it and calls `settleCaptionWrite`, because the backend fills `{previous_caption}` from the **stored** caption and the model must see the text the user sees. Then it sends a single-image `/run` with `buildFixPrompt(note)` from `constants/captionModels.ts`, `overwrite: true`, `delimiter_mode: "overwrite"`, `append_tags: false` and the stored `caption_style` (`"detailed"` when blank). See `docs/dev/captioning/jobs.md` § The `{previous_caption}` placeholder. The job reuses `aiJob`, with an extra `undoText`, the caption the fix replaced. The completion effect turns it into `fixUndo: { imageId, text }`, and an **Undo fix** button under Save puts that text back as a draft, unsaved, while the box differs from it. Every later caption write to that image drops `fixUndo` (`dropFixUndo`): Save, the `.txt` drop, merge-tags and the start of either AI job. Otherwise Undo would revert work newer than the fix.

**A completed caption job is not a successful one** (PM-023). `/run` ends `completed` when its one image timed out, hit a 429 or came back empty, and carries the loss on the `caption_summary` event's `failed_count`, which the job store has merged by the time the status turns terminal. The completion effect checks it: a failure toasts `failure_summary` (or "The fix failed" / "Captioning failed"), keeps the draft and arms no Undo. **One AI job at a time**: both run buttons are disabled on `aiBusy`, an `aiJob` that is not yet terminal on *any* image, `pending` and not-yet-seen included, as upscale and LUT do. A second click would replace `aiJob`, and the first job's completion would then refresh nothing. The running label (`aiRunningLabel`) follows the job's kind, not the mode on screen. Generate does not save a dirty draft first, so its prompt hint says `{previous_caption}` is the *saved* caption. `frontend/e2e/detail-caption-fix.spec.ts` pins the request body, the save-before-run order, the disabled states and, against a provider that refuses the connection, the failed-fix path.

## Other captions panel

`components/caption/OtherCaptionsPanel.tsx` (#45), mounted between *Merge redundant tags* and *Generate with AI*, lists up to 8 other images from the same dataset with how they were captioned. It is read-only: one route, `GET /images/{image_id}/similar-captions?by=tags|objects|clip|recent&limit=8`, whose body is `services/similar_captions_service.py`. Candidates are always captioned, in the image's own dataset, and never the image itself. `tags` scores the terms a candidate shares with this caption by idf, `log((N+1)/(df+1)) + 1`, so a tag on every image (`1girl`) counts for little; a caption is tag-like when it has two or more comma parts, most of them four words or fewer, and otherwise it is matched on words, minus a stoplist. `objects` runs the same score over detection labels, `clip` is a cosine over the stored vectors, and `recent` orders by `captioned_at`. When a mode cannot run for this image, the route answers `available: false` with a `reason` the panel shows.

The two dataset-wide scans, `tags` and `clip`, are one streamed pass each, pinned to `STATS_SCAN_INDEX` for decision 15's reason; `_scan`'s docstring has the timings. Unpinned keyset pages re-sorted the dataset per page and took 15 s at 100k rows; pinned, a `tags` request takes about 0.9 s and `clip` 0.5 s there. Only the winners' spellings are worked out, by `_terms_with_spelling`; the hot loop is `_shared_terms`.

The query key is `similarCaptionsKey` in `constants/queryKeys.ts`, deliberately **not** under `["images", ds]`: `TopBar` invalidates that prefix every couple of seconds during a caption job, and each refresh would rescan the dataset. So the page's five caption writers (Save, Fix, merge-tags, the `.txt` drop and the AI job's completion) invalidate `similarCaptionsScope` themselves; a new caption writer on this page must too. The fetch waits 300 ms after the image opens and passes the query's abort signal, so arrowing through images starts no scan per image passed over. The tags score is also divided by the square root of the candidate's term count, so a 150-tag caption does not win on chance overlaps. **Add N tags** writes the unsaved draft through `setDraft`. It is synchronous, so the async-writer rule above does not apply, and it is offered only for a tag-like candidate whose current caption is tag-like, a single short tag or blank (`canTakeTags`), since a prose caption's comma parts are not tags. The chip counts shared tags against the live draft, as the highlights do. **Open** is Style match's `paneGo`, so on an image outside the gallery's nav list ← / → are disabled, as they are there. `captionTags.ts` mirrors the server's tag rule for the highlights and the missing-tag count. Open and mode persist in `OTHER_CAPTIONS_KEY`.

## Check tags

`components/caption/CheckTagsPanel.tsx` (#50), mounted between *Merge redundant tags* and *Other captions*, looks the caption's tags up on Danbooru through `POST /booru/check` (`docs/dev/workspace.md` § Booru tag lookup page for the router and `_danbooru_get`). It renders only while `looksLikeTags(captionText)` holds, since a prose caption's comma parts are not tags, and its key is prefixed (`check-tags-${image.id}`) because `OtherCaptionsPanel` is a sibling keyed on the bare id.

**It runs on a press only, so it is a `useMutation`, never a `useQuery`.** The check sends the caption's tags to danbooru.donmai.us, and a query would refetch on mount, focus or reconnect, each time sending them again without being asked. The result lives in the mutation, so it dies with the panel, and the panel's key makes that happen on every image change. A check still in flight when the user arrows away lands on an unmounted panel and is dropped.

**The service, `booru_service.check_tags`, makes two batch requests whatever the caption's length, plus at most eleven for suggestions** — the batch params were measured against Danbooru on 2026-11-14:

- `tags.json` with `search[name_comma]` for every name, and `tag_aliases.json` with `search[antecedent_name_comma]` and `search[status]=active`. Danbooru leaves an unknown name out of the reply. These two raise `BooruUnavailable`, so an outage is a 502 and never every tag "not found", which was the user's condition for the feature.
- For the flagged tags only — no alias and under `RARE_POSTS` (100) posts — capped at `MAX_SUGGESTED` (10): one more `name_comma` batch for each tag's variants (each word dropped once, singular/plural) and the alias targets, plus one `autocomplete.json` per tag (`search[type]=tag_query`), which corrects typos (`schol_uniform` → `school_uniform`). `search[fuzzy_name_matches]` was tried and returns only the tag itself. This step only degrades: a failure, or a flagged tag past the cap, sets `suggestions_complete: false`.
- Each name, alias and autocomplete answer is cached in the module's 5-minute `_cache`, misses as `False`, so a repeat check sends nothing.

The status rules are the user's (2026-11-14): `alias` wins; `missing` is no tag or 0 posts (an alias's antecedent often keeps a 0-count row); `rare` is under 100 posts **and** a candidate with at least `RARE_RATIO` (100) times more, else the tag is `ok`, since a niche tag is still a real one. A rare tag whose neighbours could not be looked up stays `rare` with no suggestion: undecided, not fine. Parts are normalised as Danbooru names (`normalize_tag`: `\(` unescaped, lowercase, whitespace to `_`), while each result carries `input`, the part as written.

**Replace finds the tag by its text, not its index** (`captionTags.ts::replaceTag`): the user may edit the box between the check and the press, so an index could hit the wrong part. The first exact match wins, then the first `normTag` match; when the tag is gone the button disables. The name goes in the caption's style — underscores only if that part used them, parens escaped if the caption escapes them — keeping the part's surrounding whitespace. It writes the unsaved draft through `setDraft`, synchronously, so the async-writer rule does not apply, and it saves nothing. `frontend/e2e/detail-check-tags.spec.ts` fakes the route and pins press-only, the order, Replace and the outage message; `backend/tests/test_booru_check.py` pins the rules against a fake Danbooru.

## Synonym card

`components/caption/SynonymCard.tsx` (#52) sits directly under the textarea, inside its wrapper, so it appears where the selection is. It shows only while Settings' *Synonym suggestions* is on (`uiPrefsStore.synonymsEnabled`). The dictionary behind it, the install and the lookup are in `docs/dev/captioning/dictionary.md`.

**The selection is state stamped with its image, and the card is derived from it.** The textarea's `onSelect` stores `synSel: { imageId, span }`, where `captionWords.selectedWord` trims what a double-click or a loose drag picks up and enforces the server's limits (4 words, 40 characters, letters). `synSpan` is that span only while `synSel.imageId === imageId` **and** the caption still holds `span.text` at those offsets. So a swap, typing, an AI result, Save or arrowing to another image closes the card, with no effect to clear it. React's `onSelect` follows mouseup and keyup, not a bare `setSelectionRange`, which is why the e2e helper ends a selection with a Shift press.

**A collapsed caret never closes the card; only a new word replaces it.** The first press of a double-click collapses the old selection before the second press selects the new word. Closing the card there made the right-hand panel shorter between the two presses: scrolled near the bottom, its scroll clamped, the caption moved under the pointer, and the second press landed on a different word. For the same reason the lookup keeps the previous list on screen while the next word loads (`placeholderData: keepPreviousData`), dimmed, `aria-busy`, with its chips disabled because they belong to the old word, rather than collapsing to a one-line *Looking up…*. Typing closes the card explicitly in `onChange`, since a caret move no longer does.

**A swap is guarded the way Replace is.** `captionWords.replaceSpan` writes only if the span still holds its text, and otherwise the chip disables. It writes the word styled after the word the user *selected* (`styleFrom`): all caps, an initial capital, and underscores when the selection used them, so a run of swaps keeps one style. The word goes in as WordNet spells the base form, and the header says when the lookup used a base form ("words for goose"), so the user can re-inflect it by hand. It writes the unsaved draft through `setDraft`, synchronously, so the async-writer rule does not apply and nothing else needs invalidating.

**A swap keeps the card open on the same list and re-points it.** `synSel` holds two things: `word`, what the user selected, which the card looks up, and `span`, where the current word sits. `onSwap` moves `span` onto the new word and leaves `word` alone, so the list is never looked up again; the current chip shows `aria-pressed`, and **Put back** restores the selected word. Both halves matter. Closing the card on a swap shrank the panel, its scroll clamped and the caption jumped under the pointer, the same failure as between a double-click's two presses. And a span left on the old text after "blond" → "blonde" still matches at its old offsets, so a second swap wrote "blondee". The chips and Put back `preventDefault` their mousedown so focus never leaves the textarea: a button that took focus and then unmounted dropped it on `<body>`, where the next ArrowRight went to the window listener and stepped to the next image, discarding the draft. The caret goes after the new word on the next animation frame, once React has written the value, with `focus({ preventScroll: true })` so focusing cannot scroll the panel either.

**Closing.** Esc in the textarea closes the card through its own `onKeyDown`; the page's window listener already leaves a text field's Escape alone. Esc inside the card calls `stopPropagation`, so the annotation-mode Escape does not fire as well. A click outside both the card and the textarea closes it. That is a document `click` listener, tested against the event's `composedPath()` rather than `contains()`: Put back unmounts itself as it is clicked, and a detached target would read as a click outside. It is not the textarea's blur, which fires before a chip's click and would close the card under the pointer. It is not `pointerdown` either: the card sits above Save, so closing it at pointerdown moved Save up before pointerup and the click never reached it.

**The lookup is a query, unlike Check tags' mutation**, because nothing leaves the machine. The key is `synonymsKey(word)`, with `staleTime: Infinity`; it is debounced by 150 ms, so a drag does not send one request per letter, and it is enabled only when `useDictionaryStatus` says the dictionary is installed. Without one, the card shows the install state and a download button. `frontend/e2e/detail-synonyms.spec.ts` fakes the routes and pins the double-click, the card holding its size across a collapsed caret and a loading word, the case-keeping swap, chained swaps and Put back on one list at one size, focus and the caret after it, Save with the card open, underscores, Esc, off-by-default and the not-installed path.
