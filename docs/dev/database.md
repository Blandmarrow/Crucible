# Database: SQLite engine, schema conventions, backups and migration drift

This file covers the SQLite engine and the schema conventions every model follows: WAL and the per-connection pragmas, foreign-key enforcement and every `ondelete`, virtual subfolders, the images and videos index inventories, UTC datetime serialization, dataset-folder deletion and the startup orphan sweep, deferred blob columns, the migration drift check, and the startup database backup. The running process — the lifespan hook, SSE and the job queue — is in `docs/dev/backend-infrastructure.md`, and server control and the restart loop in `docs/dev/http-edge.md`. The versioning tables' own semantics are in `docs/dev/versioning/storage.md`, and the frame-lineage FK in `docs/dev/video/extract.md` § Frame lineage.

## SQLite engine and schema conventions

SQLite in WAL mode (`synchronous=NORMAL`). ORM models live in `backend/models/`. Alembic migrations in `backend/alembic/versions/`. The Alembic `env.py` strips `+aiosqlite` from the URL when running synchronous migrations.

**`backend/config.py` sets `OPENCV_FFMPEG_LOGLEVEL=-8`** with `os.environ.setdefault` at module scope, and the *position* is load-bearing: it must be set before the first `cv2` use, which config is guaranteed to precede. Rejecting a file is a normal outcome for the video probe, and each rejection otherwise prints libavformat's `moov atom not found` to stderr; `cv2.utils.logging.setLogLevel` does not suppress those. `setdefault`, so an operator can override it. See `docs/dev/video/decode.md`.

**Per-connection pragmas / foreign-key enforcement**: `foreign_keys` and `synchronous` are *per-connection* SQLite settings (not persisted in the DB file), so they are applied in a `@event.listens_for(engine.sync_engine, "connect")` listener in `backend/database.py` that runs `PRAGMA foreign_keys=ON` and `PRAGMA synchronous=NORMAL` on every new DBAPI connection. `journal_mode=WAL` is persistent per-DB-file and stays a one-time `init_db()` call. **FK enforcement is ON**, so `ondelete` clauses actually fire: `images.dataset_id` → `CASCADE` (with `passive_deletes=True` on `Dataset.images`, so `delete_dataset` issues a single DELETE and the DB cascades images → `detections` also `CASCADE`); `videos.dataset_id` → `CASCADE` likewise (`passive_deletes=True` on `Dataset.videos`, mirroring `Dataset.images`); `background_jobs.dataset_id` → `SET NULL` (deleting a dataset keeps its job history, nulling the link); the versioning tables already cascade (`dataset_branches`/`dataset_versions`/`version_image_states` on `datasets`/`dataset_versions`). Of the intra-versioning links, only `dataset_versions.branch_id` has a real DB-level FK (`SET NULL`, created by migration `a2b3c4d5e6f7`); `dataset_versions.parent_id` and `dataset_branches.head_version_id` were created as **plain columns** in that migration (no FK), so their model-level `ForeignKey` declarations are decorative (the schema comes solely from Alembic, never `create_all`). Consequence: deleting a version leaves any children's `parent_id` dangling — harmless, it's informational only — and branch-head reassignment on delete is handled in code by `delete_version` (`backend/routers/versioning.py`), not by the DB. Migration `f7e8d9c0b1a2` purges pre-existing orphans and recreates the two enforced FKs (`images.dataset_id`, `background_jobs.dataset_id`; SQLite requires `batch_alter_table` table-recreates for FK changes). The Alembic migration engine keeps `foreign_keys` OFF (env.py doesn't enable it), which is required for batch recreates.

**Subfolders** (`Image.subfolder`, `Dataset.declared_subfolders`): images are physically flat in `{dataset.folder_path}/images/`; `subfolder` is pure string metadata (empty string = root/ungrouped; nested paths use `/`). `Dataset.declared_subfolders` (JSON column, default `[]`) stores explicitly-created subfolder paths so empty subfolders survive a `list_subfolders()` call — that function GROUP BYs images, so any path not in `declared_subfolders` with zero images would disappear. `declare_subfolder()` adds a path; `delete_subfolder()` bulk-moves images to root and removes the declared entry. `normalize_subfolder()` in `backend/utils.py` sanitizes path strings before storage, stripping the whitespace around each segment (§ Folder paths are stored stripped (migration b8d2f4a6c1e3)). API: `GET/POST/DELETE /datasets/{id}/subfolders`.

**`fk_images_source_video_id_videos`** (`images.source_video_id` → `videos.id`, `ON DELETE SET NULL`) is the one FK this branch added, and belongs in the inventory above: deleting a source video must never destroy the frames curated from it. `ondelete` covers only deleting the *parent*, though, and an UPDATE onto a missing parent key still raises — which is what PM-016 turned into an incident, invisible to the suite because the harness leaves the pragma off. See `docs/dev/video/extract.md` § Frame lineage.

Images-table indexes (spread across several migrations; **every** one is now model-declared too — `ix_images_dataset_id`, `ix_images_phash`, `ix_images_file_path`, the eight composites in `__table_args__` and `uq_dataset_filename` — so the table carries zero allowlisted index drift in `scripts/check_migrations.py`): from the initial migration (`5acbb04f2f10`) — `ix_images_dataset_id` on `dataset_id`, `ix_images_dataset_aesthetic` on `(dataset_id, aesthetic_score)`, `ix_images_dataset_blur` on `(dataset_id, blur_score)`, `ix_images_phash` on `phash`, and the `uq_dataset_filename` unique constraint on `(dataset_id, filename)`; from the performance-index migration (`a1b2c3d4e5f6`) — `ix_images_dataset_created_at` on `(dataset_id, created_at)` (gallery sort), `ix_images_file_path` on `file_path` (filesystem lookups), `ix_images_dataset_caption` on `(dataset_id, caption_text)` (caption filter + listing); plus `ix_images_dataset_similarity` on `(dataset_id, style_similarity_score)` (`bdd17cfef66d`), `ix_images_dataset_subfolder` on `(dataset_id, subfolder)` (`f3a9b2c1d4e7`), `ix_images_dataset_sort_order` on `(dataset_id, sort_order)` (`a3b4c5d6e7f8`), `ix_images_dataset_caption_tokens` on `(dataset_id, caption_token_count)` (`d9f4a1c7b2e8`, the migration that also adds the persisted `caption_token_count` column and backfills it from existing captions — see `docs/dev/shared-utilities.md` for the `caption_text` sync listener), `ix_images_source_video_id` on `source_video_id` (`a7c3e5b1d9f2`, the frame-lineage migration), and `ix_images_source_video_timeline` on `(source_video_id, source_timestamp_ms)` (`c8a1d3f5b7e2`, for the gallery's "Video timeline" / "Shot order" sorts — see `docs/dev/gallery/filters.md` § Sorting; it makes the single-column lineage index a redundant prefix, kept because dropping it touches the delete-video NULLing UPDATE and `frames-summary`). Thirteen indexes plus the unique constraint.

Videos-table indexes: `ix_videos_dataset_id` and the `uq_dataset_video_filename` unique constraint on `(dataset_id, filename)` from `c1d4f7a2b9e3`, plus `ix_videos_file_path` on `file_path` (`e2f9a4c6d8b1`) — the twin of `ix_images_file_path`, for the same read pattern: `routers/filesystem.py` asks "is there a row at this exact path?" once per affected file on every move, rename and delete, and without it each of those was a full scan of `videos`. That holds on Linux. On Windows and macOS the file arms match with `utils.sql_path_equals`, a case-blind `LIKE` that cannot use either index (PM-034), so each request scans once, beside the prefix `LIKE`s the same routes already run. Declared on **both** the model and the migration deliberately, so it needs no `ACCEPTED_DRIFT` entry. The images side has since caught up the same way (see the "every one is now model-declared" claim above) — a model-side declaration that names the index the migration already created takes no migration and no schema change, only the deletion of its allowlist line.

**Datetime serialization (UTC on the wire)**: all timestamp columns are stored **naive UTC** via `datetime.utcnow()`. A naive datetime serializes to JSON with *no* timezone suffix, which the frontend's `new Date(...)` then parses as *local* time — shifting every displayed timestamp by the browser's UTC offset (this was the "job ran 3h ago" bug). Fix: **every `datetime` field on an API response schema must use the `UtcDatetime` type** from `backend/schemas/__init__.py` (a `PlainSerializer` that attaches `+00:00`), never bare `datetime`. This makes the wire format unambiguously UTC. Applies to any new schema field or any router that hand-builds a response dict — route it through a schema with `UtcDatetime`, or attach UTC before `.isoformat()`. Exception: `filesystem.py`'s `modified_at` comes from `datetime.fromtimestamp(st_mtime)` (local naive) and is *intentionally* left naive so the file browser shows local file-modification times.

**Dataset-folder deletion & the startup orphan sweep**: deleting a dataset is DB-first — `delete_dataset` (`routers/datasets.py`) removes the row and commits, then removes the on-disk folder via `remove_dataset_dir(folder)` (`services/dataset_service.py`). That helper replaces the old `shutil.rmtree(..., ignore_errors=True)`: it uses `rmtree`'s error callback (with an `onexc`/`onerror` fallback so it works on Python ≥3.12 and older) to **log a warning** naming exactly what couldn't be removed, instead of silently swallowing a partial delete. Because folder cleanup is bolted onto the row-delete path, a folder is orphaned whenever a dataset row disappears by another route (DB reset/migration/swap, manual edit). `sweep_orphan_dataset_folders(db)` reconciles this at startup: the `lifespan` hook in `main.py` calls it (via `_sweep_orphan_dataset_folders`, after `init_db()` and the two job-table passes — `mark_interrupted_jobs()` then `_sweep_old_jobs()` — and before `job_queue.start()`, which is the load-bearing half), and it handles every child directory of `settings.datasets_dir` whose resolved path is not referenced by any `Dataset.folder_path` (the two job-table passes are described in `docs/dev/backend-infrastructure.md` § Stale job cleanup at startup and § Job retention sweep). It runs before any job starts, so no job is writing into a folder the sweep is judging. `create_dataset` makes the empty folders just before its single commit, so a crash between the two leaves an empty shell with no row, and every import or upload fills a folder only once its row is committed. Keep both properties if you touch that path: the sweep's rules below rely on them. `remove_dataset_dir` no-ops safely on a missing path.

**The sweep moves data aside and never deletes it** (M9 stage 2, `docs/dev/scale-plan/README.md`). "No row" does not mean "abandoned": restoring an older database backup (`db_maintenance`'s own copies) leaves every dataset created since without a row, and a folder copied in by hand has none either, and the old sweep `rmtree`'d all of them. Now each unreferenced folder goes to `datasets_dir/.orphaned/<name>-<YYYYmmdd-HHMMSS>` (UTC, one stamp per sweep, `-2`, `-3`… on a taken name) through `utils.rename_retrying`, a same-volume rename that is instant at any size, and one warning names every move. The rules that keep it safe, each pinned in `backend/tests/test_orphan_sweep.py`:

- **Only a tree proven empty is deleted, and never with `rmtree`** (`_empty_tree_dirs`): a failed create's empty shell is removed one `os.rmdir` at a time, deepest first, rather than piling up in `.orphaned`. `os.rmdir` refuses a folder that is not empty, so a file written after the walk (a sync client, a stray second install) stops the delete instead of going with it. A link anywhere counts as content and is never followed: a symlink, or a **Windows junction**, which `os.path.islink` does not report and `os.walk` walks into, hence `_is_link`'s `os.path.isjunction`. So does anything `os.walk` cannot read, because the walk silently skips an unreadable folder and would otherwise call its tree empty.
- **A folder the rows name by another spelling is kept**: besides the string match (case-folded under `PATHS_FOLD_CASE`, § The datasets root's one spelling), a child whose `(st_dev, st_ino)` matches an existing row folder is known. That catches a case-insensitive mount where `PATHS_FOLD_CASE` is False, and macOS storing an accented slug decomposed on disk. Identity only ever keeps a folder, and a zero inode (some SMB clients) proves nothing.
- **Every dot-named child is skipped**: that is `.orphaned` itself (a second start must leave it alone) and other tools' marker folders (`.stfolder`, `.Trash-1000`). No dataset folder can start with a dot, since `_name_to_slug` strips dots.
- **A folder that will not move stays put**: a locked folder (PM-021) or a permission error is logged and skipped, and the sweep carries on; nothing falls back to deleting. If `.orphaned` cannot be created (a file holds the name), no folder with content is moved at all.

Nothing deletes `.orphaned`'s contents; the user checks them and moves back, re-imports or deletes by hand (`docs/datasets.md` § Creating and managing datasets). A recovery UI and a retention policy were left out until someone needs them ([decision 13](decisions/13-scale-work-first.md)).

**Two known costs.** A build from before this change has no dot-skip, so it deletes `.orphaned` and everything parked in it at its first start: that covers a downgrade and any branch cut before it (`feat/m4-rating-port` until it is rebased). And `delete_dataset`'s `rmtree` has no retry, so on Windows a file still being served (PM-021) can leave part of a deleted dataset behind; the next start used to finish that delete, and now parks the leftovers in `.orphaned` instead.

**The sweep touches nothing when the DB and the tree visibly disagree**: when any row's `folder_path` resolves outside `datasets_dir` (a database copied from another machine, or `DATASETS_DIR` changed under it), or when there are rows and none of their folders exist (a datasets folder on a network share that is not mounted). Each time every folder would look orphaned, and the sweep would empty a whole tree of real datasets into `.orphaned` (before M9 stage 2, delete it); it logs a warning naming the reason instead. A stored path that is not absolute on this OS (`D:\...` on Linux, `/mnt/...` on Windows) counts as outside without being resolved, since `resolve()` would join it to the working directory. And with **no rows at all** it still sweeps only folders that hold no `images/` folder: a second install given another one's `DATASETS_DIR`, or a fresh database beside a copied tree, would otherwise delete every dataset there. `backend/tests/test_orphan_sweep.py` pins every refusal.

**Deferred blob columns**: `clip_embedding`, `dino_embedding`, and `dino_layer_embeddings` are declared with `deferred=True` on their `mapped_column`. SQLAlchemy omits them from `SELECT *` queries — they are only fetched when explicitly accessed or when `undefer()` is passed as a load option. The `GET /images/{image_id}` endpoint undefers `dino_layer_embeddings` so the `has_dino_layer_embeddings` property on `ImageOut` works. Quality/similarity routers use column-explicit selects (`select(Image.id, Image.clip_embedding, ...)`) and are unaffected. Never access these columns from a full-row ORM load without adding `undefer()`.

## The datasets root's one spelling

On Windows and macOS (`utils.PATHS_FOLD_CASE`) the root's letter case used to follow how the launch folder was typed (`c:\crucible` one launch, `C:\Crucible` the next) or a `.env` edit. Every stored absolute path begins with it, so one database could hold two spellings, and an exact match missed the older rows (PM-034). One lifespan step fixes this, `_settle_root_spelling`, which is never fatal. It runs right after `init_db()` and before anything that reads a stored path (the job-table passes, the orphan sweep, the queue), and calls `services/root_spelling.py::settle_root_spelling`:

1. It works out the root's on-disk case with `utils.on_disk_spelling`, which follows no link, because stored paths are deliberately unresolved.
2. `repair_root_spelling` rewrites every row whose root is a case variant of that spelling, across the six columns in its `PATH_COLUMNS`. No JSON column holds a root-derived path, and the version object store derives from `folder_path`.
3. `settings.datasets_dir` takes the new spelling only if the repair went ahead or had nothing to do. After a declined repair the rows keep the old spelling, and on macOS `within_datasets_dir` compares case-sensitively, so a setting that disagreed with them would 403 every serve route.

The repair reads with the exact `sql_has_prefix` negated, so a healthy database costs next to nothing. A string match is only the pre-filter: a variant root is rewritten only when `os.path.samefile` says it is the same folder. That leaves a case-variant folder that really is another one alone (a case-sensitive APFS volume, or a Windows folder with per-directory case sensitivity), and so is a database copied from another machine, so the orphan sweep's refusal in § SQLite engine and schema conventions still fires. The rewrite carries `updated_at` through, so it re-stamps no row.

The repair writes only after `db_maintenance.write_named_backup_sync("root-spelling")` succeeds. That function refuses a database that fails `quick_check`, and refuses when there is no database file. It writes `backups/<stem>.pre-root-spelling.db`, a name outside the `<stem>-*.db` rotation, so a repair that fails at every boot overwrites its one copy rather than flushing the pre-session backups out of `BACKUP_KEEP` or postponing the next integrity check. If the backup fails, the repair logs a warning, returns None and changes nothing.

On Linux a case variant is another folder, and nothing here runs. `backend/tests/test_root_spelling.py` covers it. The orphan sweep compares folded under `PATHS_FOLD_CASE` too: macOS's `resolve()` keeps the spelling it is given, so a row naming `foo` did not protect the folder `Foo`, renamed by case outside the app, from the sweep.

## Folder paths are stored stripped (migration b8d2f4a6c1e3)

`utils._subfolder_parts` strips the whitespace around every segment, so `knight ` and
`knight` are one folder ([decision 12](decisions/12-strip-folder-segment-whitespace.md)).
Every folder match is an exact compare, so the rows written before the rule were rewritten
once by migration `b8d2f4a6c1e3`, with the rule copied into the migration rather than
imported. The copy is `join_subfolder`'s form, so a `..` segment is **dropped**: the old
rule stored ` .. ` as a plain name, and stripped it would become a `..` that every
normalizing route refuses (it also repairs `..` rows from before the write-time guard).
It covers `images.subfolder`, `comfy_rows.subfolder`, the snapshot mirror
`version_image_states.subfolder`, the JSON lists `datasets.declared_subfolders` and
`comfy_plans.declared_folders` (entries stripped, blanks and duplicates dropped), and
`generate.subfolder` inside `runs.recipe` and `run_recipes.recipe`. `comfy_leaves.path` is
only counted, since expansion already strips it and a rewrite could collide on its
`(blueprint_id, path)` unique index.

- **The backup is the migration's own.** Migrations run before the app starts, so neither
  § Startup database backup nor `write_named_backup_sync` has run yet. When there is
  anything to change, the migration copies the database through its own connection to
  `backups/<stem>.pre-subfolder-strip.db` (outside the rotation glob) before the first
  UPDATE, and a failed copy raises, so `manage start` stops instead of rewriting
  unprotected rows. A clean database takes no copy and prints nothing.
- **Writers that bypassed the rule were fixed with it.** Folder import (the request folder
  and each `preserve_structure` path), the folder delete's `path` query and a saved or
  started run recipe's base folder now go through `normalize_subfolder` or
  `join_subfolder`. Raw copies of already-stored values (duplicate, snapshot capture and
  restore, copy rows) need nothing, since what they copy is clean.
- **Not reversible.** `downgrade()` is a no-op, because which rows were padded is not
  recorded. The backup is the way back.

## Migration drift check

`scripts/check_migrations.py` (run from anywhere with the venv active; CI runs it as the `migration-drift` job in `.github/workflows/backend-tests.yml`) upgrades a throwaway SQLite file to `head` and compares the result against `Base.metadata` with `alembic.autogenerate.compare_metadata`. It fails on more than one revision head, on an upgrade error, or on any diff not listed in its `ACCEPTED_DRIFT` set. Two implementation constraints are load-bearing: it must `os.chdir` into `backend/` (revision `d9f4a1c7b2e8` imports `backend.utils` at module scope, which only resolves after `env.py` fixes `sys.path`), and it sets `DATABASE_URL` before the first import so `config.settings` never points at the live DB — `env.py::get_url()` reads it lazily.

`ACCEPTED_DRIFT` holds 11 exact fingerprints, not a filter by diff *kind* — a kind filter would swallow the next real drift, which is the entire point of the check. They are the pre-existing, deliberate disagreements: eight `modify_nullable` (columns typed non-`Optional` on the model whose `CREATE TABLE` left them nullable), the two decorative self-referential FKs described above, and one index — `uq_version_branch_name`, a *partial* unique index whose `WHERE` clause autogenerate does not compare, so mirroring it onto the model would look guarded without being so (the script's comment carries the measurement). A fingerprint that stops appearing is a WARN telling you to delete the line. Adding to the set to make a red check green is the wrong fix; the right one is a migration.

## Startup database backup

`services/db_maintenance.py::run_startup_maintenance_sync` runs `PRAGMA quick_check` on the SQLite file behind `settings.database_url`, then copies it to `<db dir>/backups/<stem>-<timestamp>-<nnn>.db`, keeping the newest `BACKUP_KEEP` (5). `main.py`'s lifespan fires it as a **detached task** after `job_queue.start()` (held in `_background_tasks` so it is not garbage-collected mid-run) and never awaits it — the work is seconds of disk I/O on a large database and nothing user-facing depends on it. Failures log and are never fatal.

Three details that exist for a reason: a failed integrity check **skips the backup** (rotating a corrupt copy in would age out the newest good one); the copy goes through sqlite3's backup API rather than a file copy, because the live DB has a WAL sidecar and copying the `.db` alone captures a torn state; and the filename carries milliseconds *and* an always-present zero-padded counter, because rotation orders copies by name and a bare `-{stamp}.db` sorts **after** its own `-{stamp}-001.db` (`-` precedes `.`), which would delete the newest copy. Request-level tests never reach this — `api_env` does not run the lifespan; e2e boots a fresh tiny DB, where it is a no-op-sized copy. User-facing behaviour is documented in `docs/server.md` (§ Database backups).

A fourth, added later: the run **returns immediately** when the newest backup is younger than `BACKUP_MIN_AGE_SECONDS` (15 min), checked *before* `quick_check` because that scan is most of the cost. `manage.sh dev` runs uvicorn with `--reload --reload-dir backend` and uvicorn re-runs the lifespan on every reload, so each backend file save was integrity-checking and copying the whole database — and five saves flushed the entire pre-session history out of a 5-slot rotation. The restart loop (`docs/dev/http-edge.md` § Server control endpoints) has the same shape at lower frequency. Age comes from the newest backup's **mtime**, not its filename stamp; a future-dated file (clock skew) falls through and backs up, so skew can never wedge the guard permanently. Tests that drive the routine repeatedly must pin `BACKUP_MIN_AGE_SECONDS` to 0 — `test_db_maintenance.py` does this in the rotation and corrupt-database tests, which would otherwise pass without reaching the behaviour they name.
