# `scores_stale` — the bit that qualifies the ten `*_score` columns

This file covers `Image.scores_stale`: what an in-place pixel rewrite has to record, the single writer that records it, the embeddings that writer clears, the set-covering predicate that clears the bit, and the surfaces that render it. The scores it qualifies — which scorer writes which column, and why every `*_score` column is mirrored on `VersionImageState` — are `docs/dev/quality/scoring.md` § The scorers and their columns, which this file leans on rather than restates. The export preview pair that is the bit's costliest consumer is `docs/dev/export.md`.

## What the bit records

`Image.scores_stale: bool` (migration `b2f6c8d0e1a4`, mirrored on `VersionImageState`) records that the image's pixels were rewritten **in place** after the scores were measured. Ten paths do that — batch and single resize, batch and single crop, LUT grading, upscaling, crop-to-detection, and video frame re-extraction — and every one of them deliberately leaves the ten `*_score` columns and `quality_flags` alone. That is still the right call: nothing recomputes a score, and zeroing them would be a claim about pixels nobody measured. What was missing was any durable record of the mismatch.

The consequence lands far from the edit. `exclude_flags` at export drops images on `is_blurry`/`is_uniform`/`has_watermark`, all derived from those numbers, so an export silently drops keepers and ships rejects. `blur_score` makes it worse than a rounding issue: it is Laplacian variance against a fixed threshold, so it is resolution-dependent, and a score from a 1024px triage frame is systematically wrong for the 4K frame that replaced it.

**The bit is set only when the row already carries a score.** `record_in_place` tests `any(getattr(img, c) is not None for c in score_columns(type(img)))` before writing it, and never writes `False`. An image that has never been scored has no measurement to invalidate, and marking it put an amber badge on every card, a "Scores stale" chip on every detail page and an export warning reading *"edited in place after being scored"* on the commonest workflow there is — upload, batch resize, export — where no score and no flag exists. It also made the two ends disagree: the clear predicate below reads a row with no job scores as *not* stale, so the set site and the clear site defined "stale" differently. **`processing_history` and `scores_stale` therefore diverge on purpose**: the history entry is the durable "these pixels were rewritten" record and re-extraction's skip guard, so it is written either way; the bit qualifies a *measurement*.

**Existing rows are not backfilled.** Anything the earlier unconditional writer marked stays marked — nothing can tell a genuinely-stale row from a wrongly-marked one after the fact, and the badge is advisory. A dataset that has been resized before this change may still show badges on unscored images until it is scored or the rows are edited again.

## Every in-place pixel rewrite goes through record_in_place

**Every path that rewrites an image's pixels in place goes through `utils.record_in_place(img, op, **params)`.** It is the single writer of `Image.processing_history` — pass 2's re-extraction skip guard — *and* `Image.scores_stale`, the bit saying the ten `*_score` columns and the `quality_flags` derived from them were measured on pixels that no longer exist — written only for a row that carries one of those scores, since an unscored row has no measurement to invalidate, while the history entry is written either way. Two writers drift, and the failure is silent in the worse direction: a site that records the edit by hand leaves the scores looking trustworthy, and `exclude_flags` then drops images at export on flags computed against a deleted image. A structural AST guard in `backend/tests/test_scores_stale.py` fails CI for any `processing_history = … + …` list-concat outside `backend/utils.py`. Ten sites today: batch/single resize, batch/single crop, `crop_upscale`, LUT, upscale, crop-to-detection, re-extraction. The bit is cleared **only** by a `routers/quality.py` run that **actually measured something** and refreshed every score the row carries. See PM-010.

## The single writer

**The single writer is `backend/utils.py::record_in_place(img, op, **params)`** — the same call that appends the `processing_history` entry. That is not a convenience: two writers would drift, and a site that records the edit while leaving the scores looking trustworthy is worse than one that records nothing. `backend/tests/test_scores_stale.py` holds a structural AST guard that walks `backend/routers/*.py` and `backend/services/*.py` for any `processing_history = … + …` list-concat outside `utils.py` — the enforcement PM-010's convention never had. It matches only the `BinOp(Add)` shape, so the plain copies in `restore_snapshot` and `dataset_service` (which *carry* a history rather than extend one) are correctly excluded.

**The universe it tests is derived, not listed.** `backend/utils.py::score_columns(cls)` is an `lru_cache`d frozenset of every `*_score` column on a mapped class, so the eleventh score is covered the moment it is added. It takes the class rather than importing `Image`, keeping `utils.py` free of a runtime `backend.models` import (the dependency runs the other way). The suffix rule was already load-bearing — the structural guards in `test_video_lineage_mirrors.py` and `test_versioning_restore.py` derive the same set, and the comment on `Image.scores_stale` exists to protect it — so a literal frozenset here would have been a fourth copy plus a test to police the copy. It correctly excludes `dino_layer_scores` (plural: a blob of embeddings) and `scores_stale` itself. The `getattr` loop stays pure attribute access — no `*_score` column is `deferred` and nothing loads an `Image` under `load_only` — which is what keeps `record_in_place` placeable between an irreversible write and the `commit()` that describes it (PM-013). `test_no_score_column_is_deferred` pins that.

## Embeddings are cleared, not marked

**`record_in_place` also sets `clip_embedding`, `dino_embedding` and `dino_layer_embeddings` to NULL, unconditionally**, through `utils.clear_embeddings(img)`. The bit cannot cover them: a row with vectors and no `*_score` — embed for style similarity, then crop — is never marked, and style similarity went on comparing vectors of pixels that no longer existed. Fixed on 2026-11-12, after M9 left the report open.

- **Cleared rather than marked, because a vector has no stale bit and cannot be read here.** The three columns are `deferred`, so asking "was there a vector?" would lazy-load on an async session — IO where PM-013 says nothing may raise. Assigning to an unloaded deferred column records the value without loading the old one, so the clear is a pure write; a row with no vectors gets a harmless NULL in its UPDATE. `backend/tests/test_embeddings_cleared.py` pins that against a real session (no statement before the commit, one UPDATE naming all three) and that the three stay `deferred`.
- **NULL is the state every reader already handles.** Style similarity skips the row and counts it in `skipped`, `GET /quality/embedding-coverage` and the Stats tile count it as missing, and "Score what's missing" with Embeddings or DINOv2 ticked refills it (`docs/dev/quality/style-similarity.md`, `docs/dev/quality/scoring-job.md` § The chunked job loop).
- **The same rule held for a whole library once.** When the CLIP build was found wrong,
  migration `f3a8d1c6b9e2` cleared every `clip_embedding` rather than marking which build
  made it ([decision 17](../decisions/17-clip-quickgelu-fix.md)).
- **The universe is derived** by `utils.embedding_columns(cls)`: every column ending `_embedding` or `_embeddings`, as `score_columns` derives the scores.
- **What stays, until the next style run:** `style_similarity_score`, computed from those vectors, is a `*_score`, so the bit covers it like the others, and `dino_layer_scores` is written beside it. The edit clears neither. The next style run that covers the image skips it for lack of vectors and clears both then, so no old score sits among that run's (`docs/dev/quality/style-similarity.md` § A run clears what it skipped, and records only the references it used).
- **Snapshot restore is the one other caller.** The embeddings are not mirrored, so a restore that writes a file's old bytes back clears them too (`docs/dev/versioning/restore.md` § Measured, not mirrored).

## The clear predicate

**The clear site** is `_write_score_chunk` in `routers/quality.py`, run for every chunk of every check (the loop is `docs/dev/quality/scoring-job.md` § The chunked job loop). It is set-covering over what the run actually *wrote*, never over `body.run_*`:

```python
refreshed = done_cols | check.score_cols
if check.score_cols and row.scores_stale and img_id in clearable:
    stale_left = {c for c in _JOB_SCORE_COLUMNS if getattr(row, c) is not None} - refreshed
    if not stale_left:
        cleared.append(img_id)
```

`row` is the state read just before this chunk's write, which is right: a column this check writes is in `refreshed` whatever it held, and a column it does not write is untouched by the write. `done_cols` is the union of the score columns of every check that has finished in this job, so a row is cleared in the last check that touches it even though no single chunk wrote all its scores.

**The union is exact only because every earlier check wrote this row, and `clearable` is what holds that.** It is `stale_at_start - missed`: the rows stale when the job started (a snapshot), minus any some check should have written but did not, because its chunk came back short. Real scorers only come back short on a cancel, after which the job raises, but the predicate does not rest on that. Two consequences:

- **A row that turns stale mid-job is never cleared by that job.** It was edited while the job ran, so a score an earlier check measured may describe pixels that are gone. Under the old single-commit job that race spanned the whole run.
- **Under `only_unscored`, the snapshot rows pass every check's filter.** A check otherwise visits only rows missing its own output. Without the snapshot, a stale row whose aesthetic score was present would be skipped by the aesthetic check, and the technical check would then count `aesthetic_score` as refreshed and clear the bit over a stale score. That is why the user's ruling (2026-11-08) puts stale rows in "what's missing", and why the filter reads the snapshot rather than the live bit (`docs/dev/quality/scoring-job.md` § The chunked job loop).

One race is left, and it predates chunking: a row stale at the start and edited *again* between an earlier check's write and a later one's can still be cleared over the earlier check's pre-edit scores. Closing it would need a per-row edit counter read beside the paths.

The partial modes fall out of the same test: a cancel truncates a chunk so rows past the cut are never written, a per-image subset never visits the row, an unticked check contributes nothing, and **a run that measured nothing clears nothing**. That last one is what the `check.score_cols` conjunct is for: the CLIP and DINOv2 checks write no score column, and `stale_left` would otherwise be empty for any row whose job-score columns are all NULL — clearing the bit having taken no measurement. (`ScoreRequest` has no `run_duplicates`; duplicate flagging rides on `run_technical`, which does write scores.) So the common case — re-score with the same checks that produced the original numbers — clears the bit, and a watermark-only pass never declares a stale blur score fresh. The cleared ids go out as one `UPDATE … WHERE id IN (…)` per chunk, beside the bulk write. `quality_flags` needs no separate tracking, since each flag is written in the same guarded block as its score; `is_duplicate` derives from `phash`, which every in-place path re-derives, so duplicate flags were never stale.

**`_JOB_SCORE_COLUMNS` is `score_columns(Image) - _UNREFRESHABLE_SCORE_COLUMNS`** — derived from the same source as the set site, so the two ends of the bit are provably over one set. Derivation is the safe default because the failure directions are asymmetric: a hand-written list that misses an eleventh column **over-clears**, so the badge vanishes while a score is stale — silent, and the exact bug the feature exists to prevent — while a derived set that gains a column the job cannot refresh makes the bit **un-clearable**, a permanent badge that gets reported within the hour. `test_the_clear_universe_is_the_nine_scores_the_job_writes` pins the resulting nine names, so an eleventh score column fails CI with a decision to make rather than either outcome. `_TECHNICAL_SCORE_COLUMNS` stays an explicit literal: it names what one block writes, not a property of the schema.

**`Image.aesthetic_model` is deliberately outside all of this.** The marker recording which model produced each `aesthetic_score` (see `docs/dev/quality/aesthetic-model.md`) is written in the same guarded block as the score, but it never enters `refreshed` and it is not in `_JOB_SCORE_COLUMNS` — both are `*_score`-suffix-derived and correctly exclude a string that qualifies a measurement rather than being one. Adding it to `refreshed` is inert today, because `stale_left` only ever subtracts names it finds in `_JOB_SCORE_COLUMNS`; it becomes a live bug the day anyone re-derives that universe from a wider rule. `test_the_marker_is_not_a_score_column` in `backend/tests/test_aesthetic_model_marker.py` pins both exclusions.

**`style_similarity_score` is the sole member of `_UNREFRESHABLE_SCORE_COLUMNS`, and this is a boundary, not an oversight.** `compute_style_similarity` (its scoring flow is `docs/dev/quality/style-similarity.md` § Style similarity) writes it through a Core bulk `update(Image)` with no per-row load, so it cannot evaluate the predicate at all; letting it clear the bit would declare blur and aesthetic fresh when they are not. Keeping it in the clear universe instead would strand the bit permanently on any dataset that has ever run style similarity. Do not "fix" either direction. It stays **in** the *set* universe (`score_columns` covers every `*_score` column, and it is a measurement of those pixels like any other), which leaves one corner recorded rather than fixed: a row carrying only `style_similarity_score` is marked by an in-place edit, then cleared by any later run that measured something.

## Surfaces, and what e2e can reach

Surfaces: an 18×18 `var(--warn)` badge in `ImageCard`'s flag cluster, a `badge-yellow` "Scores stale" chip in `ImageDetailPage`'s flag row (**both render conditions include the bit** — an image whose only marker is this one must not render an empty cluster), and the `stale_scores_count` / `stale_scores_will_export` pair on the export preview (`docs/dev/export.md`).

**What e2e can and cannot reach.** `frontend/e2e/scores-stale.spec.ts` covers the *negative* journey only — an in-place resize of a never-scored image leaves the badge, the chip, the count and the warning all absent. The positive one is unreachable: no HTTP surface can write a score (there is no `PATCH /images/{id}` and no score field on any input schema, so only the copy/restore paths carry pre-existing scores), and `POST /quality/score` imports the aesthetic scorer at job start, which needs torch. So the three *rendered* stale surfaces have no test beyond `tsc`; the API field is pinned by `test_the_bit_is_on_both_image_payloads`, and the clear predicate by the stubbed-scorer tests. Hoisting `quality.py`'s unconditional `backend.ml.aesthetic_scorer` import into its `if body.run_*` guards would unlock both this and torch-free technical scoring — a real defect, deliberately left to its own change. Not offered yet, and reasonable follow-ups: a gallery filter, a Stats tile, a Quality-page "N images need re-scoring" call to action. Users see `docs/reading-scores.md`.
