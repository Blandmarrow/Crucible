# File browser

Covers the `/filesystem` router behind the File Browser page: its eight endpoints, the DB-sync guards on `POST /move`, `POST /rename` and `POST /delete`, the path-safety posture, and `FileBrowserPage` itself. It split out of `docs/dev/workspace.md`, which keeps the other three workspace surfaces — the sidebar hardware meters and `/system`, the Logs page, and Booru tag lookup. The dataset folder layout these guards defend is described in `docs/dev/datasets-page.md` (dataset rename, `DirPickerModal` — the other consumer of `GET /roots` and `GET /list`) and `docs/dev/versioning.md` (`.versions`); the rescan passes whose assumptions the guards protect are in `docs/dev/image-files.md` and `docs/dev/video.md`.

## Endpoints

Router: `backend/routers/filesystem.py`, prefix `/api/v1/filesystem`, registered in `main.py`.

| Endpoint | Purpose |
|---|---|
| `GET /roots` | Windows drive roots (`C:\`, `D:\`, …) |
| `GET /list?path=` | Directory listing — dirs first, then files, both alphabetical; `media_kind` per entry (`"image"`, `"video"` or null), replacing the older `is_image` boolean |
| `GET /preview?path=` | Serve any file in `MEDIA_EXTENSIONS` directly (`FileResponse`); videos get `video_mime` as the content type, and the `FileResponse` supplies the Range/206 a `<video>` needs to seek |
| `GET /image-meta?path=` | `{width, height, format, file_size_bytes, generation_metadata}` — reads file without touching DB. Image-only on purpose: a video container carries no EXIF or generation parameters |
| `POST /move` | Move file/dir; syncs the `Image` or `Video` row's `file_path`/`filename`, and 409s rather than re-homing a registered file, letting one leave its dataset's canonical `images/`/`videos/` folder, moving a folder holding either, or moving a folder of derived artifacts whose files live elsewhere (below) |
| `POST /rename` | Rename in place; for a matched `Image` also moves its thumbnail and `.txt` sidecar, and 409s on a name or thumbnail stem a sibling row owns. A **directory** is refused outright whenever it is a dataset's own folder, sits above one, carries a layout name, or holds rows or derived artifacts (below) |
| `POST /delete` | Delete file or directory (recursive), with the same care the router deletes take: busy guard, versioning hook, orphaned thumbnail/poster/sidecar cleanup, frame-lineage NULLing, `refresh_stats` (below) |
| `POST /mkdir` | Create directory |

## `POST /move`

**`POST /move` has two branches, chosen from `src` *before* `shutil.move` runs** — `src` no longer exists afterwards, so a late `is_file()`/`is_dir()` answers False for both and the whole sync becomes dead code (PM-011).

- **File branch.** Looks up the `Image` or `Video` row whose `file_path` is the source — also before the move, so the 409 below lands with the filesystem untouched, matching the collision guards' convention. If a row exists and the destination is not inside that row's own dataset, the move is **refused with a 409**: re-homing is `batch_move_dataset`'s job (provenance materialization, stats refresh, NULLing `Image.source_video_id`, moving the poster/thumbnail), and none of it happens here. The condition is `new_ds is None or new_ds.id != row.dataset_id` — deliberately broader than "another dataset", because a registered file moved out of the datasets tree entirely is equally broken: `utils.safe_dataset_path` then 403s every request for its bytes. Files with no DB row still move anywhere. Otherwise only `file_path`/`filename` are rewritten.

  Same dataset is not sufficient either: the destination must be *directly* the dataset's canonical media folder (`images/` for an image, `videos/` for a video), else 409. Two silent failure modes otherwise. `_rescan_videos` globs `videos_dir.glob("*")` non-recursively, so a video parked in `{ds}/images/` or `{ds}/videos/sub/` is reported under `videos_missing` forever while the file is perfectly fine. And images are stored **flat** — `Image.subfolder` is a purely logical column — so `images/sub/a.jpg` makes `thumbnail_path_for`'s `parent.parent` resolve to `images/thumbnails/`, at every site that re-derives a thumbnail path from a filename. The check is nested under "a row exists" on purpose: unregistered files still move anywhere, which is the file browser's actual job.
- **Directory branch.** Checks for rows under the moved folder before `shutil.move`, for the same reason the file branch does, and **refuses with a 409 if it finds one** — a single `Image`/`Video` whose `file_path` is under the old prefix is the whole predicate. The destination is not consulted at all. Unregistered folders still move anywhere, which is the file browser's actual job.

  The 409 is unconditional because the app supports exactly one layout for registered media — the one the file branch enforces per row, directly in the dataset's `images/` or `videos/`. A folder move can only land its contents one level *deeper* than that (`new_path.exists()` refuses the move back onto the original), so there is no destination this branch could permit that the file branch would not refuse file by file.

  **Same-dataset was permitted until V-21**, together with a prefix rewrite that kept `file_path` — and a `poster_path`/`thumbnail_path` that travelled with the tree — consistent with the new location. The rows were correct and the app was still wrong: `rescan_dataset` and `_rescan_videos` glob the canonical folders non-recursively, so every moved row is reported missing forever while its file is fine, and `thumbnail_path_for`'s `parent.parent` then resolves into a `thumbnails/` beside the *new* parent, orphaning the real thumbnail at the next rename. Supporting the layout instead would mean a recursive rescan plus stored-rather-than-derived thumbnail paths at eleven sites, against CLAUDE.md's flat-storage invariant — so the endpoint refuses to create a layout the rest of the app cannot read, and the rewrite went with the permission it existed to serve.

  The two destinations that were *always* refused motivate the guard and are still tested: `POST /move {src: "{ds}/images", dst_dir: "/outside"}` returned 200 and left every row's `file_path` outside `settings.datasets_dir`, where `utils.safe_dataset_path` 403s each one's bytes — a blank gallery with nothing in the DB saying why — and a move into *another* dataset's folder left `dataset_id` stale. A tree spanning two datasets needed a set-equality check when the destination still mattered; it no longer does.

  A user who rearranges a dataset folder in their own file manager, or a database written before V-21, still arrives in the out-of-layout state — unsupported rather than blocked, and `/rename`'s guard A is tested against it via `_relocate_out_of_layout` in `backend/tests/test_filesystem_rename_http.py`.

  A second directory guard covers the folders that hold **only derived artifacts**. `{ds}/thumbnails` and `{ds}/videos/thumbnails` contain no `file_path` at all, so the guard above matches nothing, the rewrite below has nothing to rewrite, and every stored `thumbnail_path`/`poster_path` in them is stranded by a 200. The predicate is "a derived path under the old prefix while that row's `file_path` is **not**", which is exactly what separates it from an ordinary media folder: for `{ds}/videos` the poster is under the prefix but so is `file_path` (second conjunct False, permitted); for `{ds}/images` the thumbnails are in the sibling `{ds}/thumbnails/` (first conjunct False); for `{ds}/thumbnails` both hold, so 409; and `{ds}` itself has both under the prefix and falls through to the row guard above, which already refuses it. The damage it prevents is a silent full-dataset cache regeneration plus a folder of orphaned `.webp`, not permanently broken tiles — `serve_thumbnail` regenerates a missing thumbnail and `get_video_poster` backfills a missing poster, both mkdir'ing their parent — but a move that silently invalidates a whole derived cache should not answer 200.

  Both prefix tests are escaped LIKEs (`startswith(..., autoescape=True)`). `ColumnOperators.startswith` defaults to `autoescape=False`, and `_` is a single-character LIKE wildcard *and* the character `_name_to_slug` puts in every multi-word dataset folder (plus the `_{ds_id[:8]}` collision fallback), so unescaped, `{ds}/my_dataset/…` matched `{ds}/myxdataset/…`. Here an over-matched row makes `Path(media.file_path).relative_to(src)` raise *after* `shutil.move` has run — files moved, no commit, 500, a PM-013 shape.

  Permitted moves then prefix-rewrite `file_path` for every matched row, plus that model's derived path (`Image.thumbnail_path`, `Video.poster_path`) **when and only when it also starts with the old prefix**. A poster lives under `videos/`, so it travels with the folder and its stored path must follow; an image's thumbnails live in `{ds}/thumbnails/`, beside `images/` rather than under it, so moving `images/` alone leaves them valid and an unconditional rewrite would point every row at a file that was never there. No `refresh_stats` on either branch: it recomputes counts and sizes only — never a path, never `dataset_id` — and the guard makes every permitted move a same-dataset one, so none of those numbers can change.

**No UI caller.** `filesystemApi.move` exists in `frontend/src/api/filesystem.ts` and nothing calls it — there is no move menu item, drag/drop or destination picker. The endpoint is API-only; the wrapper is scaffolding for a move UI that has not been built.

## `POST /rename`

Order: **gather → guard → mutate → commit**, the shape `/move` and `/delete` already use. The rows are loaded before `p.rename(...)`, so the 409s below land with the filesystem intact; the old code synced the DB *after* the rename and left no point at which a guard could still refuse.

The File Browser is one of the three paths that **adopt** a name rather than pick one (rescan's two halves are the others, `docs/dev/image-files.md` § Importing captions & folder rescan), so it cannot step to `_001` the way upload does — a typed name is taken as typed or refused. The **`Image` arm** therefore 409s twice: on a `filename` a sibling row already holds (otherwise a raw `uq_dataset_filename` IntegrityError 500, reachable once that sibling's file is gone from disk, since `new_path.exists()` catches the ordinary case first), and on a thumbnail stem a sibling owns. The occupied set is the same two terms rescan uses — `{ds}/thumbnails/*.webp` plus sibling `filename` stems — minus the row's own stem, which is what still lets a **pure extension change** (`a.jpg` → `a.png`) through: the stem is unchanged, so the thumbnail and the sidecar stay put and no uniquifier is involved (CLAUDE.md § Key invariants). Without the stem guard, `b.jpg` → `a.jpg` beside a registered `a.png` cleared both `new_path.exists()` and the unique constraint, and the next `bulk_rename`/`batch_move_dataset`/crop/restore recomputed `thumbnail_path_for` and moved or overwrote **`a.png`'s** thumbnail — PM-007 through a different door.

Permitted renames run `ensure_not_busy(row.dataset_id)` like `rename_image`/`rename_video` do, then mutate in `rename_image`'s exact order: assign `filename`, `file_path`, `thumbnail_path` and `is_auto_named = False`, then `utils.rename_with_sidecar`, then `commit()` — nothing fallible between the filesystem mutation and the commit describing it (PM-013). `old_thumb.replace(new_thumb)` follows the commit as a logged epilogue, wrapped in `try/except OSError` with the `exists()` check inside it (an `lstat` can raise too): sitting *before* the commit, an OSError there discarded a rename that had already happened on disk (V-87 — the fix ports `rename_image`'s V-81 twin). The row keeps naming `new_thumb` even when the move fails, because `serve_thumbnail` regenerates a missing thumbnail, so the row states intent and the next view heals it. A stored `thumbnail_path` outside `settings.datasets_dir` is left alone with a `logger.warning` rather than `.replace()`d into the tree, the rule `_add_orphan` follows below.

The **`Video` arm** rewrites `file_path`/`filename`, adds the cheap `uq_dataset_video_filename` pre-check for symmetry, and deliberately does **nothing** to `poster_path`: nothing re-derives a poster path — every consumer reads the column — so a poster whose stem no longer matches its video is the normal state rescan produces on purpose, not a hazard. A file with no row is a plain rename, which is the file browser's actual job. `backend/tests/test_filesystem_rename_http.py` covers all of it.

### Directory branch

Both arms above match on `file_path == str(p)`, so a **directory** matches neither and used to fall straight through to the plain `p.rename(...)` tail: `POST /rename {path: "{ds}/images", new_name: "pictures"}` returned 200 and stranded every row in the dataset. Unlike `/move`, this was reachable — `FileBrowserPage`'s context menu offers Rename for `entry.type === "dir"`, and `GET /list` hides no dotfiles, so `{ds}`, `{ds}/images` and `{ds}/.versions` are all one click away.

`_guard_directory_rename` only ever **refuses**, and takes no `ensure_not_busy` — every dataset-touching case is a refusal, and a directory that clears all four guards touches no dataset row. A prefix rewrite is the wrong remedy here, and this is where `/move` ended up too — V-21 deleted the one it had, for a version of the same reason. A rename is a same-parent move, so the only directories that can hold registered media are structural ones, and rewriting their paths leaves the DB agreeing with disk while the *dataset* stays broken. A rewritten `{ds}/images` makes `rescan_dataset` build `Path(folder_path)/"images"`, find nothing and take its no-`images_dir` early return while the next upload recreates the folder; `{ds}/videos` is worse, since `_rescan_videos` globs non-recursively and reports every video missing forever; `{ds}` itself leaves `Dataset.folder_path` stale, which no path rewrite touches. A rename had the additional problem that there was never anything to validate a rewrite against — `/move` could at least ask `_find_dataset_for_path(db, new_path)` for a destination dataset to check containment against, while a rename's new name is arbitrary — but that distinction stopped mattering when `/move` gave up rewriting as well.

Four guards, run **C → D → A → B** — most specific and most actionable first, each next one the more general fallback, so `{ds}` holding rows gets C's "rename the dataset instead" rather than A's generic message. **C**: a dataset's own folder, or any folder above one — the prefix arm is what catches `settings.datasets_dir` itself, and is the guard `/move` lacks entirely. **D**: the layout names `_DATASET_LAYOUT_DIRS = {images, videos, thumbnails, .versions}`, for a **direct** child of a dataset folder only. **A**: any `Image`/`Video` row with `file_path` under the prefix. **B**: `/move`'s derived-artifact guard verbatim. The three prefix tests are escaped LIKEs for the reason given under `/move` above; here an over-match is an over-*refusal* rather than a delete or a 500.

D exists because A, B and C are content-based, and `create_dataset` mkdirs `images/` and `thumbnails/` before a single row exists. **`.versions` is the strongest member of the set, not the marginal one**: no row anywhere stores a path under it, so the other three are blind to it permanently, even for a full dataset. Renamed, `restore_version` takes its `elif needs_restore:` branch and every snapshot silently restores nothing, `_prune_objects_sync` returns zeros forever, and the next `mark_image_deleted_in_versions` mkdirs a fresh `.versions/objects`. An empty `{ds}/thumbnails` is in the set for legibility — one rule, "a dataset's structural folders are not renameable" — not because it is dangerous; `{ds}/videos/thumbnails` is deliberately outside it, being no direct child, caught by B once a poster exists and inert when empty.

Comparisons are **unresolved strings** throughout, deliberately: `sanitize_abs_path` does not resolve, `Dataset.folder_path` is stored equally unresolved, and the File Browser only sends paths `GET /list` gave it — resolving here would harden one guard against a request shape `/move`'s two and `/delete`'s scope predicate all still let through. `FileBrowserPage`'s rename mutation surfaces the five `detail` strings through `apiErrorDetail`; without that it toasts a fixed "Rename failed" and the guards are API-only.

## `POST /delete`

Order: **gather → guard → hook → stage + flush → filesystem → commit → epilogue**. That reconciles two rules which look opposed. "Delete from the filesystem first, so a failed FS deletion leaves DB records intact" is about *commit* ordering and still holds — if `rmtree` raises, the endpoint returns before `commit()` and `get_db`'s session discards everything staged. CLAUDE.md's PM-013 invariant is about *what may fail between the mutation and the commit*, satisfied by issuing every fallible statement before the irreversible step and closing them with an explicit `flush()`.

Ordering constraints, each silent if violated: `ensure_not_busy` before any mutation, for every dataset the delete touches; `version_service.mark_image_deleted_in_versions` before the row deletes (it does `db.get(Image, image_id)`, which after a staged delete autoflushes, returns None and makes the hook no-op) **and** before the unlink (`_backup_and_record_hash` early-returns on a file that is gone) — see PM-014; orphans computed before the unlink; `refresh_stats` last, since it commits itself.

The orphan rule is one prefix test covering both models. In the **directory** branch a derived path is an orphan iff it does *not* start with the deleted prefix: an image's thumbnail sits in `{ds}/thumbnails/`, beside `images/`, so an `rmtree` of `images/` never reaches it, while a video's poster is in `videos/thumbnails/` and travels with `videos/`. In the **file** branch everything but the file itself is an orphan — the thumbnail or poster *and* the `.txt` sidecar, which `p.unlink()` really does strand (all three deletes in `routers/images.py` unlink theirs; this reaches parity). Deleting `{ds}/thumbnails` needs no code of its own: both read routes regenerate a missing derived file. Frames of a deleted video keep their rows with `source_video_id` NULLed, exactly as `DELETE /videos/{id}` leaves them. `backend/tests/test_filesystem_delete_http.py` covers all of it.

## Name collisions

Name collisions are 409s, checked before the filesystem is touched: `POST /move` onto an existing name at the destination, `POST /rename` onto an existing sibling, `POST /mkdir` where the name already exists (as a directory *or* a file — the guard is `exists()`, not `is_dir()`). `backend/tests/test_conflict_paths_http.py` asserts each one leaves both sides on disk untouched.

## DB sync

`_find_dataset_for_path(db, file_path)` checks if `file_path` is inside any dataset's `folder_path` and returns the dataset — a `LIKE` pre-filter over `Dataset.folder_path` (longest first) with `relative_to` as the authoritative check. Both branches' guards use it. Delete still matches on the exact path and needs no dataset lookup; rename's **file** arms do too, but its directory guard runs two `Dataset.folder_path` queries of its own (an exact-or-prefix match, then a parent match for the layout names) rather than going through `_find_dataset_for_path`, because it needs to tell "is this folder a dataset's" from "is this folder inside one".

## Path safety

`sanitize_abs_path()` (from `backend/utils.py`) rejects null bytes and requires an absolute path. No further sandbox for the *client-supplied* path — this is a local desktop app with intentional full-filesystem access. A **stored** path is different: every dataset folder is created under `settings.datasets_dir`, so a `thumbnail_path`/`poster_path` outside it was never written by this app, and `POST /delete` runs each one through `utils.within_datasets_dir` before unlinking it as an orphan rather than deleting it on the strength of a request that named a different directory.

## Still open

Recorded rather than fixed: `Image.subfolder` travels unchanged, so a file moved between subfolders of its own dataset keeps the old sidebar grouping. A *dataset's own folder* is now an **asymmetry** rather than a shared hole: `POST /rename` refuses it outright (guard C above, empty or not, and refuses any folder *above* one too), while `/move` still only refuses it when it holds a row — so an empty dataset's folder still moves, leaving `Dataset.folder_path` stale, and `POST /delete` of that folder is the symmetric hole. Neither `/move` nor `/delete` has rename's layout-name guard either, which is why `POST /delete {path: "{ds}/.versions"}` still `rmtree`s the object store behind a 200. The canonical-media-root rule is no longer file-branch only — V-21 closed that gap by refusing the directory move outright rather than extending the predicate, since the predicate would have made the branch's path rewrite unreachable; see § `POST /move`.

## Frontend

Frontend page: `FileBrowserPage.tsx`, route `/file-browser`, sidebar nav item "File Browser". Three-panel layout (`200px | 1fr | 280px`): left = drive roots + quick-access links, middle = breadcrumb + file list + context menu (rename/delete/import), right = a preview panel. That panel branches on `entry.media_kind`: a video renders `<video controls preload="metadata">` against `GET /preview` — `preload="metadata"` so selecting a file in the list does not pull a whole clip off disk, and seeking works because the `FileResponse` supplies Range/206 on its own — while an image renders `<img>` plus the `<GenerationMetadata>` panel. The `["fs-image-meta", path]` query is `enabled: !isVideo`, since `/image-meta` reads EXIF and generation parameters and a container carries neither.

API client: `frontend/src/api/filesystem.ts` — thin wrappers over all endpoints; `previewUrl(path)` returns a URL string for use in `<img src>`.
