# Dataset folders: deleting a dataset, the startup orphan sweep and the root's spelling

This file covers how a dataset's folder on disk is kept in step with its database row: the delete endpoint's DB-first folder removal and `remove_dataset_dir`, the startup orphan sweep that parks unreferenced folders in `.orphaned/` and the refusals that keep it from emptying a tree of real datasets, and the one-time repair that gives the datasets root a single on-disk spelling. The engine, FKs, indexes and the other schema conventions are in `docs/dev/database.md`. The lifespan hook that runs the sweep, and the job-table passes before it, are in `docs/dev/backend-infrastructure.md` § Stale job cleanup at startup. The sweep's user-facing side is `docs/datasets.md` § Creating and managing datasets, and running two installs beside each other is `docs/dev/multiple-installs.md`. Its plan and measurements are in `docs/dev/scale-plan/README.md`.

## Dataset-folder deletion & the startup orphan sweep

Deleting a dataset is DB-first — `delete_dataset` (`routers/datasets.py`) removes the row and commits, then removes the on-disk folder via `remove_dataset_dir(folder)` (`services/dataset_service.py`). That helper replaces the old `shutil.rmtree(..., ignore_errors=True)`: it uses `rmtree`'s error callback (with an `onexc`/`onerror` fallback so it works on Python ≥3.12 and older) to **log a warning** naming exactly what couldn't be removed, instead of silently swallowing a partial delete. Because folder cleanup is bolted onto the row-delete path, a folder is orphaned whenever a dataset row disappears by another route (DB reset/migration/swap, manual edit). `sweep_orphan_dataset_folders(db)` reconciles this at startup: the `lifespan` hook in `main.py` calls it (via `_sweep_orphan_dataset_folders`, after `init_db()` and the two job-table passes — `mark_interrupted_jobs()` then `_sweep_old_jobs()` — and before `job_queue.start()`, which is the load-bearing half), and it handles every child directory of `settings.datasets_dir` whose resolved path is not referenced by any `Dataset.folder_path` (the two job-table passes are described in `docs/dev/backend-infrastructure.md` § Stale job cleanup at startup and § Job retention sweep). It runs before any job starts, so no job is writing into a folder the sweep is judging. `create_dataset` makes the empty folders just before its single commit, so a crash between the two leaves an empty shell with no row, and every import or upload fills a folder only once its row is committed. Keep both properties if you touch that path: the sweep's rules below rely on them. `remove_dataset_dir` no-ops safely on a missing path.

## The sweep moves data aside and never deletes it

This is M9 stage 2 (`docs/dev/scale-plan/README.md`). "No row" does not mean "abandoned": restoring an older database backup (`db_maintenance`'s own copies) leaves every dataset created since without a row, and a folder copied in by hand has none either, and the old sweep `rmtree`'d all of them. Now each unreferenced folder goes to `datasets_dir/.orphaned/<name>-<YYYYmmdd-HHMMSS>` (UTC, one stamp per sweep, `-2`, `-3`… on a taken name) through `utils.rename_retrying`, a same-volume rename that is instant at any size, and one warning names every move. The rules that keep it safe, each pinned in `backend/tests/test_orphan_sweep.py`:

- **Only a tree proven empty is deleted, and never with `rmtree`** (`_empty_tree_dirs`): a failed create's empty shell is removed one `os.rmdir` at a time, deepest first, rather than piling up in `.orphaned`. `os.rmdir` refuses a folder that is not empty, so a file written after the walk (a sync client, a stray second install) stops the delete instead of going with it. A link anywhere counts as content and is never followed: a symlink, or a **Windows junction**, which `os.path.islink` does not report and `os.walk` walks into, hence `_is_link`'s `os.path.isjunction`. So does anything `os.walk` cannot read, because the walk silently skips an unreadable folder and would otherwise call its tree empty.
- **A folder the rows name by another spelling is kept**: besides the string match (case-folded under `PATHS_FOLD_CASE`, § The datasets root's one spelling), a child whose `(st_dev, st_ino)` matches an existing row folder is known. That catches a case-insensitive mount where `PATHS_FOLD_CASE` is False, and macOS storing an accented slug decomposed on disk. Identity only ever keeps a folder, and a zero inode (some SMB clients) proves nothing.
- **Every dot-named child is skipped**: that is `.orphaned` itself (a second start must leave it alone) and other tools' marker folders (`.stfolder`, `.Trash-1000`). No dataset folder can start with a dot, since `_name_to_slug` strips dots.
- **A folder that will not move stays put**: a locked folder (PM-021) or a permission error is logged and skipped, and the sweep carries on; nothing falls back to deleting. If `.orphaned` cannot be created (a file holds the name), no folder with content is moved at all.

Nothing deletes `.orphaned`'s contents; the user checks them and moves back, re-imports or deletes by hand (`docs/datasets.md` § Creating and managing datasets). A recovery UI and a retention policy were left out until someone needs them ([decision 13](decisions/13-scale-work-first.md)).

## Two known costs

A build from before this change has no dot-skip, so it deletes `.orphaned` and everything parked in it at its first start: that covers a downgrade and any branch cut before it (`feat/m4-rating-port` until it is rebased). And `delete_dataset`'s `rmtree` has no retry, so on Windows a file still being served (PM-021) can leave part of a deleted dataset behind; the next start used to finish that delete, and now parks the leftovers in `.orphaned` instead.

## The sweep touches nothing when the DB and the tree visibly disagree

The sweep touches nothing when any row's `folder_path` resolves outside `datasets_dir` (a database copied from another machine, or `DATASETS_DIR` changed under it), or when there are rows and none of their folders exist (a datasets folder on a network share that is not mounted). Each time every folder would look orphaned, and the sweep would empty a whole tree of real datasets into `.orphaned` (before M9 stage 2, delete it); it logs a warning naming the reason instead. A stored path that is not absolute on this OS (`D:\...` on Linux, `/mnt/...` on Windows) counts as outside without being resolved, since `resolve()` would join it to the working directory. And with **no rows at all** it still sweeps only folders that hold no `images/` folder: a second install given another one's `DATASETS_DIR`, or a fresh database beside a copied tree, would otherwise delete every dataset there. `backend/tests/test_orphan_sweep.py` pins every refusal.

## The datasets root's one spelling

On Windows and macOS (`utils.PATHS_FOLD_CASE`) the root's letter case used to follow how the launch folder was typed (`c:\crucible` one launch, `C:\Crucible` the next) or a `.env` edit. Every stored absolute path begins with it, so one database could hold two spellings, and an exact match missed the older rows (PM-034). One lifespan step fixes this, `_settle_root_spelling`, which is never fatal. It runs right after `init_db()` and before anything that reads a stored path (the job-table passes, the orphan sweep, the queue), and calls `services/root_spelling.py::settle_root_spelling`:

1. It works out the root's on-disk case with `utils.on_disk_spelling`, which follows no link, because stored paths are deliberately unresolved.
2. `repair_root_spelling` rewrites every row whose root is a case variant of that spelling, across the six columns in its `PATH_COLUMNS`. No JSON column holds a root-derived path, and the version object store derives from `folder_path`.
3. `settings.datasets_dir` takes the new spelling only if the repair went ahead or had nothing to do. After a declined repair the rows keep the old spelling, and on macOS `within_datasets_dir` compares case-sensitively, so a setting that disagreed with them would 403 every serve route.

The repair reads with the exact `sql_has_prefix` negated, so a healthy database costs next to nothing. A string match is only the pre-filter: a variant root is rewritten only when `os.path.samefile` says it is the same folder. That leaves a case-variant folder that really is another one alone (a case-sensitive APFS volume, or a Windows folder with per-directory case sensitivity), and so is a database copied from another machine, so the orphan sweep's refusal in § The sweep touches nothing when the DB and the tree visibly disagree still fires. The rewrite carries `updated_at` through, so it re-stamps no row.

The repair writes only after `db_maintenance.write_named_backup_sync("root-spelling")` succeeds. That function refuses a database that fails `quick_check`, and refuses when there is no database file. It writes `backups/<stem>.pre-root-spelling.db`, a name outside the `<stem>-*.db` rotation, so a repair that fails at every boot overwrites its one copy rather than flushing the pre-session backups out of `BACKUP_KEEP` or postponing the next integrity check. If the backup fails, the repair logs a warning, returns None and changes nothing.

On Linux a case variant is another folder, and nothing here runs. `backend/tests/test_root_spelling.py` covers it. The orphan sweep compares folded under `PATHS_FOLD_CASE` too: macOS's `resolve()` keeps the spelling it is given, so a row naming `foo` did not protect the folder `Foo`, renamed by case outside the app, from the sweep.
