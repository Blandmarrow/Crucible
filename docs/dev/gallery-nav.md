# Gallery navigation context: how the arrows walk

The `gallery-nav-*` snapshot that `ImageDetailPage` walks with ← / →: what it stores, the two
boundary prefetch queries, `injectNavId` for newly created images, `atEnd` and the post-delete
re-derivation, and the live refresh that keeps both the arrows and the counter honest while a job
adds rows. The sibling key `gallery-state-*` — what the grid restores when you come **Back** — is
in `docs/dev/gallery-state.md`. The rest of the detail view is in `docs/dev/image-detail.md`.

## The stored context

`GalleryPage` writes it keyed by `datasetId`:

| Key | Storage | Contents | Purpose |
|---|---|---|---|
| `gallery-nav-${datasetId}` | `sessionStorage` | `{ ids, page, limit, sort, order, filters }` | Ordered image ID list + query context for prev/next navigation in the detail view — session-only, regenerated on next visit. `filters` is the gallery's whole `ImageFilterParams` memo; the shape is declared once in `frontend/src/utils/galleryNav.ts` |

`ImageDetailPage` reads `gallery-nav-*` (`sessionStorage`) for arrow-key navigation. At page boundaries it pre-fetches the adjacent page (`useQuery`, `enabled: atEnd / atStart`); on crossing, writes the new context back to `gallery-nav-*` (sessionStorage) and updates `gallery-state-*` (**`localStorage`**) so **Back** returns to the correct gallery page. **The nav context carries the grid's whole filter set, and it comes from the same `filterParams` memo the grid queries with** (`GalleryPage.tsx` § the `writeNavContext` effect) — so both boundary queries spread `navCtx.filters` and cannot describe a different set of images than the gallery was showing. A new gallery filter must therefore join that memo rather than be threaded to the detail view separately; one that does not is dropped at the boundary, and arrow-keying past a page edge steps outside it. (It carried only `captioned` until this was fixed, which is why paging past the last image of a subfolder landed in the middle of the unfiltered dataset.) `dataset_id` is re-applied *after* the spread so the URL's dataset always wins over a stale stored one, and `limit` comes from the context rather than a fresh `getGalleryPageSize()` read — the gallery captures the page size once at mount, so re-reading the setting here made the two disagree when it changed mid-session. `frontend/e2e/gallery-nav-filters.spec.ts` is the regression test, at a named subfolder and at the dataset root (`""` is a real filter, so a `subfolder || undefined` normalization would break only the root).

Both queries build their params through `navPageParams(datasetId, ctx, page)` (`utils/galleryNav.ts`), shared with the post-delete refresh below so the three requests cannot drift apart; only the `queryFn` uses it — the two key array literals stay written out, because TanStack's `hashKey` sorting and `undefined`-dropping is what makes the key and the request agree by construction. Both entries carry `staleTime: 60_000` under `["gallery-nav", datasetId, …]`, so **anything that adds or removes image rows has to evict them**: `invalidateDatasetContentScope` (`docs/dev/frontend-core.md` § `constants/`) `resetQueries` that key alongside the eight it invalidates. Reset rather than invalidate because this cache is a navigation target rather than something on screen — an invalidated entry is still served while it refetches, and → would step onto a deleted id and 404. Nothing touched the key until this was added, so the pre-delete page was served for a full minute.

Both pages must use the same storage backend for `gallery-state-*` — `ImageDetailPage`'s page-crossing handler reads and writes it through `localStorage`; do not revert to `sessionStorage` there. Arrow keys are suppressed when an `<input>`, `<textarea>`, or `<select>` has focus, or when `isContentEditable` is true. The `Delete` key opens a confirm dialog in both gallery and detail view; both handlers share the same focus guard. The arrow-key handler is additionally suppressed while the delete confirm dialog is open (`showDeleteConfirm`) to prevent background navigation.

## Newly created images: injectNavId

**Nav context invariant for newly created images**: When navigating to an image that was just created (crop, upscale new-file), the new image ID is not in the existing `gallery-nav-*` list, so `currentIndex === -1` and arrow keys would silently do nothing. Always call `injectNavId(datasetId, sourceImageId, newImageId)` (exported by `frontend/src/utils/galleryNav.ts`) before calling `paneGo` to insert the new ID immediately after the source in the nav context. This applies at four sites: sync crop, crop+upscale job completion, standalone upscale (non-replace) completion, and LUT new-file completion — the LUT job's handler navigates to the new image exactly as the other two job handlers do. `removeNavId(datasetId, imageId)` is the mirror image — it splices an id out — but it is **no longer what the delete path normally does**; it survives only as that path's offline fallback (next paragraph). Both delegate to a module-private `mutateNavIds(datasetId, transform)`, which routes through `readNavContext`/`writeNavContext` — so a context written by an older build is normalized on the way through rather than staying legacy. Growing `ids` this way makes it one longer than `limit`, which turns `atEnd` false and disables **Next** until the user returns to the gallery; that is deliberate, since creating an image shifts server-side paging by one and a relaxed `>=` test would land on a duplicate.

## atEnd, and the post-delete re-derivation

**`atEnd` is a strict `ids.length === limit`, so it fails in the shrink direction too** — a list left one *short* never satisfies it either. That is what made the old splice-on-delete a dead end: deleting from the detail view left `limit - 1` ids, so **Next** went dead at the end of that page for the rest of the session, biting the exact workflow the arrows exist for (arrow through a folder, delete the bad ones, keep going). So `deleteMutation.onSuccess` re-derives the context from the server instead: it awaits `imagesApi.list(navPageParams(datasetId, navCtx, navCtx.page))` — page N as it is *now* — takes `ids` from the response, and navigates to `rows[currentIndex] ?? rows[rows.length - 1]` (the row that slid into the deleted slot; the index is bounds-checked because a concurrent delete can shrink the page by more than one). Deleting the only image of the last page makes that empty, and the fallback then has to move `page` as well as `ids` — it steps back onto the prefetched previous page and calls `syncGalleryStatePage` (the same `gallery-state-*` patch `goTo` uses when it crosses a boundary, lifted into a module-local helper), or the context describes an empty page and *both* arrows die. `currentIndex === -1` (a deep link carrying a foreign context) skips all of it.

Three orderings inside that handler are load-bearing. The refresh runs **before** the cache mutation: `removeQueries(["image", imageId])` ahead of the await rebuilds that query and refetches the id just deleted, and 404s are not retried, so the user gets a flash of the "Image not found" screen for the length of the refresh. `setShowDeleteConfirm(false)` stays **after** the await, because the arrow keys are suppressed while it is true and TanStack live-swaps the `onSuccess` closure on every commit — closing the dialog first re-arms → for an extra round trip, and a keypress in that window would feed the handler a different `imageId`/`navCtx`/`currentIndex`. And the fetch is wrapped in `try/catch`, because a throw inside `onSuccess` routes to `onError` and a delete that succeeded would toast "Delete failed"; that catch is the one place `removeNavId` still runs, `limit - 1` freeze and all. One accepted consequence: a derivative `injectNavId` spliced in that does not sort onto page N drops out of the arrow sequence until the user revisits the gallery. Three cases in `frontend/e2e/gallery-nav-filters.spec.ts` cover the boundary delete, the mid-page delete walked to the end, and the emptied last page.

## Live refresh while a job adds rows

**`gallery-nav-*` is a snapshot, not a query, so a job that adds rows has to rewrite it.** While `comfy_generate` fills a dataset, the arrows and the counter used to freeze at whatever the gallery last wrote: `TopBar`'s per-row `["images", datasetId]` invalidation refreshes the *grid's* query, and the grid is unmounted. `refreshNavContext` (a `useCallback` on `[datasetId, imageId, qc]`) re-fetches `navPageParams(datasetId, ctx, ctx.page)` and writes the response **verbatim** — never a splice, because `atEnd` fails in both directions (above). Its guarantee is that the stored ids always describe the server's *current* page N under the stored filters; on the default Newest-first sort the new rows prepend and the denominator never moves, so the visible signal is the total rather than the counter.

If the open image is no longer on page N, it probes page N+1 first — with a prepending sort the drift is almost always one page, and this avoids pulling a 20,000-id payload for the common relocate — then falls back to `imagesApi.listIds(navIdsParams(datasetId, ctx))`, the sibling of `navPageParams` and declared in `utils/galleryNav.ts` for the same reason it is. That branch takes its slice only when `!truncated || page * limit <= ids.length`: `GET /images/ids` trims at `SELECT_ALL_ID_CAP` (20,000), so a slice at the tail of a truncated response comes back *short*, which is the `atEnd` freeze again. An id found nowhere, and any throw, keeps the old snapshot — a wrong-length list is worse than a stale one, the rule the delete path's `catch` already states. A relocate also calls `syncGalleryStatePage`, so **Back** lands right; that helper's `scrollTop: 0` write is now reachable from a *background* event for the first time, and discarding the gallery's saved scroll offset is the accepted cost of not sending Back to the wrong page.

**What fires it, and the four guards that keep it from doing harm.** `NAV_REFRESH_JOB_TYPES` (module scope in `ImageDetailPage.tsx`) is the six jobs that add or remove `Image` rows: `comfy_generate`, `video_extract` (replace mode deletes the previous frames first), `import`, `rescan`, `restore_snapshot`, `checkout_branch`. The exclusions are deliberate and must not be "completed" — `video_reextract` rewrites frames in place, so no row's identity changes; the `injectNavId` jobs (`crop_upscale`, `batch_upscale`, `batch_lut`, `crop_to_detection`, batch crop/resize) *do* add rows but are owned by this page, and a refresh would silently undo the injected slot; `caption`/`quality_score` change no row's existence, and under a `captioned: false` or score filter a refresh would evict the user's own open image from its own result set on every tick. The wake-up signal is a *scalar* Zustand selector — `${job_id}:${status}:${done}|` over the watched jobs only — never `activeJobs` itself, since `updateJob` rebuilds the Map on every SSE event app-wide (idiom: `StatsPage`'s `hasActiveJob`); no new SSE hook is mounted, because `TopBar`'s `useAllJobsSSE` is the single subscriber that fills the store.

A watcher effect then reads the store non-reactively and fires only on a high-water `done` advance or a first non-optimistic terminal status: `done` steps twice per comfy row (`comfy.py` opens with `done=i` and closes with `done=i+1`, so a strict `>` collapses the pair onto the closing emit, after the rows are committed) and is not monotone (`video_extract` pins it at 0 through its replacing/detecting phases), which is why a high-water map rather than a `!==` compare. The four guards: (1) an active-pane bail (`paneCtx && paneCtx.paneId !== activePaneId`), **required** rather than defensive, since `splitPane` clones the view and both panes share the one sessionStorage key — they would otherwise ping-pong `page` on every generated row; (2) a bail on `ids.length > ctx.limit`, which is `injectNavId` holding the list; (3) an in-flight ref plus exactly one trailing re-run; (4) a compare-and-swap re-read of the context before the write, because `deleteMutation.onSuccess` writes the same key from inside its own `await` and a blind write could resurrect a page still listing the deleted row. `navRefreshSeq` — a state bump, since a sessionStorage write is invisible to React — is what re-runs the `navCtx` memo; it and `navCtx` are absent from the watcher's dep array, and that absence is the proof the loop cannot close.

## The live total

**The live total shares the gallery's count entry.** `constants/queryKeys.ts::imagesCountKey(datasetId, filters)` → `["images", datasetId, "count", filters]` backs both `GalleryPage`'s pagination total and the detail view's third counter number, so the two can never disagree. The filters go in as **one object** rather than a spread list of values, which is what makes the sharing work: `hashKey` sorts a plain object's keys and drops `undefined` props, so the gallery's live `ImageFilterParams` memo and the JSON-round-tripped `ctx.filters` hash identically. Nesting under `["images", datasetId]` is why the number climbs with no job watching at all — TopBar invalidates that prefix per generated row and on every terminal image-modifying job; `refreshNavContext` invalidates the key explicitly to cover the job types that prefix pass misses (`rescan`, the two versioning jobs). It renders as a muted third number (`12 / 100 · 347`), hidden when `total <= ids.length` so a partial page does not print its own denominator twice. Two cases in `frontend/e2e/gallery-nav-filters.spec.ts` cover it, both driving a real `rescan` because CI has no ComfyUI: name-ascending, where the new rows grow a short last page into a full one (denominator, total and → asserted together), and newest-first, where they prepend and push the open image onto page 2 — the relocate branch, which also asserts that **Back** followed the context there.
